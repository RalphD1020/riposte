## Gates

| Package         | Tool                           | Gate                                                                                         |
| --------------- | ------------------------------ | -------------------------------------------------------------------------------------------- |
| `@riposte/web`  | Vitest + `@vitest/coverage-v8` | 100% per file (statements, branches, functions, lines) + manifest check                      |
| `@riposte/game` | Godot headless harness         | Behavioral: every suite green, zero engine ERROR/WARNING, zero leaks (not measured coverage) |

`pnpm test` is `turbo run test test:coverage` (the gating Godot harness + website coverage). `pnpm test:balance` runs the CPU balance smoke — CPU-BALANCE, non-held-out seeds only — in its own process with its own progress guard. `pnpm test:balance:audit` prints the tuning corpus (40 seeds, `CpuLadder.AUDIT_SEEDS`), a line per duel, and asserts nothing; `pnpm test:balance:accept` runs the held-out ladder (CPU-ACCEPT), once after a tuning pass. Every CPU duel prints a progress line, so the no-output guard stays a hang detector, never a budget. `pnpm test:fast` skips coverage. `pnpm check` runs `--import`, lint, typecheck, format, docs, arch, integrity, security, and `test:tooling`; it MUST NOT re-run behavior suites. `pnpm verify` is check → test → test:balance → build.

A hang guard detects hangs; it is never a budget. Each tier's guard is a **progress** guard: the Godot process is killed only after 480 s with no output (`spawnGodotWatched`, which prints why), and `TestCase` prints a line as each case finishes, so adding suites or long cases can never make a progressing run look hung, and gameplay code is never optimised to fit the harness. The benchmark tier exists so a long, non-gating measurement stays out of the correctness run.

## Web coverage scope

`src/**/*.{ts,tsx}` except tests, `*.d.ts`, and `src/test/**`. Routes and layouts are covered too (`apps/web/src/app/AppRoutes.test.tsx`); do not exclude pages to dodge coverage. `test:coverage` then runs `apps/web/scripts/check-coverage-manifest.mjs`: a source file no test imports fails the gate. `apps/web/src/app/theme.test.ts` is the website contrast gate.

## Game harness

`game/tests/harness/headless_runner.gd` runs `SUITES` in order and prints one `RIPOSTE_RESULT` line. `RIPOSTE_TIER` selects the tier: `gate` (default) skips `BENCHMARK_SUITES`, `balance` runs only them; a named `RIPOSTE_SUITE` runs regardless of tier. A suite fails on any failed assertion, a zero-assertion case, or leaked orphan nodes; the runner fails on engine errors or ObjectDB leaks at exit (the root waits briefly so the audio thread releases stopped voices). Cases are `test_*` methods and may `await`.

The Node wrapper around that harness (`game/scripts/godot.mjs` `runTest`) drops one exact engine line: `ERROR: RiposteApp: match music is missing` (`EXPECTED_TEST_ENGINE_ERROR` in `scripts/godot-bin.mjs`). That is a deliberate compromise so the missing-theme case can `push_error` and still pass. `parseEngineIssues` itself is unfiltered; `pnpm check` and export still fail on that line. `TOOL-TEST-003` proves the filter drops only that line and that any other `ERROR:` still classifies as `HARNESS_FAILURE`. The owning test (`test_a_missing_match_theme_stops_the_loop`) asserts `last_music_fault == RiposteApp.FAULT_MATCH_MUSIC_MISSING`, that playback stopped, that the stream was cleared, and that the menu theme returns. An unexpected extra occurrence of that same line in another test of the same process would also be dropped; that remaining gap is accepted because the diagnostic is named, asserted by the test that owns it, and not otherwise produced.

A claim names the layer that proves it. Godot's own testing docs distinguish unit, integration, and expected-error cases; the application suite does the same:

- **Presentation policy** (PRES-CROWD, PRES-FACE): constructed events and placed starts. Honest about those fixtures. Crowd priority, cooldown, intensity, decay, scoreline finish latch, and victory-once live here. Not a hearing proof and not a player journey.
- **Presenter integration** (PRES-PRESENTER, PRES-RIG): a real `MatchPresenter` fed snapshots and events a test builds. It proves the presentation contract — one death, one sword, the terminal policy, clocks, latches, crowd-bed ownership — but its inputs are constructed, so it is not gameplay proof.
- **App lifecycle** (APP-E2E): the shipped scene and screens, with an idle or touch-driven human against the CPU. It proves the app flow (including music selection and that the crowd bed does not leak to Results), not specific combat outcomes. It does not manufacture a successful fight by assigning velocity or writing scores.
- **Full gameplay** (FULL-E2E): the shipped scene from Quick Play, the human driven only through real input (`AppDriver.hold_move` presses the move actions and dash modifier on the Input singleton; the attack key goes through `push_input`), one frame per tick, and the real clock, solver, presenter, results, and victory showcase. Terminal scenarios (slash kill, lethal thrust, nonlethal poke, walk-off, shove off the edge, mirror colorway, next-round cleanup, leaving the victory), the bind exchange (a walk-in that meets, backs off, and meets again; a pressed bind that keeps one contact while the point slides, then parts on a back-step, the following tap consumed on the parting tick, which is already a legal attack so the blade has not moved — the torso after that tap is not claimed), the three combat journeys (PROBE-EVASION: a back-dash before the release makes a tap miss, against a standing control it meets; PARRY-RIPOSTE: a step aside carries the crossguard into a tap's path, the protective steel parries it and the walked-in riposte lands; BAIT: giving ground with the sword wound makes a full advancing cut whiff — their scripted attackers judge measure on what they saw 100 ms earlier, and each asserts the order of facts, never a tick count) and the POST-ROUND journeys (the winner walking on through the result, pushing the body, the next round arriving clean) stand a scripted opponent (`ScenarioController`) opposite the human through the test-only `RiposteApp.compose_session` seam on a pinned seed; their human scripts were found by searching the solver, and each case asserts the outcome it needs as a fixture before judging presentation, so a tuning change that moves a scenario fails loudly. The canonical case plays a whole set against the real CPU: intro once, clean rounds, the set resolved by the solver, the winner shown once from authority, results locked until the cinematic ends, the replay verified, then a Rematch that is a fresh, introduced set and a clean exit. Exact rigid-body tumbles and pixels are never asserted; they are device QA.

E2E suites drive frames through `MatchScreen.advance_frame` / `ResultsScreen.advance_frame` (the same path `_process` uses) with `_process` disabled, pin seeds, and use a scratch settings file. Shared fixtures live in `game/tests/harness/` (`DuelFixture.of_type` is the one event filter; `AppDriver` boots and drives the shipped scene).

Balance tool (not a suite): `pnpm test:balance:audit` (or `godot --headless --path game --script res://tools/balance_report.gd`) prints CPU-vs-CPU matchups (wins, rounds, hits, parries, charge, round length) with the shipping rules over the fixed 40-seed tuning corpus, disjoint from the smoke and held-out corpora (`CpuLadder`); read-only. The pnpm command runs the ladder only; run the tool directly for the slow mirror-match tactics table. `tools/feel_report.gd` (40 CPU duels) reports what a clash does to the swords and bodies — speed kept, rebound, held-contact lifetime and migration, sword-on-torso SLIDE / STALL / REST. Every first impact is blade on blade since rules 50 (STEEL-TOPOLOGY-001), so its old per-feature breakdown is gone. `tools/swing_speed_report.gd` prints peak forte, centre-of-percussion and tip speeds at tap, half and full charge against a human reference. `tools/feel_probe.gd` is the combat feel probe: consequence density (clashes per hit, kills, passive parries, held-contact lifetimes, friction saturation, threat advantage after contact; and per swing against the hands, HAND wounds, near misses — closest blade-to-hand surface gap, sampled each tick, within 2 cm and no wound — and saves by steel — a guard or blade met first where the same free sweep, carried on at its own rates with nothing in the way, would have entered a hand; passive parries and saves per released attack; clean torso strikes — no protective steel since release, not a graze — per kill, terminal and crippling shares and damage, by closing speed and contact kind; and every 30+ tick hold classified by feature pair, point count, maintained or resting, driven or not, and body motion; every held tick read as BIND, SLIDE, TANGLE or resting — PLANAR-BIND-001 readings, never physics — with disengages counted and any friction without normal impulse flagged as a solver defect) over 16 paired, side-swapped scripted duels in about 3 minutes. `-- --mu0` replays the corpus frictionless — the counterfactual that says whether friction is what holds a contact — and `-- --punish` (about 11 minutes) forks the live duel at every PARRY and every whiff, at once and 10 ticks later, and measures who could physically land first: the parrying defender or the attacker, the whiffed-at fighter or the whiffer (DEFLECTION-CONSEQUENCE-001). `tools/reacquisition_probe.gd` is the lost-line probe: hand-built displaced Long Guards, cuts into a Long Guard (tap / half / full, on the line and 20 cm either side) and whiffs, printing both swords' θ, θ̇ and phase, both time-to-threat estimates and both fighters' forked punish times 0–20 ticks after the event. A punish (`StateFork.punish`, `game/tests/harness/state_fork.gd`) is real physics: the state deep-copied, that fighter alone trying an advancing cut, an angled advancing cut either side and a lunge while the other stands idle, the opponent's sword in the way if it is — the estimate ignores the opposing sword and counts hands, so in a bind it reads both fighters as a tick from a hit when neither can land anything. A corpus that forks proves its forks once per duel against a re-simulation from the commands, and that forking left the duel untouched. `tools/speed_ledger.gd` prints (or with `-- --write` rewrites) the [Combat Speed Ledger](./combat-speed-ledger.md); `RULES` fails when the page and the rules disagree. `tools/profile_report.gd` ranks where a CPU-vs-CPU tick spends its time (CPU, collision sweep, contact solves, the rest), timed from outside through the simulation's seams because the simulation reads no clock. `tools/perf_report.gd` plays Hard-vs-Hard Quick Play matches with the real presenter mounted and prints per-frame cost (mean / p50 / p99 / max) of the authoritative step (split by held blade contact), both CPUs, the presenter's push and render, and the whole frame; `-- --sim-only` drops the presenter to give the engine floor (see [performance](../architecture/PERFORMANCE.md#measured)).

Same-tick fixtures (a kill and a ring-out in one tick, ROUND and PRES-PRESENTER) assert their own preconditions — both events on one tick and the intended `lethal_fraction` / `support_lost_fraction` order — before the production reading, so a geometry change fails as "no longer kill-first", never as a mystery winner.

## Test design (TEST-TRUTH-001)

ARRANGE (assert the fixture) → PERTURB → ACT (production code) → ASSERT (independent expectation). Lint rejects tautologies, commented-out or skipped assertions, and `Engine.time_scale` changes. Do not add tests whose only job is to inflate coverage.

Oracles are written from the rules, never from the implementation. A test that re-derives its expectation by reimplementing the code under test will agree with that code's bugs. For physical behaviour prefer ordered comparisons (`quality_a > quality_b`) so the suite survives deliberate balance tuning; reserve exact assertions for known formulas, determinism, replay fixtures, and boundaries.

Scenarios reach their configurations through the simulation (SCENARIO-REACHABILITY-001). Placing two fighters body-to-body with a centred Long Guard between them skips the point contact that live play would have resolved first; a test built that way asks the solver to fix a state the game cannot reach. Place a penetrating start only when recovery from it is the subject, and say so in the test. Hand-placed fixtures are written in metres of a particular geometry: when the hilt track changes, move them by the measured reach change and re-check what each fixture asserts about itself, rather than loosening the assertions.

## When a red test may change

A failing assertion is not an instruction to edit the assertion. Decide in this order, and record the evidence beside the change:

1. What exact invariant or player-facing promise does this test protect?
2. Does that promise still apply under the accepted new law?
3. Is the test's initial state reachable through the production path?
4. What is the first divergence, and what caused it?
5. Is the observed behavior correct according to the intended game design?
6. Should the implementation, the fixture, or the expectation change — and what evidence supports that?

| Test type         | Change it when                                                                                                                     | Leave it when                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Numerical / unit  | The mathematical contract itself changed, and the new result is verified independently of the failing assertion.                   | A precise assertion failed and the cause is not yet known.                              |
| Physics invariant | The invariant was deliberately revised, and the new contract is documented.                                                        | The new motor exposed a real symmetry, contact, or state-transition defect.             |
| Combat scenario   | The old fixture depended on an incidental pose or trajectory that is no longer guaranteed, and the gameplay promise still holds.   | The scenario is a player-visible interaction the game is still supposed to support.     |
| Application E2E   | The user-facing behavior or the input contract intentionally changed.                                                              | A domain helper can force the outcome, but the real game journey still fails.           |
| Replay golden     | Authoritative state changed for a known, accepted reason, and the event stream and the first differing state fields are explained. | The hash differs and the only evidence is that aggregate combat counts stayed the same. |

A test must not pin a specific tick when exact timing is not the contract. Deterministic replay may pin a tick when timing itself matters. A gameplay journey should assert a bounded window and the causal sequence.

If the test's claim is stronger than its setup, correct the claim even when it is green. Headless `get_playback_position` is a supporting diagnostic, not proof that music kept mixing: Godot documents that playback position may be inaccurate because mixing does not necessarily run every processed frame. The no-restart contract is `loop_start_count()`. A unit or APP-E2E assertion on `loop_stream()`, playing state, start count, and that `menu_theme.mp3` is not playing on another player proves Godot's selected source. It does not prove the player heard the intended theme. The exact build used for a hearing belongs in the manual record.

Directly constructed state is appropriate for a domain law or a presentation policy. A combat journey feeds commands into the real simulation entry point. An application E2E runs the scene, the input adapter, and the match lifecycle, and does not call a domain helper to force the combat result. Do not manufacture a round by assigning velocity, forcing a hit, or writing scores when the contract is the player journey.

## Readability proofs (PRES-PRESENTER)

Readability claims are testable, and the ones that matter are _negative_. The presenter suite proves that the ribbon carries the projected `swing_potential` unaltered rather than a presentation-local guess, that the sweet region is a distinct surface and not a tint, that turning the accessibility cues off or up changes the drawing while leaving the band width and the carried reading untouched, that wind-back tension tightens and then lets go, that burst dust stays on the floor and drifts away from the heading, and that a whiff is never punctuated like a hit. Each one is a thing that would be easy to break silently and impossible to notice from a passing screenshot.

Two more guard the accessibility floor and the one diagnostic: with shake, motion, the ribbon, and the sweet rib all switched off, a body hit is still marked in the world, still heard, still felt in the pacing, and `SWEET_REGION_MIN` is still where it was; and the debug vectors draw nothing until asked, then follow the simulated swing direction when the blade reverses while the tip _speed_ stays a magnitude. TUTORIAL covers the lessons themselves: the sweet-spot drill passes on `blade_fraction` alone and refuses a hit near the hilt, at the very tip, or by the opponent, the momentum drill refuses two hits that felt the same, and the scripted partner winds up exactly once per period without moving, paces in and out without ever swinging, and stands down outside an active round.

## Property and fuzz proofs (FUZZ)

Scripted suites prove the cases someone thought of. FUZZ generates input a person might plausibly produce — jittery taps, held keys, rolled thumbs, attacks landing on top of footwork — and asserts laws that must hold for every stream: no burst without a deliberate gesture behind it, no burst from key repeat or a held direction, bursts never overlapping, the duel staying finite and separated inside the arena, neither lateral direction cheaper than the other, and bit-identical reproduction.

Its generator is weighted toward real gestures on purpose. Uniform random axes essentially never produce a double tap, so a fuzzer made of noise would exercise only the paths nobody worries about.

The graceful-handling matrix lives there too, and it is two claims, not one. **Input and external problems are absorbed** — clamped, ignored, or cancelled into a short recovery — because they arrive from outside the simulation and are not its fault. **Impossible authoritative state is not**: it means the simulation itself is wrong, so it fails closed as a no-contest rather than being quietly repaired.

## Production scope

Code affecting authoritative state, simulation outcome, win/loss, deterministic hashes, matchmaking, ELO, or shipping product behavior MUST be in covered scope.

## The test pyramid, and what each layer may claim

Each layer is only honest about its own row. A green suite below never licenses a claim from a row above it.

| Layer                | Proves                                                                        | May **not** claim                     |
| -------------------- | ----------------------------------------------------------------------------- | ------------------------------------- |
| Unit / property      | Math laws, totality, state invariants, symmetry, scaling                      | Game feel                             |
| Simulation scenarios | Tap, bind, parry, trade, contact lifecycles, CPU commands, a full match       | Browser or mobile integration         |
| Godot app E2E        | The real `main.tscn`: menus, match lifecycle, rematch, pause, touch mechanics | Browser rendering and input behaviour |
| Browser / device     | The Web export: boot, real input, canvas, safe area, sustained performance    | Balance, or legibility across humans  |

The bottom row is the one the automated gates cannot reach, and it is split by what is mechanical versus perceptual:

- **Mechanical** — hosting, boot, `/play` resolution, navigation, reload, focus loss. Automatable, and the intended home for a future Playwright gate. Not automated for MVP-0; run by hand from [device-qa.md](./device-qa.md).
- **Perceptual** — whether a parry reads clearly, whether a wind-back is legible at arm's length. Deliberately **never** automated. A test asserting "this reads clearly" would be asserting its own fixture.

## When each test runs (TEST-TIER-001, TEST-OWNERSHIP-001)

Run the tiny truth tests while implementing; save the broad ones for checkpoints. `game/tests/suite_manifest.json` gives every suite a size and a measured budget, and every production script an owning area, so the cheap loop is chosen by the code that changed rather than by worry.

| Size        | What it holds                                                             | When                                  | Command                                                                              |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------ |
| **fast**    | local laws: math, frame movement, commitment, friction rows, contact rows | continuously, seconds                 | `pnpm test:changed` (what the working tree touched), `pnpm test:focused fast`        |
| **focused** | an affected subsystem: contact, weapon, movement, CPU, presentation, app  | after a coherent slice, a few minutes | `pnpm test:focused contact` (areas or suite names: `pnpm test:focused MOVE REPLAY`)  |
| **gate**    | every correctness suite, plus replay goldens, fuzz and the E2E journeys   | once per feature-complete batch       | `pnpm test`                                                                          |
| **audit**   | CPU smoke, tuning and held-out ladders; contact ship corpus; frame cost   | release checkpoints, by hand          | `pnpm test:balance`, `:audit`, `:accept`; `pnpm test:contact:ship`; `pnpm test:perf` |

The selective commands skip Godot's asset import; run `pnpm game:import` (or pass `--import`) once per session, and again after adding assets or a `class_name` script. A changed test file selects only its own suite, a docs change selects nothing (`pnpm docs:check`), and a production file with no owning area fails the selection until the manifest names one.

The loop:

1. **Implementing.** Parse or lint, then `pnpm test:changed`. Never the full gate, a corpus, a balance tier or every E2E.
2. **Feature complete.** `pnpm test:focused <area>`; fix local failures; leave unrelated suites alone.
3. **Batch complete.** One `pnpm test`. If it is red: classify every red, reproduce each at the lowest useful layer, fix them all, rerun only the red suites (`pnpm test:focused <SUITE>…`), then one final `pnpm test`. Never a full rerun per fix.
4. **Release checkpoint.** The audits, `pnpm check`, then one human acceptance.

A rules version still names every gameplay change, but it is not a ceremony: goldens are re-pinned once per batch, after the replay diff is explained mechanism by mechanism. The exception is a refactor that must be hash-identical, where the goldens are the acceptance test for each step.

Each law has one owner (TEST-OWNERSHIP-001). A journey proves that real input reaches the interaction and the player sees the result; it never re-proves the Coulomb bound, the commitment curve or the contact slop. When a broad test finds a bug, the permanent regression goes down to the owning suite first. The FULL-E2E combat journeys are kept to the canonical few — the full set, spacing beats a tap, the bait whiff, the Long Guard poke and thrust, the slash terminal, ring-out, the fallen body, winner control into the next round, a clean charged cut is decisive, walking into the same tap delivers more than standing — and, since the steel became the blades and each guard's protected side (rules 52), a tap through the hands misses when it misses the torso (TORSO-CIRCLE-001), and a steel catch parries an attack of the production Hard CPU and the answer lands (true steel defense; in its trace the steel is blade on blade, and the crossguard's protected side stays the GRIP suite's witness, GUARD-PROTECTION-001). Bind → disengage → re-engage has no real-input journey and is OPEN (see the traceability matrix). Attack-geometry tests name sides by the cut, never by left or right (ATTACK-SIDE-001, `tests/harness/cut_geometry.gd`): origin side / end side, behind / into the blade, radial; each states whether its result came from the line, the measure or both. ATTACK owns the line witness (`test_the_side_of_the_sweep_decides_what_a_cut_meets`: inside reach, equal measure, mirrored — on blade-only steel behind the blade the grip is met first, into it the torso) and `test_the_threat_estimate_sees_the_steel_in_the_way`. At rules 49 an inside-reach search (1.3–1.75 m × tap / 12 / 24-tick charge × planted or pressing × origin / end side / no step × walk or dash × early to late timing, the attacker a Hard CPU once its cut ends) found no whiff inside reach and a step behind the blade making the defender the first to land in about half the exchanges; those outcomes came from crossguard and handle steel. On blade-only steel no tested scene shows the defender landing first: whether a line change can be capitalized on is LINE-CHANGE-CAPITALIZATION-001, OPEN, and no current test claims it. Outside reach, whiffs are measure, not line. CPU owns the capitalize decision laws (CPU-008) on held scenes: an opening is taken from the side held, a route into steel and a guarded opponent at rest are declined, and the decision mirrors exactly. FULL-E2E owns the real-input line traces: `test_an_origin_side_step_here_meets_the_cuts_crossguard_first` and `test_an_end_side_step_here_is_struck_on_the_torso` — what the line did in that one scene, never a rule about every step.

The line game is tested in four layers. **Laws** are exact (mirror, slot swap, determinism, feature chronology, the CPU's current self and delayed opponent, label independence). **Existence witnesses** pin one readable searched state and assert causes — inside reach, the same measure, origin side avoids the body, end side does not, the mirror agrees — never an incidental tick. **Relationship grids** (LINE-GAME) assert orderings over a small deterministic grid (behind the blade takes the torso out of the first contact more often than into it), never the current rates. **The corpus** is `game/tools/interaction_audit.gd` — read-only, never a gate: `-- line` (the line-change matrix), `-- agreement` (THREAT-AGREEMENT-AUDIT: the steel-aware route prediction against a fork of the same state rolled on, a confusion matrix of torso / grip / steel / none split by whether the swords started bound, with the dangerous predicted-clear-but-steel cases broken down by the opponent's phase and where on the blades they met) and `-- capitalize` (CPU-008 conversion, every seed in both slot orders). Tuning decisions come from the corpus, never from a unit test's numbers.

Two lessons from the rules-50 pass are standing rules. **Count simulation ticks, never frames:** hitstop holds the clock for presentation, so a frame-counted "held for six frames" can be a two-tick touch, and a gesture whose rest falls entirely inside a hitstop never reaches a tick. **A searched witness is re-derived, never re-searched until green:** when a witness breaks, first replay it from a clean launch and check the headless replay hash matches the app's, then find what moved — the fixture, the measurement or the physics — and only then decide whether the law still has a witness.

Probes for one-off discovery live outside the project (`godot --headless --path game --script <absolute path>` runs them with every game class available), so they are never imported, parsed by `scripts:check`, or left behind.

## Gates a person runs

Two gates are deliberately not automated, because what they check is a human reading a screen rather than a value in a state: the combat-feel and readability gate ([combat-feel-gate.md](./combat-feel-gate.md)), which blocks the mechanics freeze, and the real-device pass ([device-qa.md](./device-qa.md)). Both list what the suite already proves, so the hand pass is spent on the part only a hand can reach.

## Tuning against the test set

Where a test grades an emergent outcome rather than an authored value, the seeds it grades on are part of the contract. CPU difficulty keeps two disjoint corpora — calibration seeds to read while tuning, acceptance seeds that grade and are never inspected — and the one claim too small to resolve at an affordable sample size is measured by a tool instead of gated. See [docs/concepts/cpu.md](../concepts/cpu.md#how-difficulty-is-tested-and-what-the-tests-can-prove). Raising a sample until a gate passes re-creates exactly the overfitting the split prevents.

## What tests cannot prove

Legibility at arm's length and the behaviour of an actual hand on glass. Everything mechanical about touch — heading-relative steering, simultaneous thumbs on independent indices, all four burst gestures with their negatives, OS cancellation — is driven through the shipped `main.tscn` in APP-E2E, because a simulated `InputEventScreenTouch` is a real one as far as the game is concerned. The rest is a written procedure: [device QA](./device-qa.md).

## Completion journey matrix

Every journey the finished game must prove, with the layer that proves it and its current status. Three layers, never substituted for one another: **domain** (a law on a constructed state — it proves the law, not that play reaches it), **sim journey** (the production simulation stepped from recorded or scripted commands; a fixture may set the start, the outcome must come from production systems), and **app E2E** (the real scene and the production input path, `AppDriver` keys, axes and touch, into a real `MatchSession`; nothing forced). A test named in an earlier plan is not evidence; each row's evidence is the test that passes on the current tree. Status: PASS (evidence passes now), OPEN (no truthful witness yet, or it fails), NOT IN SCOPE.

### Weapon motor A/B (rules 53): the PD experiment, rejected

The shipped drive (`WeaponSystem._drive_motor`: `SimMath.approach` toward the phase's target speed, at most the phase's authored torque cap a tick, `α = τ / M_θ`; caps are N·m, every `WeaponDefinition.*_accel` is drive × torque / `M_θ` in rad/s²) against an implicit velocity-tracking PD (`ω' = (ω + dt·Kv·ω*) / (1 + dt·Kv)`, the implied α capped by the same cap), motor-only, same definitions, same `M_θ(θ)`, same starts. Pre-registered: keep PD only if it improves release-to-threat, redirect latency, settle time, overshoot or jitter by at least 10 % on some scene and regresses none by more than 5 %.
