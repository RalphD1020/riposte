# Invariants

> Source: architectural constraints

Normative contracts for the Riposte project. RFC 2119: MUST / MUST NOT / SHOULD / SHOULD NOT / MAY.

Conflict rule: **spec > code > docs**. Code that violates this file is defective unless this file has been explicitly superseded.

## Monorepo (MONO)

### MONO-001

Sibling packages. `@riposte/web` (`apps/web`) and `@riposte/game` (`game`) MUST be siblings under the root monorepo. Next.js MUST NOT own the Godot runtime. Godot MUST NOT be initialized under `apps/web`.

Next MAY **serve** the exported Web artifact staged at `apps/web/public/game/`, which is gitignored build output produced by `pnpm game:stage:web` from the canonical `dist/game/web/`. Serving bytes is not owning a runtime: Godot sources (`.gd`, `.tscn`, `.tres`, `project.godot`) MUST continue to live only under `game/`, and no Next source may import, build, or configure the engine.

### MONO-002

No-op ban. A package MUST NOT add a script that only echoes success to satisfy Turbo.

### MONO-003

Command-name abstraction. Root `dev` / `build` / `lint` / `typecheck` / `test` MUST invoke Turbo. Implementation technology MUST belong to each package.

## Web (WEB)

### WEB-001

Godot renderer. Riposte's canonical Godot renderer MUST be Compatibility.

Rationale: the browser is a first-class deployment target and Godot 4 Web exports use WebGL 2 through Compatibility. Forward+ and Mobile MUST NOT be used.

### WEB-002

Gameplay runtime language. Production Godot gameplay/runtime code MUST use typed GDScript.

C# MUST NOT enter the production game runtime without an architecture decision. Godot 4 C# cannot export to Web.

### WEB-003

Web threading. Riposte uses Godot's single-threaded Web export (Compatibility / WebGL 2.0). The committed Web preset MUST enable both `vram_texture_compression/for_desktop` and `vram_texture_compression/for_mobile`.

### WEB-004

Export hosting. `dist/game/web/` is the canonical Godot Web export and the itch.io upload; itch.io MUST NOT receive the Next.js app. The same artifact MAY be **copied** (never moved or symlinked) into `apps/web/public/game/` by `pnpm game:stage:web`, which MUST fail closed when the export is absent or missing any of `index.html`, `index.js`, `index.wasm`, `index.pck`.

`/game/:path*` MUST receive a path-scoped Content-Security-Policy granting `script-src 'wasm-unsafe-eval'` and `worker-src 'self' blob:`; those capabilities MUST NOT be added to the site-wide policy. `'unsafe-eval'` MUST NOT appear in either. The export MUST stay single-threaded (`variant/thread_support=false`), so COOP/COEP MUST NOT be required. `/game/index.html` MUST be served `no-cache`.

### WEB-005

Play admission. Every Play CTA MUST navigate to `/play`; only `resolvePlaySurface` decides the destination, and it MUST prefer, in order: the export staged on this origin (`/game/index.html`), `NEXT_PUBLIC_PLAY_URL` (the itch page), `NEXT_PUBLIC_LOCAL_PLAY_URL` (default `http://127.0.0.1:8060/`), then the `/play` explanation.

Admission MUST NOT depend on the visitor's hostname. Server builds MAY redirect `/play` to the staged shell, but only when the artifact is present, and MUST NOT rewrite it: the shell resolves its engine files relative to its own URL and needs the `/game` policy; static exports perform the same hop in `PlayGateway`. Components MUST NOT branch on hosts or on itch, and itch MUST be presented as a secondary destination rather than the primary Play target.

### WEB-006

Purpose-named destinations. Community (shown as Discord) and support (shown as Patreon) are configured by `NEXT_PUBLIC_COMMUNITY_URL` / `NEXT_PUBLIC_SUPPORT_URL` on the web and `CommunityLinks.COMMUNITY` / `SUPPORT` in the game. An unconfigured destination MUST render an announced "Coming soon" stub. URLs MUST NOT be invented or hardcoded elsewhere. Environment destinations MUST be validated: public URLs https only; local play may also use loopback http or a same-origin path; anything else is unconfigured.

## Simulation (SIM)

### SIM-001

Authoritative duel. Only `DuelSimulation.step(state, command_0, command_1)` advances authoritative state: exactly one `PlayerCommand` per fighter per 60 Hz tick (`SimulationTimebase`). The simulation MUST NOT read render delta, wall-clock time, input devices, Godot physics, scene nodes, or which source sent a command. `src/domain` and `content/rules` MUST NOT depend on application or presentation (SIM-PURITY lint). Same **build**, same `DuelRules`, same seed, same commands MUST reproduce the same duel, bit for bit, including the state hash. The guarantee is deliberately scoped to one build rather than to "every platform": every arithmetic operation in `src/domain` goes through `SimMath`, but the double-precision result of a transcendental function is the engine's and the C library's, and promising cross-platform identity would be promising something no gate can check. What is checked is replay verification against the recorded commands (SIM-002), which is the strongest claim the gates can actually hold. Modes are configuration (rules + controllers), never separate simulations.

### SIM-002

Determinism proof. `StateHasher` MUST hash every authoritative field from exact IEEE-754 bits in a fixed order (SHA-256); presentation values MUST NOT enter the hash. `ReplayRecord` stores rules id + version, seed, and every tick's commands. `ReplayVerifier` re-simulates and MUST reject a rules mismatch, invalid rules, or a final-hash mismatch. Changing any rules value MUST bump `DuelRules.version`.

### SIM-MATH-001

Deterministic math. Simulation code MUST use `SimMath` (only + − × ÷ sqrt, each a separate operation) instead of engine trig / pow / lerp helpers (platform libm, FMA contraction), and scalar float fields instead of float32 engine vectors (`Vector2`, `Vector3`, …). `exp(−t)` for `t ≥ 0` is `SimMath.exp_minus`: range reduction by ln 2 and the alternating series of the remainder.

### SIM-RNG-001

Randomness. Duel physics uses no randomness. Decision makers (the CPU) MUST draw from `SeededRng`, the only domain wrapper of `RandomNumberGenerator`, seeded from the match seed. Global `randf()` / `randomize()` MUST NOT appear anywhere under `game/src/`.

### MOVE-001

Frame-relative footwork. `PlayerCommand` movement is intent in the fighter's **combat frame** (MOVEMENT-FRAME-001): `+y` drives down the CombatHeading φ, `−y` backs off it, `±x` steps to its right and left. Every controller — human, CPU, replay, network — MUST emit the same frame-relative language; `PlayerCommand` gains no fields. The frame used is recorded as `duel_forward` in authoritative state and MUST be a unit vector (hashed, reset per round, invariant-checked). The stride's share of top speed (`MovementSystem.stride_multiplier`) reads only the intent's direction in that frame. Improved facing recovery while retreating MUST come from orbit geometry alone; no movement state may modify `turn_speed_max`. No tick may end with body centers interpenetrated, and `buffer_ticks` MUST NOT exceed `WeaponDefinition.BUFFER_TICKS_LIMIT`.

### MOVEMENT-FRAME-001

Movement input is expressed in CombatHeading space (rules 47 onward). The simulation MUST rotate footwork intent through each fighter's heading φ as it stood at the start of the tick, read for both fighters before any heading turns, so update order never decides which way a body was asked to go. The TargetBearing τ (toward the opponent) MAY influence movement only indirectly, by driving the bounded heading motor (`FacingSystem`); it MUST NOT enter the footwork frame, and footwork MUST NOT home on the opponent by itself. τ is otherwise read only by the heading motor, CPU observation, threat geometry and the presentation glance. There is no root-steering penalty and no running, forward or dash bonus: walking down φ costs and earns exactly the stride it always did, and an identical physical state meets identical contact whatever input history produced it. Consequence: a committed fighter whose heading lags a target that has moved off-line keeps driving down its own line — the positional window a well-read commitment concedes. Implementation: `game/src/domain/combat/movement_system.gd` (`step_in_frame`, `stride_multiplier`), `game/src/domain/match/duel_simulation.gd`. Tests: `MOVE` (`test_forward_follows_the_heading_wherever_the_opponent_stands` MOVE-FRAME-001, `test_forward_follows_the_heading_as_it_catches_the_bearing` MOVE-FRAME-002, `test_frame_movement_mirrors_exactly` MOVE-FRAME-003), `MOTION-COMMIT` (`test_a_committed_advance_runs_down_its_heading_not_onto_the_target` COMMIT-CHASE-001, `test_moving_with_the_strike_adds_exactly_its_own_velocity` POINT-VELOCITY-001, `test_a_dash_shoves_no_harder_than_a_walk_at_the_same_speed` NO-RUNNING-BONUS-001, `test_two_identical_fighters_pressing_keep_their_midpoint` EQUAL-PRESS-001).

### MOVE-002

Burst footwork. A double tap in one duel direction launches a short burst of footwork, and it MUST be derived from the command stream alone — `PlayerCommand` gains no fields, so human, CPU, replay, and server re-simulation reach the identical burst and no client can claim a gesture. `DirectionalTapRecognizer` reads cardinal sectors with hysteresis (`burst_enter_deflection` to enter, `burst_neutral_deflection` to leave); only rising edges out of neutral count, so held input and key repeat MUST NOT register, and a deflection held past `tap_window_ticks` MUST cancel the pending tap. `MovementGestureState` lives in authoritative `FighterState` — hashed, reset per round and on death, invariant-checked. The heading is frozen in world space at activation and MUST NOT bend mid-burst; mode, kind, and remaining ticks MUST agree, and the heading MUST be a unit vector while bursting. A burst is bounded acceleration toward a bounded peak speed with normal body and arena collision; it MUST NOT phase, teleport, grant invulnerability, or restore facing. Commitment scales burst acceleration exactly as it scales ordinary footwork (PHYS-003), so a dash is never an escape from a swing already paid for. Spam control MUST stay physical — a required return to neutral plus burst duration — with no stamina and no cooldown. Forward dash is fully committed ballistic motion: velocity IS burst direction × speed (not additive), with zero steering and zero facing authority during the drive phase. Lateral/back bursts remain additive. Forward dash terminates immediately on body impact, entering a progressive RECOVERY phase where steering/facing authority ramps from 0→1 over `dash_recovery_ticks`. No new burst may be launched during recovery. `MovementGestureState.Mode` tracks `NORMAL`, `BURST`, and `RECOVERY`.

### CMD-001

Command contract. `PlayerCommand` is the only input between a controller and the simulation (human, CPU, replay, future network). Movement is quantized to integer milli-units. Attack fields are edges within the tick window: pressed, released, canceled. Commands are untrusted; the simulation consumes `sanitized()` values. A cancel drops a charge without attacking (focus loss, touch cancel, pause).

### HITSTOP-001

Hitstop is wall-clock only. `FixedTickDriver.hold(seconds)` pauses tick consumption while impact feedback plays and MUST NOT change any tick-indexed result; headless runs and replays ignore it. A frame runs at most `MAX_CATCH_UP_TICKS`. Resuming from pause or a backgrounded tab MUST drop the backlog (`clear_backlog()`), never fast-forward.

## Combat (COMBAT)

### COMBAT-001

One-button language. A tap (release before `tap_threshold_ticks`) is exactly 0% charge and a 90° cut **from wherever the blade actually is** — never a move to the opposite canonical guard. Holding past the threshold winds the blade physically away from the swing; release launches from the actual retracted angle with arc `min_arc + earned wind-back`. The sword persists where it stops. Commitment `K ∈ [0, 1]` reduces control authority; recovery follows from what actually happened (whiff, hit, deflection, bind) through RECOVERY-001.

### ATTACK-ARC-001

The control domain is not the attack. θ ∈ `[−guard_limit, +guard_limit]` (±135°, **270°**) is where the sword can turn (SLASH-SHAPE-001); one attack travels `arc(charge) = min_arc + (max_arc − min_arc) × charge` from where it was released — 90° for a tap, at most `max_arc` (**180°**) for a full charge, clamped to the domain: a full right attack runs −135° → +45°, a full left one +135° → −45°, exact mirrors. Past its commanded end the blade sweeps on into its overswing until its own brake stops it (RECOVERY-001) — physical, sized by `ω²/2α`, still dangerous, never authored — so the swept travel is the arc plus that overswing, inside the domain. No attack sweeps the 270° domain, and an analysis, estimate or doc that treats the domain span as an attack's travel is wrong. The two full attacks together cover the domain. Implementation: `game/src/domain/rules/weapon_definition.gd` (`arc`), `game/src/domain/combat/weapon_system.gd` (`_launch`). Tests: `RULES` (`test_the_control_domain_is_not_the_attack_arc`), `SHAPE` (full charges from either side are exact mirrors).

### RECOVERY-001

Physical recovery (rules 44 onward). Recovery MUST end exactly when **both** hold: the universal floor `CombatTuning.recovery_min_ticks` (6 ticks, 100 ms — hand and control re-acquisition, mirrored, the same for every attack and weapon) has passed, **and** the blade is physically back under control, `|θ̇| ≤ WeaponDefinition.control_speed`. There is no other duration term: no commitment, overswing, displacement, facing-error or balance ticks and no recovery cap, because overswing, facing error and stability already cost real time through the brake torque, the turn torque and movement authority — counting them again would be a hidden whiff penalty. While the blade is above `control_speed` in recovery it is actively arrested by the attack's own **brake** torque (the swing's charge, condition-scaled, CONDITION-001), never the weak hold torque; only once it is under control does the guard return carry it to the committed guard (GUARD-RETURN-001). So a tap (little momentum, a strong brake) clears the gate quickly and a full whiff (overswinging on a weak brake) takes longer, with no authored difference. Ending the phase does not by itself restore full turn authority: a blade still inside `control_speed` but not yet stopped still owes that redirect debt (DIRECTIONAL-COMMIT-001). The debt is gone when the speed is, not after an extra settle timer. A finished overswing, a contact that arrested the cut (RIGID-CONTACT-002), a dropped charge (the wound blade braked at the charge it carried) and a lost hold all enter the same gate. Commitment through recovery is `recovery_commitment × max(floor_left / floor, clamp01(|θ̇| / swing_speed_full))` — continuous into and out of recovery, mirrored, and gone at the gate. Time-to-threat reads the same rule (THREAT-001). Implementation: `game/src/domain/combat/weapon_system.gd`, `commitment_model.gd`, `initiative_model.gd`. Tests: `ATTACK` (no recovery term reads overswing, facing, displacement or stability; a tap recovers sooner than a full whiff; recovery never ends above `control_speed`; the floor always holds; mirrored).

### COMBAT-004

Charge is earned displacement, never elapsed time. Charge MUST equal the outward travel a hold actually generated, measured past `max(guard_angle, |hold_start_angle|)` and expressed as a fraction of `windback_span()`. Therefore: restoring an under-prepared blade to the canonical guard earns nothing; a blade a collision flung outward earns nothing for being there; a blade that cannot travel (at the guard limit, or pinned in a bind) earns nothing however long it is held; and no single tick may credit more wind-back than the motor could have produced. `WeaponDefinition` MUST NOT expose a charge duration.

### COMBAT-005

Committed side and readiness. The blade's side is remembered state (`stable_side ∈ {+1, -1}`), updated only once `|angle| > side_deadzone`, so numerical noise near 0° cannot flip the next swing's direction; `swing_direction = -stable_side`. Preparation is the continuous `clamp(|angle| / guard_angle, 0, 1)`, captured once at release as `launch_preparation` and never recomputed in flight. Preparation gates achievable angular velocity only; it MUST NOT be a damage multiplier, and it is not readiness — how soon a blade can threaten is time-to-threat from the whole state (THREAT-READINESS-001). ±`guard_angle` on the committed side are the resting targets of the guard return (GUARD-RETURN-001, rules 54); angles MUST NOT be snapped toward them. `GuardRegion` is diagnostic classification for HUD, telemetry, and debug only: `src/domain/combat` and `src/domain/match` MUST NOT branch on it (lint-enforced). Physics drives classification, never the reverse.

### GUARD-RETURN-001

Guard return (rules 54 onward). In `NEUTRAL`, and in `RECOVERY` once `|θ̇| ≤ control_speed`, the weapon motor is a critically damped pose tracker toward `stable_side × guard_angle`. The hinge error is `e = θ* − θ`: the guard interval is convex, so the error is not wrapped through the stop. With `ω* = 0`, `Kp = ωn²` and `Kd = 2·ωn` (`ωn = CombatTuning.guard_return_natural_frequency`): `ω' = (ω + dt·Kp·e) / (1 + dt·Kd + dt²·Kp)`. The implied `α = (ω' − ω) / dt` is capped at the hold acceleration, then multiplied by the return scale. The return is suspended in `CHARGING`, every swinging phase, `OVERSWING`, `STAGGER` and `DEAD`. An attack held this tick takes the tick: the neutral hold kills speed and does not fight the command. While blade contact is in any phase but `SEPARATED`, the return acceleration is multiplied by `guard_steel_return_scale`, and always by that fighter's impact authority (IMPACT-AUTHORITY-001). The neutral hold and the return carry the damage term of force only, never the fatigue term (STAMINA-004). `InitiativeModel` integrates this same coast. It starts from the persisted impact authority and, on each predicted tick that continues, recovers that local scale the way the duel does (IMPACT-AUTHORITY-001). Angles are never snapped.

### IMPACT-AUTHORITY-001

Impact authority (rules 57 onward, layout 9). Each fighter carries `impact_authority` ∈ [`impact_authority_floor`, 1], hashed, projected, and set to 1 at every round reset. It multiplies the guard-return scale and nothing else: not damage, not stamina, not swing or brake torque, not footwork, not turn torque, not `push_radius`. A new steel episode — the blade manifold's first sword contact, the one `observe` admits only from `SEPARATED`, and only when that solve's normal impulse is positive — dips each sword once from that contact's own solved change in angular velocity (`SwordContactSolver` deltas on that solve, not the motor, not a later hold, not another constraint row). The update is `share = |Δθ̇| / (|Δθ̇| + ω_full)` and `authority' = max(floor, authority · (1 − share))`. That ratio is the generalized angular impulse `|J_θ| / (|J_θ| + I·ω_full)` with `J_θ = I·Δθ̇`; the inertia cancels, and a shared normal magnitude is not a per-side measure. A zero angular change does not dip. Manifold points of that one solve are one dip, not one per point. Later re-holds of the same episode are not further dips. A torso entry, a grip, or a hand is not an episode. A genuine return to `SEPARATED` followed by a new steel contact may dip again. On every other living tick the deficit fades at the guard return's natural frequency, `da/dt = ωn·(1 − a)`, integrated as `authority' = authority + (1 − authority)·(1 − exp(−ωn·dt))`, toward 1 and never past it. The floor binds a dip; it is not a rest state. A tick that dipped does not also recover. That recovery is its own step after contact lifecycle and before the stamina settle, which is why `TICK_ORDER_VERSION` is 16. Rules 56 kept version 15: the dip stayed inside the contact step and authority did not recover until the round reset. A dead fighter does not recover. No second solver, scripted parry impulse, bind winner, or release timer. `InitiativeModel` coasts with the start-of-tick value and recovers the same local scale on each predicted tick that continues. Implementation: `game/src/domain/combat/impact_authority.gd`, `contact_resolver.gd`, `duel_simulation.gd`. Tests: `AUTHORITY`.

### GUARD-LIMIT-SOFT-001

Soft guard limit (rules 54 onward). Inside a zone of width `guard_limit_zone` before `±guard_limit`, the acceleration `α = −(k·s + c·max(ω_out, 0))` resists outward motion only. `s` is the C¹ Hermite ramp of the penetration (`s(0) = s'(0) = 0`, `s(1) = 1`). `k` is `guard_limit_stiffness` times this tick's wind-up acceleration, so a sustained wind-up still reaches the stop on every sword; `c` is `guard_limit_damping`. `α` is capped at the weapon's strongest brake acceleration. Inward speed is not damped. `settle_at_stop` and the solver's stop row remain the hard fallback. Arrival includes a shortfall of `WeaponSystem.STOP_ARRIVAL_RAD` (1e-9 rad, inclusive): outward speed is removed when `turned >= limit - STOP_ARRIVAL_RAD`, and on the negative mirror when `turned <= -limit + STOP_ARRIVAL_RAD`. The mirror of `θ + ω·dt` can land one ulp short of the limit the other side reached, and that rounding must not keep outward speed. A larger gap is not the stop. Inward speed (`speed` toward the centre, including a blade already on the limit with none) is never removed. The angle clamp is unchanged, so a shortfall inside the band does not snap the blade onto the limit. Removing that speed is a state transition: the next tick's motor torque is `I·(ω' − ω) / dt`, and a later contact can diverge. It is not a tolerance chosen to preserve a replay hash. One predicate, `_outward_at_stop`, decides the stop. `assign_stop` writes a `WeaponState`: the weapon step and the post-contact carry. `write_limited` writes a caller-owned buffer and is what `InitiativeModel` uses after copying angle and speed into locals; that estimate MUST NOT write the fighter. A fallback that removes outward speed greater than one tick of wind-up acceleration, or finds the blade already past the limit, increments `ContactDiagnostics.guard_hard_stop_hits`. That counter is never hashed. The resting wind-up's own push into a stop it already occupies is not the fallback. `|angle| ≤ guard_limit` remains the state invariant.

### COMBAT-006

Totality and fail-closed. `StateInvariants.check(state, rules)` MUST run at the end of every authoritative tick. Problems originating outside the simulation (input, focus loss, impossible commands) MUST recover in-band — `ATTACK_CANCELED`, a clamp, or an idempotent ignore. A non-finite or structurally impossible _authoritative_ state MUST emit `SIMULATION_FAULT` and end the match as `REASON_NO_CONTEST` without repairing the evidence. "Impossible" means beyond what the physics can produce, never beyond what a player can command: the motor's actuated limit (`swing_speed_full`) is not a corruption bound, because a contact can legally knock a blade far faster; the weapon-speed bound is `SimulationGuardrails.physical_weapon_speed_bound` — the motor's full swing plus the largest kick one held-sword contact can give, from the sword's centroidal inertia, the weakest coupling, the wielders' masses and the fastest contact closing — with safety headroom. Nothing clamps a legal fast blade; the motor recovers it (FUZZ). `DuelSimulation.TICK_ORDER_VERSION` pins the canonical tick order documented in `docs/concepts/simulation.md` and MUST be bumped deliberately when that order changes.

## Combat physics (PHYS)

> These four laws exist to stop plausible-sounding but false shortcuts: that moving forward is a damage buff, that standing still is maximum force, that body mass is automatically strike mass, or that a vulnerable target makes a sword heavier.

### PHYS-001

Relational contact. All contact severity MUST derive from contact-time _relative_ velocity along the contact normal. Blade-point velocity is `v_fighter + ω_body × r_pivot + ω_weapon × r_blade`; closing speed is that velocity minus the target's, projected on the normal. Target motion therefore participates in every collision: the same swing MUST produce a larger closing speed against an advancing target than a stationary one, and a smaller one against a retreating target. No movement state may carry a direct damage bonus or penalty.

### PHYS-002

Mass, inertia, and effort are different questions. A body's translational mass in every contact is the fighter's real mass. A held sword's passive inertia is `M_θ,held = M_θ,sword + M_θ,grip/arms`: the sword's generalized inertia plus the hands riding the grip. Plant, commitment, and structural coupling MUST NOT scale either. Coupling remains a derived reading of plant quality and movement coherence — not identical to commitment, and not a mass. A planted or committed fighter is harder to overcome only through root actuator force, weapon motor torque, and turn authority. `FighterDefinition.hand_mass` is an authored reflected-grip approximation for the current roster, not a universal anatomical constant.

### PHYS-003

Momentum integrity. Attack commitment reduces _control authority_, not existing momentum. Implementations MUST scale desired acceleration and corrective torque (`A_move`, `A_turn`), and MUST NOT scale `velocity` or `angular_velocity` directly. Facing correction MUST resolve as `α = τ/I` against existing angular velocity, so reversal costs time rather than snapping. No attack phase may instantaneously erase velocity except through a resolved force or constraint. Collision-induced velocity changes (from body-body contact, arena boundaries, or weapon-body pushback) persist as the initial condition for the next tick's motor step. The movement motor accelerates _toward_ player intent; it does not _set_ velocity. A body-collision push at tick T is still partially present at tick T+1 because the motor's per-tick acceleration budget cannot fully counteract it.

### DIRECTIONAL-COMMIT-001

Commitment is physical redirect debt (rules 46 onward): how much present momentum, and actuator effort still being committed, must be overcome before the fighter can redirect the action. It MUST be continuous readings of the state every tick (`CommitmentModel`), never state of its own, never selected from a phase, an animation, a whiff label or a named move, and never a threshold. **Weapon:** `t_w = (|M_θ(θ)·θ̇| + max(dir·τ_motor, 0)·T_look) / τ_brake`, `C_w = t_w / (t_w + T_w)` — the coordinate's one inertia (UNIFIED-MASS-001), `τ_motor` the torque the weapon motor actually applied (`WeaponState.motor_torque`), `dir` the drive asked for (the swing's direction while driven, its wind-back while charging). **Root:** `t_r = (m·v_f + F_f·T_look) / F_brake`, `C_r = sign(t_r)·|t_r| / (|t_r| + T_root)` — `v_f` and `F_f = m·a_f` the body's velocity and footwork force along its combat heading; toward +1 strongly forward, 0 planted or lateral, toward −1 strongly retreating. **Facing:** `C_φ = clamp(1 − (1 − C_w)(1 − k·max(C_r, 0)) − relief·max(−C_r, 0), 0, 1)`. The saturating map `t / (t + T)` is 0 at no debt, ½ at the reference and approaches 1 without an edge, so a little more momentum always means a little more commitment. The brakes in the debt are the fighter's **healthy** ones: commitment describes the action, never the wound (CONDITION-001). The heading motor's final turn-torque share is `max(lerp(1, commit_turn_torque_curve, C_φ) · force_scale, commit_turn_torque_floor)` and its final turn-rate share `max(lerp(1, commit_turn_speed_curve, C_φ) · tracking_scale, commit_turn_speed_floor)` of healthy — injury applied once, floors applied last. Constraints sit outside the floors: a corpse cannot turn, a staggered body turns at its stagger tracking, and a committed forward dash keeps zero turn authority through its drive (MOVE-002). Turning never exceeds healthy neutral. Commitment MUST NOT reduce footwork force or steering (mass, bounded force and velocity already make a change of direction cost time); a modest root-steering share MAY be added only if real-input play shows it is needed. There MUST be no authored overswing, whiff, active-phase or counter-rotation term and no reset on contact: a parry that takes the blade's momentum takes its commitment with it on that tick. Calibration (content, `CombatTuning.commit_*`): lookahead 0.10 s, weapon reference 0.30 s, root reference 0.35 s, root facing weight 0.30, retreat relief 0.25, turn-torque curve 0.35 / floor 0.25, turn-speed curve 0.50 / floor 0.40 — started soft so control is never felt as taken. Implementation: `game/src/domain/combat/commitment_model.gd`, `facing_system.gd`, `initiative_model.gd`. Tests: `MOTION-COMMIT` (WEAPON-COMMIT-001, DRIVE-COMMIT-001, FORWARD-COMMIT-001, RETREAT-RELIEF-001, LATERAL-001, COMBINED-001, PLANTED-POWER-001, MOTION-ENERGY-001, NO-BONUS-001, EQUAL-PRESS-001, SYMMETRIC-PRESS-001, CONTACT-RELEASE-001, MIRROR-001, AUTHORITY-001, continuity through the reference, forward and back opposite around neutral, injury never changes the commitment), `COMMIT`, `FACE`.

### RESPONSIVE-COMMITMENT-001

Player input is accepted immediately; commitment never removes control. Every turn, movement, retreat, attack and release command enters the simulation on its tick, and commitment only limits the physical rate at which the fighter can redirect present body and weapon motion: a fully committed fighter asked to turn begins turning on that tick and keeps at least the turn floors. Commitment MUST NOT delay, buffer, discard or reorder input, disable movement, lengthen recovery, change damage, create a whiff stun, apply a counter bonus or lock facing. Discrete attack edges that arrive just before the weapon becomes controllable are kept by the attack buffer (`WeaponDefinition.buffer_ticks`, 4 ticks ≈ 67 ms, at most `BUFFER_TICKS_LIMIT`), so an early press or release executes on the first legal tick instead of being lost; continuous steering is never buffered, and the buffer never bypasses physical recovery. The simulation stays at its fixed 60 Hz; interpolation is presentation only and never touches collision or command timing. Commitment is readable without labels: stance, head and weapon window face `φ` (PRES-HEADING-001), so `τ − φ` is the tell. The same physical state always gives the same authority and the same contact. Implementation: `game/src/domain/combat/commitment_model.gd`, `weapon_system.gd`, `game/src/application/clock/fixed_tick_driver.gd`. Tests: `MOTION-COMMIT`, `ATTACK` (buffered press), `APP-E2E`.

### COMMITMENT-001

The simulation does not author commitment from attack states. Commitment is derived from the fighter's current generalized weapon momentum, root directional momentum, currently applied actuator effort and available braking authority (DIRECTIONAL-COMMIT-001). Forward motion increases directional commitment and contributes physical closing velocity to attacks; backward motion reduces forward commitment and reduces closing velocity while restoring tracking toward neutral; lateral movement changes the line without an additional authored penalty. Root movement and weapon movement are never separate damage systems: every sword contact uses the one authoritative point velocity (root translation + heading rotation + weapon θ + the hilt track's `C′(θ)`, PHYS-007) and the one effective-mass solve (IMPACT-PHYSICS-001), so an advancing strike closes faster than a planted one by exactly the body's velocity along it, and no movement-state multiplier may exist. Pushes are mass, velocity, actuator force, contact normal, friction and constraint impulse alone — no dash push. Whiff, exposure, parry and counter are descriptions of the resulting interaction and never select a different physical response (WHIFF-001, PARRY-001). Lint `COMMITMENT-001` refuses the usual names of authored shortcuts (dash push, plant/backpedal bonus, whiff penalty or stun, counter window or damage, angle advantage, parry commitment reset, running-attack bonus) in the domain, application and content.

### FRICTION-ORDER-001

Storage and update order decide nothing physical (rules 46 onward). (1) Every friction pass — the first-impact solve (`SwordContactSolver.solve_points`) and the held velocity solve (`RigidContactSolver`) — MUST choose all rows' tangent steps from the same velocities and apply them together, at one relaxation `ω = 1 / max_i Σ_j |T_ij| / √(T_ii·T_jj)` over the friction rows' tangent couplings (a Gershgorin bound, so each simultaneous projected step only removes kinetic energy); one row is exactly the one-row step. (2) The two ends of a near-parallel overlap MUST be built from the endpoint that bounds each end, on its own feature, with its closest point on the other — the same physical points whichever sword is `a`. (3) Footwork MUST take each fighter's combat frame from its own heading at the start of the tick, before any heading turns (MOVEMENT-FRAME-001). Consequences proved: two identical fighters pressing through their swords from the crossed resting overlap stay each other's exact reflection, and a Light-against-Heavy press is the exact reflection of its slot-swapped twin on every tick. Implementation: `game/src/domain/combat/rigid_contact_solver.gd`, `sword_contact_solver.gd`, `sword_contact_geometry.gd`, `movement_system.gd`, `game/src/domain/match/duel_simulation.gd`. Tests: `TWO-POINT` (`test_a_line_contacts_point_order_changes_nothing_physical`), `MOTION-COMMIT` (`test_two_identical_fighters_pressing_through_their_swords_stay_mirrored`), `GENERIC` (`test_a_heterogeneous_press_is_slot_independent`).

### PHYS-004

Exposure separation. Exposure is a **reading**, not a factor (rules 36): how far behind the opponent a fighter is in time-to-threat (`ExposureModel.reading`, `margin = T_threat(target) − T_threat(attacker)`, even initiative reads 0.5), computed from state immediately _before_ contact so a hit cannot amplify itself. It feeds the CPU, telemetry, the HUD and presentation; it MUST NOT scale contact impulse, damage, stagger pressure or criticals, and MUST NOT fabricate incoming kinetic energy, impulse, or relative momentum. A fighter who whiffs is punished because the opponent can physically hit first, never because a hidden number makes their flesh softer. Displacement, blade deflection, and camera impulse MUST be driven by impulse; injury and lethality by severity. A single scalar MUST NOT drive both.

### THREAT-001

Immediate threat is the actual swept blade (rules 43 onward). Time-to-threat (`InitiativeModel.threat_time`) MUST be one bounded estimate: for a fixed horizon (`HORIZON_TICKS = 30`, half a second, fixed iterations) it advances the attacker under the same bounded laws the duel uses — the weapon motor's torque over the coordinate's one inertia (UNIFIED-MASS-001) toward its target speed once the weapon is back under control (the RECOVERY-001 gate), the heading's turn torque under the authority commitment leaves, footwork closing at the locomotion force — each scaled by the attacker's own condition (CONDITION-001), carries the target along its current velocity, and samples the actual blade capsule against the target's hurt circle (SLASH-SHAPE-001, TORSO-CIRCLE-001) — the earliest flesh contact is the threat. An earlier steel crossing still wins. A weapon that is not yet ready is not frozen: its resting blade moves with the predicted footwork under the same arresting motor, so a resting guard walked into a torso threatens exactly as it would poke. The first overlap is the threat time. Past the horizon there is no time to give: the result is a `ThreatEstimate` tagged out of the horizon, whose time reads the horizon itself, carrying only what was still left — the blade's surface gap to the torso and the readiness still owed — which a consumer may use to rank two out-of-horizon options and MUST NOT turn back into seconds (rules 45 onward). Every quantity is the attacker's or the target's own (COMBATANT-GENERIC-001). It is the **unopposed** physical threat time: it MUST NOT predict the opponent's sword or guard (a sword in the way makes an attack defendable, not unreachable — the contact solver decides when the contact happens; whether an attack can actually land through a defence is measured by forking real physics, `StateFork`, never by the estimate), MUST NOT become a second contact solver, and MUST NOT contain an injury branch. There is one predictor: exposure (PHYS-004), the riposte advantage a parry carries (PARRY-001 — a reading, never what makes it a parry), the CPU, the HUD and the debug overlay are readings of it, and damage never reads it. The 270° range is potential coverage only. Implementation: `game/src/domain/combat/initiative_model.gd`, `threat_estimate.gd`. Tests: `DAMAGE` (outside the actual sweep reads unthreatened inside the sector; a sidestep raises the attacker's threat time; recovery delays the threat; past the horizon the time is the horizon and only the residual ranks; mirrored; an injured attacker is slower with no injury branch; bounded), `GENERIC` (reach is the attacker's weapon against the target's torso).

### THREAT-READINESS-001

Readiness is time-to-threat, never position (review 11). Four readings MUST stay distinct and none may stand in for another: **commitment** — how hard present motion is to redirect (DIRECTIONAL-COMMIT-001); **readiness** — how soon this physical state can threaten this opponent, the `InitiativeModel` estimate from θ, θ̇, φ, φ̇, X, V and the bounded actuators (THREAT-001); **preparation** — `|θ| / guard_angle`, the launch-speed authority of where the blade sits at release (COMBAT-005), a law of the swing, not of readiness; **advantage** — one fighter's time-to-threat minus the other's, a measurement. No code, doc or metric may read `|θ|` (or any position alone) as readiness: the same θ moving toward the threat and moving away from it are different readiness, and a sword moving away MUST physically arrest and reverse under its own motor before it threatens. The estimate follows the side the simulation would commit to (`stable_side` updated past `side_deadzone`, COMBAT-005) as the predicted blade moves, so a blade carried across the centre is predicted to cut the way the duel would launch it. Implementation: `game/src/domain/combat/initiative_model.gd`, `game/src/domain/rules/weapon_definition.gd` (`preparation`). Tests: `DAMAGE` (`test_a_blade_turning_away_threatens_later_than_one_turning_back` — REVERSAL-DEBT-001, mirrored), `RULES`.

### PHYS-005

Independent mass and geometry. Size and mass are separate authored facts. Implementations MUST NOT derive a fighter's mass from their height or a weapon's mass from its length at runtime; cubic scaling is available only as an explicit default _generator_ for hypothetical same-density geometry. Geometry MUST scale linearly. Strength MUST be authored as force and torque, never as acceleration: every linear acceleration MUST resolve as `a = F/m` and every angular acceleration as `α = τ/I`, so a heavier build pays for its own mass without any authored speed penalty. Fighter mass MUST NOT multiply strike damage, and a wielder MUST NOT alter a weapon's mass or inertia — a stronger arm scales applied torque only. Mass and strength are separate profiles: a fighter's _physical_ profile (mass, body inertia, push radius, hurt geometry, held-sword inertia (the sword plus the hands at the grip; plant and commitment do not scale it)) decides how hard they are to move; their _actuator_ profile (weapon drive, control speed, charge drive, heading authority, commitment) decides how hard they drive. A heavier fighter resists displacement more and MUST NOT thereby drive a sword harder; physical strength is an explicit actuator value. Weapons likewise store their physical profile explicitly (mass, lengths, centre of mass, inertia, grip and guard positions, blade radius) and everything else — `C(θ)`, the contact Jacobian, effective mass, the centre of percussion — is derived from the fighter–weapon combination, so a longer or heavier weapon changes acceleration, momentum and contact response with no weapon bonus. Size and mass MUST NOT affect reaction delay, decision cadence, input timing windows, or buffer length. Body-body collision uses inverse-mass normal impulse (nearly inelastic) plus bounded Coulomb tangential friction: the tangential impulse MUST NOT exceed `body_friction × normal_impulse`, and MUST NOT reverse the direction of sliding. Persistent body contact (ticks_in_contact > 0) uses zero-restitution nonpenetration constraint after the first-contact impact. Motors apply force once; the constraint prevents interpenetration. Equal and opposite motor forces cancel exactly — no drift, no energy injection.

### PHYS-009

Body contact lifecycle. Body-body contact is tracked in `BodyContactState` as a two-phase lifecycle: `SEPARATED` (no contact) and `CONTACTING` (bodies touching). `ticks_in_contact` distinguishes the impact tick (= 0, uses authored restitution) from persistent contact (> 0, uses zero-restitution constraint). The contact normal is derived from live geometry each tick (`n = normalize(P_B - P_A)`), not cached from the first contact. Persistent contact applies the minimum impulse needed to prevent interpenetration without injecting energy. The solved constraint impulse (`last_constraint_impulse`, `last_constraint_normal`) is exposed on `BodyContactState` for downstream consumers (CPU observation, analytics) without coupling the solver to them. The lifecycle resets per round and on separation; `end_contact()` clears both phase and impulse data.

### PHYS-010

Bilateral sword-body contact. A weapon→body contact computes one authoritative bilateral impulse `J` from the contact's inverse effective mass `k = 1/m_T + 1/m_A + c²/M_θ` (IMPACT-PHYSICS-001): `m_T` and `m_A` the fighters' real masses, `c` the weapon coordinate's Jacobian on the normal at the contact point and `M_θ` the held sword's inertia (sword plus hands). Every contact, whatever its classification, applies all three from that one `J`: target `+J*n/m_T`, attacker `-J*n/m_A`, sword `-J*c/M_θ`. The persistent nonpenetration constraint uses the same `k`. No classification removes a term: a point driven along its blade has `c ≈ 0` (only the carriage's `C′·n`, zero at Long Guard), so its sword barely turns; a point met off its axis has a real lever and is deflected. Nonlethal contacts (SLASH, GRAZE, nonlethal POKE) enter `CONSTRAINING` and are held impassable every tick at velocity and position level (RIGID-CONTACT-001). Lethal contacts apply `penetration_resistance_fraction` of the full blocking impulse, then enter `PENETRATING` and release the nonpenetration constraint. The `WeaponBodyContact` lifecycle is `OUTSIDE → ENTERED → CONSTRAINING/PENETRATING → EXITING → OUTSIDE`.

### PHYS-006

Rotational inertia. A weapon's own moment about its origin MUST be `I = k · m · L²`, where `L` is its effective rotational length and `k` is an authored mass-distribution coefficient (a uniform rod about one end is `1/3`). A fighter's body MUST use `I_body = k_b · m · r²`. Angular acceleration MUST be derived through `α = τ / I`; implementations MUST NOT author an angular acceleration independently of the inertia it acts against, because the two would drift apart and the object would stop obeying its own mass. One generalized inertia per coordinate is shared by actuator and contact (UNIFIED-MASS-001).

### UNIFIED-MASS-001

One inertia per coordinate (rules 41 onward). The weapon angle θ has exactly one inertia, `M_θ(θ) = M_θ,held(θ)`: the sword's generalized inertia at the pose (its own moment, plus its mass riding the hilt track's `C′(θ)`) plus the hands on the grip (`WeaponKinematics.motor_inertia` / `held_inertia`). Every consumer of θ's dynamics divides by it — the motor in every phase (`θ̈ = τ / M_θ(θ)`: swing, brake, windup, hold), every contact impulse (`Δθ̇ = J·c / M_θ`), the motor's exertion ledger, the initiative estimate, and the physical speed guardrail (through a lower bound valid at every pose). No code may accelerate θ through `moment_of_inertia()` alone, which would give the coordinate one mass for its actuator and another for its contacts. The body translation uses the fighter's real mass for both, and the heading uses `I_body` for both. Implementation: `game/src/domain/combat/weapon_kinematics.gd` (`motor_inertia`), `game/src/domain/rules/weapon_definition.gd` (accelerations take the inertia explicitly), `game/src/domain/combat/weapon_system.gd`. Tests: `RULES` (`test_the_motor_and_every_contact_share_one_weapon_inertia`), `SCALING`, `IMPACT`.

### PHYS-007

Shared contact kinematics. All sword/sword, blade/body, and point/body interactions MUST derive contact-point velocity from the same translational and rotational kinematic model: `v_contact = v_fighter + ω_total × r_contact`, where `ω_total = ω_body + ω_weapon`. No attack classification may apply duplicate movement or momentum bonuses. A sword does not need angular velocity to have contact velocity — body translation alone moves the entire weapon. A stationary weapon struck by a body-translated weapon MUST receive impulse through ordinary relative contact velocity. Forward movement coherence (`v_fighter · â_sword`) participates through structural coupling, not as a separate multiplier on tip velocity, because the translational contribution is already present in `v_contact`. Double-counting forward speed — once in `v_tip` and again as a bonus — is explicitly prohibited. On the attack manifold (WEAPON-PATH-001) the weapon term gains the path's own motion: `v = v_fighter + φ̇·perp(r) + θ̇·(R(φ)·P′(θ) + perp(û·d))`, evaluated additively so a fixed pivot (`P′ = 0`) adds exact zeros; impulses act on the weapon coordinate through its Jacobian (`WeaponKinematics.lever`) and generalized inertia, never through a `(r×n)²/I` revolute assumption.

### WEAPON-PATH-001

One-degree-of-freedom attack manifold. One scalar weapon angle θ ∈ `[-guard_limit, +guard_limit]` drives one rigid sword on the gameplay plane. The sword's carriage (grip centre) `C(θ)` rides an authored, mirrored track in the fighter's CombatHeading frame — `C_lat(-θ) = -C_lat(θ)`, `C_fwd(-θ) = C_fwd(θ)` — with C0 and C1 continuity, sampled from a deterministic table built once per rules instance (WEAPON-PATH-003); the pommel `P = C − g·û` is the origin of blade radii, blade points are `P + û(φ + θ)·r`, and blade yaw is **exactly** φ + θ, never the path tangent. All authoritative sword geometry MUST come from `WeaponKinematics`; no other code may build `centre + û·radius` (lint-enforced). No side-specific physics compensation is allowed. `C(θ)` is the **hilt track**: the projection of the original radial 270° weapon origin (fighter centre + θ + a straight sword) out to where two hands hold the sword in a HEMA guard. It is the only weapon joint — one coordinate, no independent hilt position, velocity, spring or offset state — and its motion is inertia-carrying through `M_θ(θ)` and the Jacobian, while how θ evolves is dynamics (motor, contacts, inertia). Its knots MAY be calibrated offline from posed fighter rigs (symmetrized, one mirrored half), never read from animation at runtime. Implementation: `game/src/domain/rules/weapon_attack_path.gd`, `game/src/domain/combat/weapon_kinematics.gd`. Tests: `KINEMATICS`, `COLLIDE`.

### WEAPON-PATH-002

θ semantic preservation: the manifold changed geometry, not topology. It changes the hilt's translation as a function of θ; it MUST NOT change θ's meaning, ordering or bounds — increasing θ moves monotonically toward the same logical side as before, and the bands (Longpoint, Ready, Load) are defined in θ, never in path arc length or tangent. `WeaponPose = f(θ)` MUST be single-valued: the same θ gives the same hilt and yaw whether it was reached by charging, releasing, rebounding or recovering; there are no separate charge and release paths. Longpoint is a derived θ region (a pose), never a contact override: an active cut passing through it is a SLASH; a settled, low-ω point walked into a body is a POKE; the same posture driven by a committed forward burst is a THRUST. Wherever a swing, rebound, parry or recovery leaves θ is the next starting position (end-angle seating); attack input is legal across the whole range and uses the retained side history at θ ≈ 0. The hands (the carriage), not the pommel, stay structurally forward. Tests: `KINEMATICS`, `POINT`, `ATTACK`.

### WEAPON-PATH-003

A stretched rotational orbit, not a new path system. The sword is still the one-degree-of-freedom 270° rotational sword it always was; the attack path only deforms the old constant-radius hand orbit — which buried two hands in the torso — into a smooth, forward-elongated, mirrored orbit, so forward angles have room for a two-handed posture (WEAPON-ORBIT-001 – 006). It adds no weapon coordinate, no second path, no Long Guard or inflection physics state, and changes no attack, contact or classification law. A blade point at offset `r` from the carriage is `P(θ) = C(θ) + R(θ)·r`, so `P′(θ) = C′(θ) + perp(R(θ)·r)` — the ordinary rotational term plus the carriage's translation, and nothing else. The orbit is authored as a few calibration samples on one side (the named postures — Long Guard 0°, Ready, Gather, Load 135° — are samples of one deformed orbit, not separate paths) and mirrored exactly. It is sampled once into a table and read between samples as the cubic Hermite through the samples' values and slopes, so the slope `C′` a contact is solved with is the derivative of the `C` the sweep moves on (rules 51, BLADE-COLLISION-PARITY-001). It is shape-preserving: away from the centre the carriage's forward offset MUST never rise and its lateral offset MUST never fall (monotone tangents, no overshoot), so it never loops or backtracks. A full charge from the right sweeps −135° → +45° and from the left +135° → −45°: the two attacks are exact reflections, overlap across [−45°, +45°] and together cover the 270°. The shipped calibration (rules 40 onward) is a forward-biased, bilaterally mirrored teardrop: Long Guard keeps the deepest hilt, and the outside of the swing **narrows** toward the fighter — the hands at the load stay inside the shoulder line — rather than spreading sideways, so the swept slash reads as a leaf in front of the fighter, not a propeller round him (SLASH-SHAPE-001). Where a load fails clearance, its forward depth gives before its lateral width. The authoritative carriage MUST describe a sword pose the fighter could physically occupy before any animation or IK is applied; presentation may make that pose look better, never make an impossible one possible. Ownership is split: the domain proves the rigid sword fits around the fighter, and the rig (PRES-RIG, PRES-POSE-001, PRES-ARMS-001) proves the articulated arms can hold it — reach, upper arm, elbow and forearm clearance against the real clothes. Domain clearance is surface to surface: over the whole orbit each hand's surface (`FighterDefinition.hand_radius` round its grip point) and the whole rigid sword, pommel to tip, as a capsule of `blade_radius`, MUST stay outside the hurt torso (`WeaponKinematics.least_surface_gap ≥ 0`); the hands keep visible air at the named postures. An orbit that fails validation — too few, unordered or mismatched knots, an off-centre Long Guard, a rising forward or falling lateral offset, or a hand or any part of the sword inside the torso — makes the rules invalid and the duel unavailable, with `DuelRules.problem()` naming the reason; never a silently substituted profile, which would diverge replays (fail closed; `DuelSimulation.create` returns null). Implementation: `game/src/domain/rules/weapon_attack_path.gd`, `game/src/domain/combat/weapon_kinematics.gd`, `game/src/domain/rules/duel_rules.gd`. Tests: `SHAPE`, `KINEMATICS`.

### SLASH-SHAPE-001

The 270° range is not a hitbox. θ ∈ `[−guard_limit, +guard_limit]` is the weapon's angular coordinate and guard domain — where the sword can mechanically turn. The damaging volume is the actual rigid blade capsule at its authoritative pose, swept continuously from the previous θ to the next (COMBAT-002); the slash's shape is the union of that moving blade and nothing else. There MUST NOT be an attack circle, sector collider, authored attack hitbox curve, animation-driven collider or direction-specific weapon path, and no rule may treat "inside the 270° sector" or "within `strike_reach`" as "can be hit". A target inside the sector but outside the swept blade is missed; a sidestep beats an attack only by leaving the actual future swept blade, and a whiff is the physical result of that (no `WHIFF_PENALTY`, no `SIDESTEP_EVADE` flag). The 270° sector MAY be drawn as debug or guard coverage and MAY inform an estimate (CPU, initiative) — never a hit. Tests: `COLLIDE` (`test_a_target_inside_the_sector_but_outside_the_swept_blade_is_missed`), `SHAPE`, `KINEMATICS`.

### WEAPON-ORBIT-001

θ authority. `−guard_limit ≤ θ ≤ +guard_limit` (±135°) remains the sole weapon angle — in state, payloads, hashes and APIs. No track coordinate, arc length or tangent replaces it; a normalized `θ / guard_limit` may exist only as a lookup index.

### WEAPON-ORBIT-002

Elongated rotation. The carriage (grip centre) `C(θ)` is a deterministic, C0/C1-continuous deformation of the original radial orbit with greater forward extension near the centre. It is a function of θ alone and introduces no other degree of freedom, orientation or state.

### WEAPON-ORBIT-003

Mirror symmetry. `forward(−θ) = forward(θ)` and `lateral(−θ) = −lateral(θ)`. No side-specific physics compensation.

### WEAPON-ORBIT-004

Yaw parity. `weapon_world_yaw = CombatHeading + θ`, always. The world blade direction is the heading's rotation of `(cos θ, sin θ)`: the heading uses the half-turn pair (`heading_sine` / `heading_cosine`, so a heading and the heading half a turn away carry exactly opposite directions) and θ uses the odd series (`sine` / `cosine`, so a left guard is the exact reflection of the right). The orbit's tangent never sets yaw and nothing authors an orientation curve.

### WEAPON-ORBIT-005

One horizontal truth. Collision, the displayed sword and the grip/IK targets all derive their horizontal pose from the same θ + `C(θ)` (`WeaponKinematics`); presentation evaluates it at the interpolated θ, so every drawn pose lies on the orbit. No presentation layer may add a horizontal sword or grip offset, a yaw correction, tip targeting, or a side-specific translation.

### WEAPON-ORBIT-006

Presentation lift. Presentation MAY derive height, pitch and roll of the sword (rotating it about the carriage) and the kinetic chain — arms, elbows, torso coil, hips, feet — from θ, charge and motion state. Those values never alter authoritative planar physics, and presentation bones never drive collision.

### LONG-GUARD-GEOMETRY-001

Long Guard is the longest posture. At θ = 0 the hilt track's carriage is the farthest forward on the whole track (`C_fwd(0)` the maximum, `C_lat(0) = 0`, `dC_fwd/dθ = 0` there), and the tip's forward reach along the combat heading is the maximum over every θ — no angled blade may reach farther forward than the point straight down the heading. The shape stays mirrored (forward even, lateral odd) and Long Guard's top is rounded: inside the corridor's leave edge the hilt stays within a few centimetres of its maximum and ahead of every hilt outside it, and the hands never travel faster per radian of θ than the track allows (`SHAPE`). The centre's depth is authored from the fighter's own canonical rig — the furthest both hands hold the grip while the limiting arm keeps its extension reserve, with the shoulders unmoved to reach it — and never from where an opponent's body would be: the opponent is the contact physics' concern (LONG-GUARD-INTERCEPT-001). The arms' elbows need not match. Long Guard is a reading of the one continuous θ; it MUST NOT select a different mass, solver, brace or retraction. Tests: `SHAPE`, `PRES-RIG`.

### LONG-GUARD-TERMS-001

Three names, and they are not the same state.

- **Long Guard posture.** The blade geometry at θ = 0: the point extended toward the opponent, the longest reach on the track (LONG-GUARD-GEOMETRY-001). A centred-point intercept witnesses this posture as the blade passes the line. It does not witness a stance that stays there.
- **Neutral return target.** The angle the guard-return motor tracks when no stronger control or commitment governs it: `stable_side × guard_angle` (GUARD-RETURN-001).
- **Settled neutral guard.** The equilibrium the current motor law actually holds. With the return active and nothing else driving the blade, that equilibrium is the return target, not θ = 0.

θ = 0 is a posture. This rules version has no control that holds it against the return, so it is not a persistent player stance and no test may treat an intercept as proof that it is. A persistent Long Guard would need that control, and a journey that establishes and maintains it. Tests: `ATTACK` (`test_an_idle_blade_settles_on_its_committed_guard`), `CONTACT-INTEGRITY` (`test_a_centred_point_meets_an_advancing_body_before_the_fighters_do`).

### PHYS-008

Weapon/body coupling through the contact Jacobian. A weapon→body ENTER always computes the physical impact (ImpactResult), and the one solved impulse drives both target pushback and blade reaction (PHYS-010, IMPACT-PHYSICS-001). The weapon's reaction is `Δθ̇ = −J·c / M_θ`, `c` the weapon coordinate's Jacobian on the contact normal (`WeaponKinematics.lever`), applied to `weapon.speed`, never directly to `weapon.angle`; the chronological solver carries the corrected trajectory through the remainder of the tick. Toward the tip a transverse contact has the longer lever and turns the sword more.

There is no stabbing exemption. Classification (SLASH, POKE, THRUST, GRAZE) describes how a contact arose and chooses how its result is read; it MUST NOT choose a different mass model or remove the weapon term. A point driven straight along its blade has a near-zero lever — the rotation term is perpendicular to the axis, leaving only the carriage's `C′·n`, which is zero at Long Guard — so the sword barely turns and the point drives through; the same point met off its axis has a real lever, gives way, and is deflected. Clean penetration of a lethal blow is the lifecycle's job (`penetration_resistance_fraction`, then `PENETRATING`), not a suppressed reaction. Tests: `IMPACT` (`test_an_off_axis_point_turns_the_sword_and_a_centred_one_does_not`), `CONTACT`.

Pushback is the solved impulse, unamplified: there is no game-feel push scale, because any amplification of the target's push without the same impulse on the blade would break equal-and-opposite reaction. Readability comes from presentation, never from extra push. A charged attack pushes harder than a walk-into-point because it carries greater resolved impact, not because the pushback system reads the word `CHARGED`. Charge influences push only through `charge → weapon velocity → relative contact velocity → impact impulse → pushback`.

Body↔body collision MUST NOT directly modify weapon angular state on either fighter.

A well-braced or committed fighter is harder to overcome through the actuators that run before the constraint — root force, motor torque, turn authority — not because contact treats them as heavier. Passive `M_θ` does not change with plant or commitment. There is no second reduced-mass collision for the blade.

### COMBAT-002

Swept collision. Blade and body contact MUST be detected across the whole tick motion in substeps sized so no blade point travels more than `substep_travel`; the earliest contact wins. The sweep samples interpolated poses. It is not an analytic rotational time of impact. Inside `max_substeps`, `substep_travel` is narrower than two blade radii, which is the no-tunnel bound on that sampled path. A graze thinner than the sample can show is not established by the bound alone; the witnesses name the envelope that was actually tried. Past the cap the overflow is counted and the sweep still runs at `max_substeps`. Blade contact MUST outrank body contact when both fall in the same substep. An exact TOI tie between a defensive blade contact and a weapon→body contact MUST be resolved as defense-wins: the blade interception invalidates the body strike. Godot physics MUST NOT decide a hit.

### EMERGENT-COMBAT-001

One small physics kernel, many readings. Authoritative contact response MUST depend only on the current geometry, the current velocities, the rigid mass properties (mass, centre of mass, inertia, generalized inertia `M_θ`, the contact Jacobian), the material properties (friction, restitution, restitution threshold), the bounded actuators (motor torque, locomotion force), and the persisted contact impulses. The simulation knows mass, inertia, geometry, contact, friction, actuators and momentum; swordfighting _concepts_ are read out of what those produce, never built into them. The gameplay labels — Strong/Middle/Weak, sweet spot, centre of percussion, glance, slide, bind, tangle, parry, beat, poke, thrust, riposte, whiff — MAY read the solved result (to classify, to name an event, to drive presentation, to inform the CPU) but MUST NOT select a different contact response, add an impulse, scale a force, zero a velocity, or hold a timer. The one permitted exception is a genuinely different _physical_ feature or material actually being involved (a living body's friction differs from a blade's because the material differs, not because of a label). Consequences of this law that are enforced elsewhere: no Strong/Weak/parry/tip force multiplier and no authored body share (IMPACT-PHYSICS-001); the sweet spot is a loss-only cut-efficiency reading in `(0, 1]` derived from the weapon's own centre of percussion and never an impulse bonus (IMPACT-PHYSICS-001); there is no `BIND` physics state, timer or winner (RIGID-CONTACT-002, CONTACT-MANIFOLD-001); classification MUST NOT branch the solver (COMBAT-003, PHYS-008). Impact emphasis for game feel (hitstop, shake, sparks, clang, trails) is derived downstream from the solved impulse and energy and MUST NOT feed back into the authoritative contact response (PRES-001, HITSTOP-001). A sword-specific conditional in the contact response is a defect unless it names a real physical feature or material.

### CONTACT-AGENCY-001

Contact never disables ordinary fighter controls. Movement, heading control, and weapon actuation stay active through a contact; the contact solver decides which of those bounded efforts are physically possible. A persisted contact is not a bind that freezes the motor, the root actuator, or the turn. Presentation hit emphasis, if it is ever added, is not this — it does not run inside the authoritative step (HITSTOP-001, PRES-001). Tests: `IMPACT` (root motion, retreat, lateral motion, and heading rate all reach the contact), `CONTACT-INTEGRITY` (a commanded walk still presses a held guard).

### RIGID-CONTACT-001

Rigid, impassable contact in live combat. Each authoritative sword's steel is rigid planar convex geometry — its blade capsule and its guard root (STEEL-TOPOLOGY-001); steel MUST be impassable to steel it meets, and a sword MUST be impassable to a living fighter's hurt torso (TORSO-CIRCLE-001). Hands and the handle are not that volume. No blade may move from one side of another blade to the other without a resolved contact, and no blade may pass through a living hurt volume without a body contact; after a contact is resolved, overlap MUST stay within invisible solver slop (millimetres, never a visible pass-through). Contacts are found and resolved in time order (COMBAT-007): a sword lying between the attacking blade and the body is met first, and that contact may change or end the attack before the body is reached; nothing — not a strike that would be lethal — may ignore an intervening sword. Contact geometry MUST NOT favour a slot: where two blades are equally close along an overlap (parallel blades), the contact is the overlap's midpoint, whichever blade is named first. A nonlethal body contact is completely impassable.

Rigidity MUST hold for as long as a contact lasts, not only at its time of impact. A first contact is an impulse; a **persisted** contact — a blade pair the `SwordContactSet` has seen touch (any phase but `SEPARATED`), a sword inside a living body's entry lifecycle (`ENTERED`, `CONSTRAINING`, `EXITING`) — is a normal constraint, solved every tick by `RigidContactSolver`. The constraint is unilateral normal rows (steel↔steel at the nearest points of each steel pair, STEEL-TOPOLOGY-001, and each sword on the other's hurt torso) with Coulomb friction on every sword row (BLADE-FRICTION-001, rules 34 onward) — never a bind, tangle or guard lock. Steel is the blades and each guard root against the other blade from its protected side (STEEL-TOPOLOGY-001, GUARD-PROTECTION-001, rules 52 onward; rules 50–51 the blades alone); two guards never meet, and hands and the handle are not combat geometry (TORSO-CIRCLE-001). (1) Before the tick's motion is carried, every persisted pair touching at the start removes its closing speed (`v_n ≥ 0`, `J_n ≥ 0`, no restitution) and the tick is carried again from the constrained velocities — the motors (bounded torque and force, never assigned speeds) give what a fighter tries to do, the constraint what the sword can do, and nothing later in the tick may overwrite it. (2) After every contact the chronological loop resolves, held contacts are held again from the new velocities; a persisted pair whose overlap passes twice `contact_slop` mid-tick — or, once it has been re-held, one more slop deeper than where that sweep began — is held at that time of impact, from its own fixed budget (`RigidContactSolver.HOLDS_PER_TICK`), never the contacts'. That time is where the pair crossed its line, not where the substep happened to end: a held pair alone in its substep (nothing new, no hand) is refined by bisection, the step count derived from how far the pair closed inside the substep — enough halvings to bring it within one slop, at most `CollisionSystem.REHOLD_REFINEMENT_MAX` = 6, none for a slow pair — so a pair driven slowly through a coarse substep cannot sink a substep of travel past the line between re-holds. The line itself and the tick rate are unchanged. Held contacts rest at the slop itself, so the trigger is clear of where they rest and rounding never decides whether one is re-held (that would break mirror symmetry); "driven deeper" always means deeper than it was held, so a fast-turning contact's second-order drift is cleared by the position stage instead of re-held every substep. A mid-tick re-hold whose velocity solve finds nothing closing (zero normal impulse) proves its deepening is that drift — holding again cannot change the trajectory — so no further re-hold is taken that tick and the position stage clears what remains (rules 41 onward); that is not the re-hold budget running out and is not counted as such. (3) After the loop, overlap beyond `contact_slop` is removed at position level (NGS-style pseudo-motion): θ and the bodies move, velocities never do; each contact's correction is bounded per pass by `contact_max_correction`, a degenerate pin by `RigidContactSolver.TURN_GUARD`, and persisted pairs within reach are held at `w ≥ 0` so clearing one contact never drives another in. Both stages solve their rows together as one complementarity problem (`ContactLcp`: exact, deterministic least-index principal pivoting over the active rows — every touching point of the steel pairs (TWO-POINT-001), each sword on the other's torso, the two bodies, and each held sword's guard stop; every row moves the same few coordinates, the regularized block is positive definite and the solution unique, and `ContactLcp.MAX_PIVOTS` bounds the work), because a sword pinned between the opponent's blade and torso has opposed rows that sequential correction cannot separate, and a sword resting on a torso pushes the bodies, which corrected on its own would drive them into each other. The body row joins only a solve the swords already need, holds the bodies at no overlap (no slop), and every separated body pair rests 1 nm outside touching (`ArenaConstraints.REST_MARGIN`), so rounding never decides whether the next tick sees a body contact. Every solve uses **one mass per coordinate** — each body's and each sword's contact-mechanics mass (IMPACT-PHYSICS-001), taken from the first active row that moves it, in the fixed row order (blade, slot 0's sword, slot 1's, bodies) — so the matrix is symmetric and each solve is a projection in one kinetic-energy metric: with the actuators frozen it MUST NOT add kinetic energy or move linear momentum in that metric, and no clamp on its result is needed. A solve MUST apply its impulse through exactly the inverse masses and inertias it built its effective mass from — never `K` from one mass and `Δv` from another (that has no single energy metric, and is how a solve creates energy). So if bodies are ever moved to answer contacts with their whole mass (a calibration audit, taken only for a demonstrated defect), the translation term is `1/m_body` in `K` **and** `Δv = J/m_body`; the wielder's resistance to a held sword being turned belongs on the weapon coordinate, as a reflected held/grip inertia added to `M_θ` (`M_θ,held = M_θ + I_grip`, used in `K` and in `Δθ̇ = J·c/M_θ,held` alike), never in a substituted translational mass. That passive inertia is distinct from the bounded motor torque, which is the wielder's active strength (mass is not strength). The translation term is the fighter's real mass, applied the same way. Passive `M_θ` is the sword's generalized inertia plus the hands at the grip; plant and commitment do not scale it. The physical normal impulse (velocity stage) is recorded on the manifold and may feed friction, warm starting and impact telemetry; the position stage's pseudo-impulse is recorded nowhere, never warm-started, and never counts as impact, damage or friction pressure. A sword at its guard limit is held there by its stop row and nothing else: no row removes or "locks" its weapon term, because locking it in one manifold row while another row (or the stop row) still turns it gives one coordinate two models and the solve stops being passive (rules 48: a two-point hold against a sword resting on its stop added 3 J). Reaching the stop — landing exactly on it included (`WeaponSystem.settle_at_stop`, one law for the motor and the carry, SYM-STORM-SEPARATING-001) — ends the outward turn (an inelastic stop). A held sword within `RigidContactSolver.STOP_WINDOW` of a stop brings a speculative stop row into the same block — `θ̇·side ≤ (guard_limit − |θ|)/dt` — so no solve counts on rotation the stop will take away and lets a pressed contact sink (no friction, nothing recorded). A hold ends a driven swing (into recovery, a lifecycle rule that moves nothing) only when it arrested the cut, by the one arrest law of RIGID-CONTACT-002: it opposed the cut's progress (`Δθ̇·dir < 0`) and left it stopped, reversed, or pinned under the wielder's control with nothing gained over the tick (`θ̇·dir ≤ min(control_speed, θ̇_start·dir)`). No ratio, no `deflect_fraction`, no timer. A glancing or sliding contact that leaves the cut travelling faster than `control_speed` MUST NOT end it — a persisting contact is not by itself an interrupt, or the phase becomes a hidden bind — and a cut pinned against a body or a stopped guard that only creeps as it yields MUST NOT be pressed forever. An overlap that has not been resolved as a contact yet is a pending hit and MUST be left to the sweep, which resolves it on the next tick. Fixed iteration and pass counts, never "until converged"; a first impact is resolved before anything is held, so the constraint MUST leave it exactly as the impulse model resolves it. `contact_slop` is millimetres (shipped 2 mm). Every fallback is legal (deterministic, and the overlap bounds still hold on its tick) and counted on its own (`ContactDiagnostics.rehold_budget_exhausted`, `position_guard_hits`, `pivot_cap_hits`, `meaningful_contacts_dropped` — TWO-POINT-001), never summed with each other or with the CCD and contact caps; an illegal state is not a counter but `SIMULATION_FAULT`. Adversarial and fuzz play may reach a fallback and is bounded (re-hold budget: at most one exhaustion per 5000 live ticks); the representative ship corpus MUST show zero of each. A budget MUST NOT be raised to make a counter read zero. Tests: `CONTACT-INTEGRITY-SHIP` (audit tier: an 8-seed corpus and a 40-seed ship corpus hold every held contact within the slop, resolve every pending touch the next tick, never cross centrelines, saturate, reach the turn guard or leave the legal state set), `CONTACT-INTEGRITY` (an audited live corpus with frozen actuators proves passivity and momentum; a clean first cut and a first clash are bit-identical with the constraint inert; walking pressure and a driven cut cannot push through; held pressure mirrors exactly; the solver carries nothing between solves; the motors pressing a held contact are bounded; a blade across a handle is no contact; the swing interrupt moves nothing and fires only on an arrested cut — a BLOCKED cut ends by the hold, PRESSURE-GUARD keeps a cut active against a guard on its stop while it travels faster than `control_speed` and ends it once the press brings it under control; clearing a sword on a torso never drives the bodies together; LONG-GUARD-INTERCEPT-001 and beat-aside-then-close).

### RIGID-CONTACT-002

No scripted bind; one arrest law. A bind is not a physics state — there is no `BIND`/`BOUND` phase, no `bind_started` event, no bind timer, no `bind_escape_ticks`, no plant-or-squareness winner, and nothing that zeroes a weapon's speed because two blades are touching. A bind is only a _reading_: a contact the `SwordContactSet` has kept persisting (CONTACT-MANIFOLD-001), solved rigidly every tick by `RigidContactSolver` like any other persisted contact. Whether a swing is interrupted MUST be decided by one arrest law shared by a first impact and a held contact: a contact arrests a cut when it **opposed** it (the contact's change to the cut's angular speed is against the cut, `Δθ̇·dir < 0`) **and** left it either **stopped or reversed** (`θ̇·dir ≤ 0`) or **pinned** — back under the wielder's control (`θ̇·dir ≤ WeaponDefinition.control_speed`) with nothing gained over the whole tick despite its motor (`θ̇·dir ≤ θ̇_start·dir`, the blade's speed at the start of the tick, `FighterTickScratch.weapon_start_speed`; rules 45 onward). `control_speed` is the one speed at which a blade is under control everywhere: it gates a new attack (`can_start_attack`) and ends a recovery (RECOVERY-001); a cut a contact holds there and its motor cannot gain on is no longer swinging through anything — the wielder is pressing it. A cut launched from a contact it was already resting in is under control on its first tick but gaining, so it is still a cut: cutting out of a bind stays possible. An arrested cut ends into recovery — a lifecycle rule that changes the phase only and MUST move no velocity; a contact that reversed the cut keeps its rebound into recovery, never assigned away. How long a contact lasts MUST NOT be part of the law: persistence is not interruption, and a contact that slows a cut but leaves it travelling faster than `control_speed` (a glance, a frictionless slide, a beat carried through) MUST leave it active, so continued pressure that later brings it under control ends it only then. A cut pinned against a torso or a stopped guard, creeping only as what it presses yields, is arrested — never pressed for as long as the bodies take to slide apart, which would hold the wielder unable to act (AUTHORITY-001). The derived vocabulary — glance, slide, bind, tangle, disengage, beat, parry, riposte — names what these trajectories did and MUST NOT be read back as solver state (EMERGENT-COMBAT-001). Implementation: `game/src/domain/combat/contact_resolver.gd` (`arrests`), `game/src/domain/combat/weapon_system.gd` (`begin_recovery`). Tests: `CONTACT` (`test_one_interrupt_law_decides_blocked_from_glancing`), `CONTACT-INTEGRITY` (BLOCKED ends on an arresting clash; PRESSURE-GUARD stays a cut while it travels faster than control and ends once pressed under it), `IMPACT` (`test_a_frictionless_crossing_does_not_consume_tangent_velocity`), `CPU` (a CPU tapping from a clinch is never stuck in a pressed cut), `REPLAY`.

### CONTACT-FALLBACK-001

Solver saturation invokes a fixed, deterministic, conservative no-tunnel fallback; it is not a combat mechanic, and representative play MUST NOT depend on it. The re-hold budget (`RigidContactSolver.HOLDS_PER_TICK`) is a fixed bound and MUST NOT be raised to make a counter read zero. Contact identity across ticks is geometric — the least movement along both blades (CONTACT-IDENTITY-001) — so a held contact keeps its identity through a storm. Once a tick has spent the budget, the remainder of that tick MUST be carried so a held contact cannot be driven through: in the sweep's own substeps (its travel metric, capped at `max_substeps`), each followed by the position stage, so the pair keeps its last non-penetrating side and only the advance along the contact normal is cancelled. Tangent slide and every other motion MUST carry on; the fallback MUST NOT touch a velocity (θ̇ is never zeroed), snap a pose, or create a bind or any event; it is counted only as `ContactDiagnostics.rehold_budget_exhausted`; the next tick starts with the full budget. In representative play an exhaustion is accepted only as CONTACT-REHOLD-FALLBACK-001's class, within that law's measured baseline; the development corpus is only bounded (at most one exhaustion per 5000 live ticks). Implementation: `game/src/domain/match/duel_simulation.gd` (`_carry_without_tunnelling`). Tests: `CONTACT-INTEGRITY` (`test_a_rehold_storm_falls_back_without_tunnelling_and_stays_mirrored` — a point-symmetric adversarial storm: no held overlap beyond the slop, no centreline crossing, the side kept, θ̇ left as the contact left it, the reflection exact, one exhaustion only), `CONTACT-INTEGRITY-SHIP` (the ship and development corpus bounds), `TWO-POINT` (contact identity follows the point, a surviving endpoint keeps its own history).

### CONTACT-REHOLD-FALLBACK-001

The bounded re-hold fallback in representative play (rules 52 onward). One held contact sliding fast along a turning blade can close again after every re-hold — its normal turning a few degrees between them — and so spend all of `RigidContactSolver.HOLDS_PER_TICK` without a fault in the contact; the rest of the tick is then carried by CONTACT-FALLBACK-001. Representative play MAY reach this, and only when all of these hold: (1) it is deterministic and reproducible — the same input replays the same states; (2) the contact is geometrically valid: the exhausted tick's re-holds held **one** persistent contact identity (CONTACT-IDENTITY-001), neither stale nor duplicated, and every one solved a positive closing impulse (`ContactDiagnostics.rehold_fallback_identities` / `rehold_fallback_least_impulse` — diagnostics, never hashed and never read by play); (3) every impulse and every authoritative value stays finite and physically possible (`StateInvariants`); (4) held penetration stays within the solver slop; (5) the fallback adds no energy and changes no velocity (CONTACT-FALLBACK-001's construction), and the contact is never one ordinary input cannot leave — a back step by either fighter, forked from the tick after, parts the blades legally and within the slop; (6) the following ticks are stable — no second exhaustion within 60 ticks, the contact resolves, continues as a valid held interaction, or separates; (7) it is counted only as `rehold_budget_exhausted`, never as a converged hold, and reported with its rate. The acceptance envelope is the ship corpus's measured baseline, not a chosen rate: one exhaustion (ship seed 122, tick 854) in 46,031 live ticks on rules 52, and none in 47,247 on rules 53 (stamina re-rolled the duels), so the baseline is now zero; the class stays witnessed by the seed-122 regression played with stamina neutral. The corpus is deterministic, so a different count is a behaviour change to attribute — more is a deterioration and fails; fewer is re-measured and the baseline lowered. An exhaustion outside the class fails the ship gate whatever the count. The budget MUST NOT be raised, and the solver's impulse direction is not changed to remove this class. Tests: `CONTACT-INTEGRITY` (`test_the_seed_122_fast_slide_fallback_is_bounded_and_escapable` — the rules-52 duel, stamina neutral, production input from tick 0: two identical runs, one counted exhaustion of one identity with a real impulse, the slop and every tick legal through 60 ticks after, no saturation, and a back step from either side or neither fighter acting parts it), `CONTACT-INTEGRITY-SHIP` (every exhaustion in the ship corpus classified against (2), (5) and (6), and the count against the baseline).

### BLADE-FRICTION-001

Coulomb friction, one law for every sword contact. Every sword contact — a first blade clash (`SwordContactSolver`) and every held row (`RigidContactSolver`: sword↔sword and sword on a living torso) — opposes sliding at the contact point with a tangent impulse along `(−n_y, n_x)`, computed from the same authoritative point velocity as the normal (fighter translation, CombatHeading rotation, θ̇, the attack track's `C′(θ)`) and applied through the same masses. The **accumulated** tangent impulse MUST stay in `[−μ·Jn, +μ·Jn]` (clamped on the accumulation, applying only the difference), for a fixed iteration count (`RigidContactSolver.ITERATIONS = 4`), in fixed row order. `μ` is a property of the touching materials only, resolved from the rules' material table (CONTACT-MATERIAL-001: steel↔steel 0.20, steel↔flesh 0.05, steel↔stone, steel↔wood; rules 50 removed `guard_friction` with the crossguard and handle steel it described, STEEL-TOPOLOGY-001) — gameplay calibration seeds owned by 7B.8, never a function of strong/weak, charge, bind or glance. The same law holds a sword on a stage structure (STRUCTURE-CONTACT-001). The laws, which tests prove and tuning may never break: `μ = 0` ⇒ `Jt = 0` exactly and the solve is the frictionless one bit for bit at any iteration count; a slide whose demand exceeds `μ·Jn` keeps sliding (saturated, residual slip); one inside the cone may stop; more normal impulse means more capacity and less means less; a separating contact has `Jn = 0` and no friction; geometric separation removes friction immediately; the mirrored contact gives the same `Jn` and the reflected `Jt`; with the actuators frozen a held solve adds no kinetic energy. Friction MUST NOT be accepted or tuned against "fewer long contacts": a long contact may be a legitimate fast slide. A body's surface moves with its centre (no torso spin is modelled). Tests: `FRICTION`, `MANIFOLD`, `CONTACT-INTEGRITY` (passivity audit), `FUZZ` (mirrored stream including the tangent impulses).

### RIGID-CONTACT-003

Warm start from the same contact point only. The tick's first held velocity solve starts each row from the physical impulses accumulated over the previous tick by the record that is **the same contact point** (CONTACT-IDENTITY-001: least movement along both blades, one to one) — never by array slot (`SwordContactSet.hold_*` with the blade fractions each row was solved at, `WeaponBodyContact.hold_*`). A point that jumped past the match distance, or a pair that is no longer touching, starts cold and clears the record. The record is kept compact in row order. The normal block is solved exactly from the warm start, so it changes where the iterations begin, never the problem. The position stage's pseudo-impulse MUST NEVER be recorded, warm-started or read as friction pressure. The record is carried state and is hashed (`StateHasher`). Tests: `FRICTION` (`test_a_warm_start_reads_only_the_same_point`: another point's record is exactly cold; the position stage never feeds it; `test_a_held_slide_keeps_its_identity_while_the_point_migrates`), `TWO-POINT` (a surviving line-contact endpoint starts from its own held impulse).

### CONTACT-IDENTITY-001

A contact point's identity is geometric, never its storage slot. Contact points are stored compactly in a canonical, mirror-safe order (by distance along each blade from its base), but when one end of a line contact leaves, the survivor changes slot — so "which point is the same contact as last tick" MUST be decided by one matcher, `SwordContactSet.assign`: a new point matches an old point only within `MATCH_DISTANCE` of movement, measured as `|Δfraction_a| + |Δfraction_b|` along the two blades; the assignment is one to one; of every legal assignment (at most seven for two points — a fixed 2×2 problem, no dictionary, no general matching algorithm) the one matching the most points wins, then the least total movement, then a fixed order (identity before swap). A mirror leaves every fraction, and so the assignment, unchanged. That one matcher owns everything that asks "same contact?": the warm-start impulses (RIGID-CONTACT-003), `persisted`, a point's `age`, and its `contact_id` — the identity presentation keys spark streams and scrape loops on (CONTACT-PRESENTATION-001). There is no separate "same physics point" and "same presentation point". `contact_id`, `age`, the next id and the hold record's blade fractions carry from tick to tick and are hashed. Implementation: `game/src/domain/state/sword_contact_set.gd`, `game/src/domain/combat/rigid_contact_solver.gd`. Tests: `TWO-POINT` (`test_contact_identity_follows_the_point_not_the_slot`, `test_a_surviving_endpoint_keeps_its_own_history`), `FUZZ` (identity mirrors), `FRICTION`.

### GUARD-CONTACT-001

Superseded at rules 50 by STEEL-TOPOLOGY-001 and GRIP-NONBLOCKING-001. Rules 35–49 made the crossguard and the handle rigid, frictional features of each sword (`GUARD`, `HILT`, `guard_friction`); their concave hooks and slots, two held points on non-parallel features locking the pivot, and the crossguard friction reaching both bodies held binds that ordinary input could not open. Nothing in the simulation keeps that topology.

### STEEL-TOPOLOGY-001

Steel is three pairs (rules 52 onward): blade on blade, and each sword's blade on the other's guard root — never guard on guard. Each blade is a capsule of `blade_radius` from its guard root's apex (`WeaponDefinition.guard_root_apex_radius()`) to the point (`tip_radius`) at the authoritative pose; the guard root is the convex proxy of GUARD-PROTECTION-001, steel only against a blade on its protected side. Every pair holds at most two points (TWO-POINT-001): `SwordContactSet.PAIRS` = 3, `POINTS_PER_PAIR` = 2, `CAPACITY` = `RigidContactSolver.BLADE_ROWS` = 6. Ownership never overlaps: a guard point and a blade point that are one constraint (pushing the same way at the same place) are one row — the blade's, unless the guard's surface is nearer along that push by more than `SwordContactGeometry.OWNERSHIP_TOLERANCE` (numerical), and then the guard's, the blade point behind it dropped — so no stretch of steel is held twice and a tie at the apex never flips owner. No code path lets a hand or the handle reach the rigid solver, nor one crossguard the other: guard on guard has no pair, so two guards cannot hook, tangle or lock. This is structural — those parts are absent from the contact geometry — never a zero-impulse check after the fact. Rules 58: when the handles or crossguards meet and both guard pairs have a candidate within `SwordContactGeometry.START_CAP` (1 mm of that blade's apex), those start-cap candidates are not steel. One blade into one guard stays. Blade on blade stays. The only sword-on-sword material is `blade_friction`. A defender is protected only by steel that physically intercepts the incoming cut — its blade, or its guard root from the blade side; no stance confers protection because it is called a guard, and where that steel is not in the cut's path the cut may reach the torso. The full sword is still the moving model — kinematics, damage, leverage and the drawn sword are unchanged. Rules 50–51 had the blades alone (each from `blade_base_radius`, `CAPACITY` = 2) and the crossguard passed through, visual only; rules 52 restores its protective side as steel and nothing else of it. Implementation: `game/src/domain/combat/sword_contact_geometry.gd`, `game/src/domain/state/sword_contact_set.gd`, `game/src/domain/combat/rigid_contact_solver.gd`. Tests: `GRIP` (`test_steel_is_the_blades_and_each_guard_on_its_protected_side`, `test_two_crossguards_never_meet`, `test_hilts_pass_and_a_blade_still_meets_the_guard`, `test_the_mutual_cap_is_symmetric_and_one_sided_blocks_stay`, `test_live_manifolds_are_two_points_a_pair_at_most` — live play reaches the guard pairs —, `test_every_parry_is_an_arrested_steel_contact`), `TWO-POINT` (the broadphase is exact near contact against a brute-force reference of all three pairs and conservative beyond), `CONTACT-INTEGRITY-SHIP`.

### GUARD-PROTECTION-001

A crossguard protects its blade side and only that (rules 52). Its steel is the guard root, a deliberately bounded convex proxy: a rounded triangle from the crossbar's two ends (`crossguard_half_span` either side, at `crossguard_centre_radius`) to an apex on the axis, every edge at the bar's own thickness (`crossguard_radius`). It rises only as far as keeps it within the bar's rounded edge: its surface stands out beyond the drawn bar and blade by at most `crossguard_radius` — the rise `WeaponDefinition.guard_root_rise()` = `crossguard_radius / (crossguard_half_span − blade_radius)` of the half-span is derived from exactly that bound (0.1025 on the shipped sword, apex 0.259 m, 1.25 cm) — and nowhere on the grip side of the bar. (A first rules-52 root rose half its half-span with edges at the blade's thickness and stood out 5.4 cm in the corner: steel the player could not see.) The blade's steel starts at the apex, just above the drawn guard, so the blade's own stretch there is steel from either side. Whether a blade against it is steel is decided before any solver row exists, from the side it comes from: the signed distance, along the guard's own sword axis from the bar, at which the attacking blade's centreline crosses that axis. Beyond the bar's thickness (`crossguard_radius` + `SwordContactGeometry.SIDE_TOLERANCE`, a numerical tolerance) toward the point is the protected side; beyond it toward the pommel is the grip side; within it is no side, and no side is never protection. A blade within `PARALLEL_SINE` of parallel to the sword has no stable crossing and reads its point nearest the bar instead; one lying beside the bar is no side. The reading is latched when the pair first touches (`SwordContactSet.guard_mode`: free, protected or passing; hashed) and kept until the pair is apart by `separation_epsilon`, with one release: a protected pair whose blade reads clearly on the grip side — beyond the band, having slipped off round the quillon — passes from then on, so the root never holds a blade against the bar's grip-side face. Passing never turns protected while the pair touches: a blade that entered from the grip side passes through the root even once its line is above the bar. Within the band a protected pair stays protected — no jitter at the line. A protected pair is ordinary steel: the same rows, friction and chronology (earliest contact → classify → solve → resweep) and the same outcome readings — a parry or deflection only under PARRY-001's and DEFLECTION-001's physical criteria, with `WeaponDefinition.crossguard_protects` the guard's protective reading as `blade_protects` is the blade's (DEFENSE-ROLE-001, NO-LABEL-PHYSICS-001). ### TWO-POINT-001

### COMBAT-007

Contact chronology and lifecycle. All contact types — blade↔blade, blade→body, tip→body, and body↔body — MUST share one unified chronological TOI loop. The tick MUST be resolved in the order its contacts actually happened: find the earliest contact among all interaction types in what remains of the tick, advance to that time of impact, resolve it according to its interaction type (bilateral blade physics, one-way weapon→body consequence per PHYS-008, or bilateral body mass impulse), then carry the remainder forward from the **post-resolution** state and search again. Body separation MUST NOT be applied as a pre-contact pass before sword contacts are evaluated, because a body-separation correction can move a fighter away from a sword tip and erase a stab that chronologically preceded the body overlap. Implementations MUST NOT enumerate candidates from the original start and end poses and sort them, because an early blade contact changes whether a later body contact exists at all. The loop MUST be bounded by `max_contacts_per_tick`; exhausting it MUST hold the pair in contact and report a diagnostic rather than permit tunnelling. A contact already being held MUST NOT spend that budget again: a pair is reported on the substep it comes into touch (bodies: when they meet, at most once a tick — a later re-overlap is separated where each remainder is carried; persisted sword contacts: when their overlap passes `contact_slop`, from their own hold budget, RIGID-CONTACT-001), never on every substep it stays touching. Live play MUST NOT saturate the loop (`CONTACT-INTEGRITY`).

Whether a touch is a _new_ blade contact MUST be decided by the `SwordContactSet` lifecycle (`SEPARATED → CONTACTING → SEPARATING`, see CONTACT-MANIFOLD-001) with `separation_epsilon` hysteresis, not by a cooldown counter: touching parts MUST genuinely separate before they can strike again, and a persisted pair MUST register no new first-impact restitution until it separates. A persisted contact is never a bind state (RIGID-CONTACT-002): it is re-solved rigidly every tick, it has no timer or forced release, and no pressure picks a winner.

Weapon→body contact MUST use a per-attacker entry-contact lifecycle (`OUTSIDE → ENTERED → INSIDE → EXITED → OUTSIDE`) with separation hysteresis. Damage is applied only on the `OUTSIDE → ENTERED` transition. While the weapon remains inside the body volume (`INSIDE`), no further damage is dealt. The lifecycle rearms only after a genuine geometric exit (`EXITED → OUTSIDE`). This prevents a penetrating sword from dealing repeated damage across successive ticks while overlapping. Arbitrary invulnerability timers MUST NOT be used; geometry decides when the weapon has genuinely left the body.

### IMPACT-PHYSICS-001

Unified weapon contact. Lethality is never calculated from charge, angular velocity or blade region on their own: every interaction is derived from the complete instantaneous state of the authoritative rigid sword at the exact time and point of contact. The contact point's world velocity includes fighter translation, CombatHeading rotation, the weapon's rotation and the carriage's translation along its orbit (`C′(θ)`, `WeaponKinematics`); the contact's blade fraction (0 guard, 1 tip) identifies where on the weapon it landed. Every sword contact — blade on blade, blade into a body, the persistent sword-body constraint — MUST be solved through one contact mechanics (`ContactMechanics`): each sword-holding side contributes `1/m_body + c²/M_θ` (its real body mass and its held weapon inertia through the Jacobian `c`), a struck body its real mass; the impulse is `J = (1 + e)·v_n / k` and maps back into body velocities (`J/m`) and weapon speeds (`J·c/M_θ`) through the same terms. There is no authored body share, Strong/Weak multiplier, parry multiplier or tip multiplier; Strong and Weak are readings of leverage. There is one contact model and many readings: contact geometry decides the normal, the axial and transverse components and the Jacobian; the same effective-mass solve gives the impulse and the energy; classification (SLASH, POKE, THRUST, GRAZE) only interprets that result and MUST NOT select another mass model (PHYS-008). Knockback, recoil and stagger read the solved impulse. Severity reads the energy the contact dissipates. There is one energy law: `E_diss` is the drop in the kinetic energy of the coordinates the contact solve moved, in the masses it moved them with (`SwordContactSolver.kinetic_energy` before minus after) — one point or two, restitution and friction included, never a per-row sum. For one frictionless row it is exactly `E_diss = ½(1 − e²)·v_n² / k` — the physical ceiling, never equated with injury: damage reads `E_diss` against the classification's reference (cut or thrust), scaled only by loss-only factors in `(0, 1]` — the blade's bite at the contact (cut efficiency) and the contact's validity (edge alignment for a cut, incidence for a point) — and exposure never modifies the consequence (PHYS-004). Out-of-plane edge alignment is not simulated: during an active slash the edge is structurally assumed to lead, and presentation honours that plane. Charge reaches impact only through the velocity the motor built; the motor never adds impulse at contact. A weapon's centre of percussion about the hands (`I_grip / (m·a)`) is a derived weapon property and a reference point, not "where the most force is": the cut-efficiency profile peaks there and MUST stay in `(0, 1]` — it models losses the rigid model omits and can never add energy. The references that normalize impulse and severity (`reference_impulse`, `reference_severity`, `reference_thrust_severity`) are the **injury calibration** (rules 42 onward): named, unit-bearing physical constants authored in the rules content — the stagger impulse (N·s), the cut's reference-quality wound (J), and a point driven straight in (J), seeded from what the reference strike of the reference pair (CONTENT-002) delivered when the damage curve was calibrated (rules 39) — never re-derived from the current mechanics, so a change to the hilt track, the inertia or the swing speed changes what a cut delivers and never what that much energy does to a body. The cut's reference was re-seeded once, deliberately, at rules 49 (the knife-edge pass, DEFLECTION-CONSEQUENCE-001's companion): the reference strike's measured energy (`REFERENCE_STRIKE_ENERGY_J`) is `REFERENCE_STRIKE_SEVERITY` = 2 reference-quality wounds, so a square, fast cut at the centre of percussion saturates the compressive top of the curve while severity's `v²` keeps a slow or misplaced cut a scratch. `ContactMechanics.reference_*` derives the same strike on the current mechanics as a witness that MUST stay close to the pinned measurement (`RULES`, `IMPACT`); re-seeding the calibration is a deliberate damage-balance change, never a side effect. There is no universal sword force: peak force depends on contact duration and the compliance of what is struck, so no rule MAY author, calibrate against or read a contact force; average force `J/Δt` is presentation or instrumentation only. Velocity, effective mass, impulse and energy are the primary quantities. All of this stays in the fixed-tick domain; Godot receives immutable results. Implementation: `game/src/domain/combat/contact_mechanics.gd`, `game/src/domain/combat/impact_model.gd`, `game/src/domain/combat/sword_contact_solver.gd`. Tests: `IMPACT`, `DAMAGE`, `MANIFOLD`.

### CONTACT-MANIFOLD-001

One owner of blade contact. `MatchState.blade_contact` is a `SwordContactSet`: the single authoritative record of whether, where, and how the blades touch. No second class or flag MAY carry an independent notion of blade contact. Its points MUST be fixed capacity (`CAPACITY = 6`: two on each of the three steel pairs, TWO-POINT-001), stored in a canonical mirror-safe order (by pair, then by distance along each sword from its origin), and identified geometrically (CONTACT-IDENTITY-001) by their pair and their place along both swords — never by the strong/middle/weak band a blade fraction falls in, so a contact sliding along a blade stays the same contact. A point is `persisted` only when `SwordContactSet.assign` matches it to a point touching on the previous tick — never by slot. Separated geometry MUST leave no points; no timer may keep one alive.

Blade impulses MUST go through `SwordContactSolver`: a normal stage (`Jn ≥ 0`, restitution as a target set once from the pre-solve closing speed) then a tangent stage clamped to `|Jt| ≤ μ·Jn`, for a constant iteration count — never "until converged"; the normal stage is repeated only after a tangent stage moved the velocities. Final normal guarantee: when the fixed iterations end on a tangent step, a last normal-only top-up adds non-negative normal impulse until every row meets its restitution target, and no tangent step follows it (a larger `Jn` only widens the cone, and a non-negative projection only removes energy) — one point or two, first impact or hold (`RigidContactSolver._push_normal`). With one point and `μ = 0` the solve MUST equal the one-shot impulse `(1 + e)·closing / K` exactly, at any iteration count, where `K = lever_a²/I_a + lever_b²/I_b + 1/m_a + 1/m_b` (IMPACT-PHYSICS-001; `m` each wielder's real mass): the swords are held, so each wielder's body takes the impulse too (`Δv = J/m` along the normal). Along a long lever the weapon terms dominate; near the hands, where the levers vanish, the bodies carry the contact instead of the swords spinning without bound. Shipped blade contact has Coulomb friction (BLADE-FRICTION-001).

Every contact-pipeline cap (`max_substeps`, `max_contacts_per_tick`, `SwordContactSet.CAPACITY`, the iteration counts, `ContactLcp.MAX_PIVOTS`, `RigidContactSolver.HOLDS_PER_TICK` and its iteration and pass counts) MUST be fixed; reaching one MUST NOT add work, MUST take a deterministic fallback, and MUST be counted in `ContactDiagnostics`, one counter per cap (never hashed, never read back by the simulation, never summed into one opaque number). The application exposes each counter and the step cost as its own `Riposte/*` Godot custom monitor (`CcdCapHits`, `ContactCapHits`, `MaxManifoldPoints`, `ReholdBudgetExhausted`, `PositionGuardHits`, `MeaningfulContactsDropped`, `PivotCapHits`, `SimStepUs`).

### COMBAT-003

Physical, relational consequences. Blade contact resolves as a 2D rigid impulse (relative contact-point velocity, effective mass, effective inertia, contact radii, normal); low-energy contact binds. Parry and riposte are classified outcomes, never inputs: a parry is physical interception (PARRY-001), and the riposte advantage it leaves is a separate tempo reading. A body strike resolves in two stages that MUST stay separate: a _physical interaction_ producing impulse and severity from blade-point velocity, target velocity, effective mass, and contact geometry; then a _combat consequence_ mapping severity, blade efficiency, and edge alignment to damage, stagger, and recovery disruption (exposure is a reading, PHYS-004). Criticals come from physical convergence — quality, blade region, edge alignment — never chance and never exposure. Simultaneous body hits are evaluated against pre-hit state, so double hits stay symmetric. See PHYS-001 – PHYS-004.

### PARRY-001

A parry is physical interception, never a timing verdict (rules 45 onward). `PARRY` MUST be emitted exactly when an attack's **first sword contact** — so the defender's weapon met it before any body did — lands on the defender's protecting steel — its blade (`blade_protects`) or its guard root from the blade side (`crossguard_protects`, GUARD-PROTECTION-001; DEFENSE-ROLE-001; the handle is not steel, STEEL-TOPOLOGY-001) — has exactly one side swinging, solved a positive normal impulse, and **arrested** the cut by the one arrest law (RIGID-CONTACT-002), so the body hit it was carrying is prevented or delayed. A clash the cut carries on through, however slowed, is not a parry. The event carries the **riposte advantage** (`MARGIN`: the attacker's time-to-threat minus the defender's, THREAT-001, read from the state the interception left) as a separate tactical reading; it MAY be zero or negative — a physical parry that won no tempo is still a parry — and MUST NOT decide whether the event fires. There is no parry window, no parry input and no parry margin constant.

Arrest does not make that attack immune (rules 55). No timer, no `defended` flag, and no scripted skip of a later entry (COMBAT-007, COMBAT-013). The cut's body hit is prevented when the trajectory the arrest left misses the torso, and delayed when that same trajectory still enters it. A later entry is a residual hit of the arrested attack only when all of these hold: it is before the attacker's next release, the attacker is in `RECOVERY` and not swinging, the contact is a torso entry, and it is not a `THRUST` — a thrust that still qualifies drove through and the defense failed (COMBAT-010). A residual hit is also not a decisive wound: its damage stays strictly below half the target's health, the bar a clean committed cut is already required to clear. A larger hit, a thrust, or a hit from a new release is a different attack, not evidence the parry worked. Implementation: `game/src/domain/combat/contact_resolver.gd`. Tests: `CONTACT` (`test_tap_into_a_strong_guard_is_parried` proves the parry physically — the same tap lands with the guard seated away, the guard meets it first with a positive impulse that arrests it, no body is hit — and then requires the label; `test_a_clash_the_cut_carries_through_is_not_a_parry`), `FULL-E2E` (`test_a_blade_catch_parries_a_cpu_attack_and_the_riposte_lands` — arrest, then any residual entry of that swing under the conditions above, then the human's later hit).

### WHIFF-001

A whiff is a label applied after physics produced a miss, never a mechanic. `ATTACK_WHIFFED` MUST be emitted exactly once, when an attack ends (its overswing comes to rest) without having met the opponent: `WeaponState.attack_contacted`, reset at release and set by any solved opponent contact with a positive normal impulse — a body hit (lethal or not), a blade clash, a held contact pressing on the opponent's sword or torso. A speculative touch that solved no impulse is not contact, and a sword's own guard stop is not the opponent. Nothing in the authoritative simulation or the CPU may read the whiff: it MUST NOT lengthen recovery, reduce turning, change damage, shove a body, change a brake or drive a decision. A whiffed attack is punished only by where its physics left it (RECOVERY-001, COMBAT-002). `attack_contacted` is hashed state only so the label is emitted deterministically once. Implementation: `game/src/domain/combat/weapon_system.gd`, `contact_resolver.gd`, `rigid_contact_solver.gd` (`opponent_contact`); lint `WHIFF-001` restricts who may name the event and the flag. Tests: `ATTACK` (a landed tap is never a whiff; the same free miss with its label suppressed moves every body, sword and phase identically on every tick), `CONTACT` (a hit that carries into overswing is never a whiff; the cut that met nothing is, once).

### DEFLECTION-CONSEQUENCE-001

A won line is physical, never awarded (review 11). Weapon contact MUST NOT assign a winner, a recovery state, a counter window, an angle bonus, a knock-away direction or a commitment penalty. The contact's solved impulses (normal and friction, at the contact point, through each sword's lever and generalized inertia and each body's mass, from the pre-contact velocities — RIGID-CONTACT-001, IMPACT-PHYSICS-001) determine each fighter's resulting X, V, φ, φ̇, θ and θ̇, and that state is the whole consequence. A fighter whose weapon is displaced, or moving away from a threatening line, must physically arrest and redirect that momentum with the same bounded actuators used everywhere else (RECOVERY-001, COMMITMENT-001), so a stronger deflection — a larger solved change in `M_θ·θ̇` away from the line — makes a larger and longer-lived threat advantage, and a glancing contact makes little or none. A whiff obeys the same law: nothing stopped its momentum. There is no `PARRY_RECOVERY`, `WHIFF_RECOVERY`, parry knock-back or strong/weak parry multiplier, and restitution is not an opening lever. PARRY, WHIFF, RIPOSTE and advantage are readings of the outcome (PARRY-001, WHIFF-001, THREAT-READINESS-001); presentation MAY scale clang, sparks, recoil and camera impulse from the solved impulse and the advantage, never feed them back. Tests: `CONTACT` (NO-LABEL-PHYSICS-001), `DAMAGE` (REVERSAL-DEBT-001); the lost-line corpus (`game/tools/reacquisition_probe.gd`) measures the advantage a deflection leaves from forked, real-physics punishes (`game/tests/harness/state_fork.gd`), never from the estimate alone.

### PHYSICS-GAMEFEEL-001

Physical truth, calibrated interaction density (review 15). The deterministic simulation defines what is physically possible; game design calibrates the physical parameters so that the strategically interesting possibilities occur often enough, read clearly enough and resolve quickly enough to form a competitive combat loop — READ → COMMIT → CHANGE LINE / DEFEND → PHYSICAL OUTCOME → RECOGNIZE ADVANTAGE → CLOSE / CAPITALIZE → DECISIVE CONSEQUENCE → RESET — rather than swing → collide → both safe → repeat. There MUST NOT be a separate law for WHIFF, PARRY, COUNTER, DODGE, PUNISH, PLANTED or ADVANTAGE. It is legitimate to tune swing drive and brake torque, movement acceleration and braking, turn authority, target swing speed, momentum-driven overswing, arc geometry, input buffering, weapon and hurt geometry, contact materials and the damage calibration when measured play shows the correct system is dull or degenerate — one lever per rules version, measured, with its version bump (SIM-002). Ordering constraints, not numbers: a tap is fast, low-commitment and relatively safe, punishable mainly when badly spaced or read, and never equivalent to a full cut; a full commitment controls more space, carries more energy, redirect debt and visible wind-up, and makes a larger exploitable error when read early and sent down the wrong line, without every full miss guaranteeing a hit; lateral movement changes geometry fast without dodging; retreat buys space and relieves forward debt at the cost of closing energy; defense spans hard block, neutral bind, glancing deflection, strong parry and lost line from the actual contact, so a passive sword is never a forcefield. Responsiveness is command, not agility: turn, movement reversal, attack and release inputs take effect on the tick they arrive (AUTHORITY-001) with the small deterministic attack buffer; the time to turn, stop, reverse a sword or re-enter comes only from physics. Good positioning MUST be able to change whether an identical action is safe or punishable.

### NO-LABEL-PHYSICS-001

A classification changes no physics. For each contact label (PARRY, WHIFF) the same physical scene, once labelled and once with the label made ineligible by a classification-only input, MUST move every body, sword and phase identically on every tick; the only difference is the event. `WeaponDefinition.blade_protects` and `crossguard_protects` are read by PARRY and DEFLECTION classification alone (DEFENSE-ROLE-001), so a defender whose steel is declared non-protective parries nothing and is moved exactly as one whose steel protects. Tests: `CONTACT` (`test_a_parry_label_changes_no_physics`), `ATTACK` (`test_a_whiff_label_changes_no_physics`).

### PLANAR-BIND-001

Sword contact never receives an authored escape (review 12). The deterministic planar manifold MAY persist indefinitely while geometry and applied forces maintain it: equal geometry, equal forces and no useful tangent motion is equilibrium, not a defect. Sliding, winding-equivalent weapon rotation, footwork and disengagement arise only from ordinary root and weapon inputs acting through the existing contact constraints (RIGID-CONTACT-001, BLADE-FRICTION-001). There MUST be no bind timer, bind winner, separation push, out-of-plane release or contact-duration rule. BIND (persistent normal pressure on one primary constraint), SLIDE (persistent contact with tangent motion at or near the friction limit), TANGLE (both points of a steel pair held at once) and DISENGAGE (a persistent manifold reduced to no meaningful point) describe the manifold and MUST NOT change its physics. A one-plane sword model produces more binds and steel interceptions than unrestricted swordplay, by design: the escapes are root movement, blade sliding, θ rotation, heading reacquisition, changing pressure and geometry separating — never an abstract out-of-plane disengage, which is added only if measured play shows common contact that neither fighter's meaningful input can resolve, with long dead time and no decision. A jam is a defect only when the manifold does not answer changed physical input — a released or reversed force, a step, a retreat — or when contact identities churn, friction acts without normal impulse, an impossible normal appears, or the solver's work grows; duration alone is never the criterion. **The combat heading is stance-supported** (CONTACT-HEADING-001). Turning the heading under contact is the fighter's own voluntary act, through the turn motor. Every bind is a steel bind and always physically escapable (BLADE-ESCAPE-001); two crossguards never bind (STEEL-TOPOLOGY-001). Tests: `CONTACT-INTEGRITY` (`test_ordinary_separating_input_takes_a_bind_apart`: idle, each canonical bind stays bound; pressing stays legal and never tunnels; each bind's own separating input parts it with nothing held; no timing is a law). The rules-49 crossguard wedge witness is gone with the topology that made it (GUARD-CONTACT-001).

### CONTACT-HEADING-001

Contact never turns the heading (review 14). Weapon and contact impulses MAY alter root translation and the weapon coordinate's motion (`V`, `θ̇`); CombatHeading φ is stance-supported — driven by the bounded turn motor and supported through the feet, which take a contact's reaction torque about the root — and is never assigned angular impulse by weapon contact: no contact may change φ or φ̇. Contact changes later facing only indirectly, by changing the fighters' positions (so the target bearing τ), the weapon's momentum and the motor's committed drive (so the redirect debt, DIRECTIONAL-COMMIT-001) — the bearing and the authority the heading actuator must reacquire with. There is no outcome-vector → facing path and no "knock-away" direction derived from facing. A coupled `(φ, θ)` free-yaw model was tried and backed out (it took 28–44% of a clean cut's energy into a yaw the stance does not have). Tests: `CONTACT` (`test_contact_never_turns_the_heading_it_changes_what_the_heading_must_do`: the same clash leaves φ and φ̇ exactly as they were while changing `V` and `θ̇`; the next heading tick from the resolved clash turns faster than from the untouched one, through redirect debt alone).

### CONTACT-OUTCOME-001

One solve, one description (review 14). Every solved sword contact is described by a read-only `ContactOutcome` computed from the solve's own result — point count, the total normal and friction impulse, the impulse vector each sword received (`Σ Jn·n + Jt·t`), friction saturation, the rows' closing before and after, each fighter's `ΔV` and `Δθ̇`, which cuts the arrest law arrested, the attack's progress `θ̇·dir` before and after, and, for an attack's first opponent contact, whether the cut was on the line before the solve (its own remaining sweep reached the body, THREAT-001 unopposed, no new footwork). The solver MUST NOT read it, and nothing in the physics may. Every contact label is a reading of it and of what the attack then did — there is one contact mechanics (IMPACT-PHYSICS-001) and no second path for block, parry or deflection. The vocabulary: **PARRY** — protective steel arrested the cut (PARRY-001); **DEFLECTION** — protective steel redirected a cut on the line without arresting it and the attack ended having struck nothing (DEFLECTION-001); **BIND** (and a block, which is not an event: a parry that stays loaded) — protective contact persisting under pressure (PLANAR-BIND-001); a strike that carries through — contact too weak to change the outcome; **WHIFF** — no contact (WHIFF-001); **RIPOSTE** — an ordinary attack from the state a defense left (RIPOSTE-001). Every blade contact is also read as one of three (`ContactReading`, rules 53 onward, a description only). A contact that met a cut is read by what it did to the cut's progress `θ̇·dir` (carried as `PROGRESS_BEFORE` / `PROGRESS_AFTER`): **GLANCE** — the cut kept at least half its progress, redirected rather than stopped; else **CLASH** — it lost more, was stopped or turned back. A contact between blades neither (or both) of which was cutting is a **CLASH** if the solve changed either blade's θ̇ by at least its wielder's `control_speed` (so it changed what that blade can do next), else a **TOUCH**. Friction saturation does not separate them: steel on steel slides at its cone's limit in most first impacts. Touches are counted apart from meaningful contacts. The outcome's direction is the impulse the blades exchanged, never a direction built from either fighter's facing. The BLADE_CONTACT event carries the outcome's impulse vector, closing after the solve, friction saturation and each side's arrest (`ARRESTED_0/1`). Implementation: `game/src/domain/combat/contact_outcome.gd`, `contact_reading.gd`, `contact_resolver.gd`. Tests: `CONTACT` (`test_a_contact_reading_describes_the_solve` — a glance and a clash read from real solves, the reading changing nothing; `test_where_the_blade_is_met_decides_its_response_through_the_lever` — CONTACT-POINT-LEVER-001: the same cut met at the forte and the foible changes θ̇ by exactly `J·c/M_θ` each, more per N·s at the foible, no zone multiplier).

### DEFLECTION-001

A deflection is what a redirected attack did, never a mechanic (review 14). When an attack's **first** opponent contact is protective steel (DEFENSE-ROLE-001) that solved a positive normal impulse without arresting the cut (RIGID-CONTACT-002) while the cut was on the line (CONTACT-OUTCOME-001), the attack is marked (`WeaponState.deflection_pending`, reset at release, cleared by any body strike, hashed only so the label is emitted deterministically once). `DEFLECTION` MUST be emitted exactly when such an attack ends — its overswing comes to rest — still marked: it struck nothing. It is credited to the defender against the attacker. An arrested cut is a parry (or a held block), never a deflection; a cut that lands after meeting steel is neither; an attack that met no steel is a whiff. Because the reduced model sweeps θ about φ, a contact cannot bend a cut's path — it slows it, shoves the bodies, or stops it — so a deflection is a contact whose delay or shove let the remaining sweep miss, usually a defender moving off the line while their steel takes the cut. Nothing in the simulation or the CPU may read the label or the mark (lint `DEFLECTION-001`). Presentation reads it, subtly and derived: a glancing redirect's sparks lean the way the solved impulse shoved the cutting blade, and the label adds only a quiet metal tail — no HUD word, no flash, no gameplay effect (PRES-FEEDBACK `test_a_glancing_redirect_throws_its_sparks_the_way_the_blade_was_shoved`). Implementation: `game/src/domain/combat/contact_resolver.gd`, `weapon_system.gd`. Tests: `CONTACT-INTEGRITY` (`test_a_redirected_cut_that_strikes_nothing_is_a_deflection`, a production-input witness: the same cut lands with the guard seated away; with the guard in its path, positive impulse, not arrested, nothing struck → one DEFLECTION credited to the defender, no PARRY, no whiff; the same scene with non-protective steel moves identically on every tick and emits none).

### RIPOSTE-001

A riposte is an ordinary attack from the state a defense left, never an attack mode (review 14). There is no riposte state, window, input, torque, damage or commitment bonus; whether an answer works is the physics of the post-defense state — the defender's blade on a good line, the attacker's off line, reversing or bound — read, never awarded, as the defense's riposte advantage (`MARGIN`: attacker's time-to-threat minus the defender's). Telemetry and presentation MAY call a successful answer a riposte. Tests: `CONTACT` (`test_an_answer_after_a_parry_is_an_ordinary_attack`: the parry scene answered by the defender, once labelled and once with no label anywhere, moves identically on every tick and every contact's impulse and every hit's damage is identical — that parry won no tempo, so its answer meets steel, which is also the law: a parry does not mean the defender wins), `FULL-E2E` (`test_a_blade_catch_parries_a_cpu_attack_and_the_riposte_lands`: against the production Hard CPU, the human's blade arrests a CPU cut and the human's ordinary answer lands on the torso, through real input — no "first" is claimed).

### ATTACK-SIDE-001

Where a cut comes from is geometry, never a direction word (review 15). The side a cut sweeps from is the side its blade rests on: `swing_dir = −stable_side` (a dead zone keeps the previous side near the centre line), so consecutive cuts alternate. In the attacker's frame, with `forward = unit(φ)` and `ccw = perp_ccw(forward)`, the cut's **origin side** is `ccw · (−swing_dir)` and its **end side** `ccw · swing_dir`. From rest (θ = −guard_angle) a tap sweeps −45° → +45° and a full charge winds to −135° and sweeps to +45°, so every cut from rest ends at the opposite guard reference. A defender stepping toward the origin side steps **behind the blade**; toward the end side, **into the blade**. Physics tests and their docs MUST use origin side / end side / behind the blade / into the blade / radial inward and outward — never left or right, which do not survive a mirror or a camera — and every attack-geometry witness MUST state θ_start, swing_dir, the charge (so the arc and θ_end), the defender's bearing and start distance against strike reach, and whether its result came from the **line** (bearing changed), the **measure** (distance changed) or both. Implementation: `game/src/domain/combat/weapon_system.gd` (`swing_direction`); test vocabulary `game/tests/harness/cut_geometry.gd`. Tests: `ATTACK` (`test_the_side_of_the_sweep_decides_what_a_cut_meets`).

### LINE-CHANGE-001

Footwork beats a cut by changing the line, and the physics decides what that buys (review 13, amended in review 15; formerly WHIFF-LINE-001). Changing position relative to the physical side of a committed cut changes which geometry the attack reaches: moving behind the blade (toward its origin side, ATTACK-SIDE-001) MUST never be treated as equivalent to moving into it. The outcome may be a body miss with the cut meeting the defender's steel instead, a complete whiff, or a later advantage — physics decides which; inside strike reach a line change usually changes what the cut meets rather than making it whiff — stepping behind the blade often carries the defender's hands or steel into the sweep ahead of its torso; the hands are not a target (TORSO-CIRCLE-001), and the cut meets steel only where a blade, or a guard root from its blade side, lies in its path (rules 52: in the FULL-E2E origin-side trace the cutter's own crossguard meets the defender's blade and carries on to the torso). Three outcomes stay distinct: a **true whiff** (the attack ends with no meaningful opponent contact — `ATTACK_WHIFFED`, WHIFF-001, never broadened), a **body-line miss** (no body or hand hit because the line changed; it may still meet steel — a reading, not an event), and **defensive steel contact** (protective steel met; arrest, glance, slide, bind, deflection or separation follow from the one solve, CONTACT-OUTCOME-001). Footwork changes the line only through ordinary planar movement: it moves the target bearing τ; the attacker's CombatHeading φ starts turning toward it on the next tick (AUTHORITY-001) at the authority its redirect debt leaves (DIRECTIONAL-COMMIT-001), and the sword sweeps its real arc about the resulting φ (`world angle = φ + θ`, ATTACK-ARC-001). There is no duck, roll, dodge state, invulnerability, collision exemption, forced whiff or whiff recovery: a blade already crossing a body hits it. Capitalization is a possibility the resulting state may offer, never an entitlement. Tests: `MOTION-COMMIT` (FORCE-COMMIT, ROOT-COMMIT, INPUT-IMMEDIATE, mirrored; ATTACK-LINE-001 `test_a_sidestep_leaves_a_committed_line_behind_a_neutral_one`), `ATTACK` (`test_a_whiff_label_changes_no_physics`; `test_the_side_of_the_sweep_decides_what_a_cut_meets`: inside reach, equal measure, no step → torso, behind the blade → the grip, not the torso, into the blade → torso, mirrored), `DAMAGE` (THREAT-COMMIT-001 `test_on_an_empty_line_the_threat_estimate_is_the_strike_the_duel_lands`), `LINE-GAME` (`test_the_line_changes_what_a_tap_meets`; `test_behind_the_blade_shields_the_torso_more_than_into_it`: over a grid of measures and read timings, behind the blade takes the torso out of the tap's first contact more often than into it — an ordering, never rates), `FULL-E2E` (`test_an_origin_side_step_here_meets_the_cuts_crossguard_first`, `test_an_end_side_step_here_is_struck_on_the_torso` — scenario traces through real input, not rules about every step). Whether the line change can be capitalized on is LINE-CHANGE-CAPITALIZATION-001, OPEN.

### KNIFE-EDGE-LINE-001

Riposte does not require an attack to make no contact for footwork to beat it (review 15). A fighter wins an exchange by changing the physical line, measure or weapon relationship so that the resulting state gives them superior access to meaningful hurt geometry. A line change may cause a whiff, a glancing steel contact, a bind, a parry, a deflection or a later positional advantage — all outcomes of the same deterministic physics. The game MUST reward the player who recognizes the resulting advantage and physically moves to capitalize on it; no event label grants that advantage and none guarantees a counter: the swords, bodies, momentum, contact geometry and the movement that follows decide whether the opening exists. Tests: `LINE-GAME`, `FULL-E2E` (as LINE-CHANGE-001), `CONTACT` (ACTIVE-DEFLECTION-001 `test_an_active_beat_displaces_this_cut_more_than_a_resting_guard`: in one canonical scene an active beat solves more Δθ̇ and a later attacker threat than a resting guard, under the same PARRY label — a relationship witness, never a monotonic law in guard speed or |Δθ̇|). Rules 50 (blade-only steel) leaves its capitalization half unproven: LINE-CHANGE-CAPITALIZATION-001.

### LINE-CHANGE-CAPITALIZATION-001

**OPEN — a deferred combat-design acceptance criterion, not a failing topology invariant.** A deliberate line change must create a reproducible, physically explainable positional or defensive advantage against a relevant attack. The advantage must arise from authoritative blade contact, movement, timing, reach, or resulting weapon state — not crossguard/handle rigid collision. The advantaged fighter must have a meaningful opportunity to capitalize through an ordinary attack, without a scripted riposte bonus or forced outcome. It does not require the defender to always land first, and no scripted advantage may substitute for physical positioning; a successful parry test does not satisfy it. Removing crossguard and handle collision (rules 50) is not a verdict on it either way, nor is restoring the crossguard's protective side (rules 52). Acceptance needs reproducible real-input journeys: one in which a line change creates the advantage and the fighter capitalizes through an ordinary attack while the opponent keeps counterplay (B13, post-clash reposition into capitalization), and one in which weapon position and measure alone hold a cut off the body. The current-pass tests (`LINE-GAME`, `ATTACK`, the `FULL-E2E` line journeys) assert only what the line does now.

### AUTHORITY-001

Input is immediate; authority is physical. Every command takes effect on the tick it arrives: commitment, injury and momentum MUST decide how quickly a fighter can comply — how much force, torque and turn rate is available to change what their body and sword are already doing — and MUST NOT reject, delay, queue or drop an input. A fighter may always ask to turn, back up or redirect; physics answers how fast. No state may leave a fighter unable to act for longer than physics holds them (a pressed cut that never ends is such a state, RIGID-CONTACT-002). The attack buffer (`buffer_ticks`) is a convenience that admits a press made just before the weapon is controllable; it is not a delay.

### COMBAT-008

First-contact attribution. Every death MUST record the sub-tick instant the lethal blow arrived (`FighterState.lethal_fraction`, set only through `WeaponSystem.kill` from the contact's time of impact), and `StateInvariants` MUST reject a dead fighter without one, a living fighter with one, and a value outside `[0, 1]`. When both fighters are dead at round-end evaluation, the round MUST go to whoever fell later (`REASON_TRADE_FIRST_CONTACT`); only an exactly equal instant is a draw (`REASON_DOUBLE_KILL`). Attribution MUST NOT consult slot number, attacker or defender role, remaining health, iteration order, or randomness.

### COMBAT-014

Chronological terminal precedence. A fighter leaves the round at their **terminal instant**: the earlier of the instant a lethal blow arrived (`lethal_fraction`) and the instant they lost support at the platform edge (`support_lost_fraction`, set with every `RING_OUT` from the crossing's time of impact; hashed, reset per round, invariant-checked). `FighterState.terminal_kind()` / `terminal_time()` are the one home of that reading. A fighter carried over the edge by a contact's impulse loses support where their centre actually crossed in the carried remainder of the tick (`DuelSimulation.remainder_crossing`), never at the contact's own time of impact. A fighter whose lethal blow and lost footing fall at exactly the same instant was killed: the blade arrived no later than the edge did. When both fighters have a terminal instant in the same tick, the round MUST go to whoever left later; only an exactly equal instant is a draw. The round's reason is the loser's terminal kind (`RING_OUT` for a lost footing, otherwise the kill reasons of COMBAT-008). A fighter who crossed the edge and then landed a kill later in the same tick has already left the round; a dead fighter never wins by an opponent's later ring-out. Precedence MUST NOT consult event order, slot number, role, health, or randomness. Both instants come from the solver: the lethal fraction from the contact's time of impact, the lost footing from the edge crossing of the motion that caused it — for a fighter carried over the edge by a contact, the crossing within the carried remainder after that contact, never the contact's own time. A fighter's own exact tie between a lethal blow and a lost footing reads as the kill (the blade arrived no later than the edge did).

### COMBAT-009

Swing semantics are descriptions, never decisions. Named readings over authoritative state — swing potential, swing progress, contact quality, exposure as a fraction, and a strike grade — MUST be derived from the physics and MUST NOT participate in it. Nothing in the simulation may read one back, and no presentation code may recompute a combat formula: a value not carried on `PresentationSnapshot` or a `DuelEvent` payload MUST be done without rather than invented.

Swing potential MUST be a bounded reading of how dangerous the current part of the current swing is, taken from the blade's **actual** tip speed and quadratic in it (severity goes as `v²`), gated to zero whenever the blade is not carrying a strike. A quantity already carried by another MUST NOT be multiplied in again: charge and arc are expressed through the speed the motor achieved, so counting them a second time would make the same physical blade speed mean two different things. The dangerous part of an arc therefore emerges from the acceleration curve rather than being authored, and moves between swings.

Swing progress MUST be measured in physical travel along the commanded arc, never in elapsed ticks, so a blade stopped by another blade stops progressing.

Potential MUST NOT be prediction. Convergence exists only at contact, so no pre-contact surface may promise what a strike would do; before contact an interface may show the attacker's own potential and let vulnerability read from the target's own physical state. Grades MUST describe the resolved result and MUST NOT choose damage, and there MUST be no dice roll.

### COMBAT-010

Emergent point strike. A point strike is a **contact classification**, never an input, attack state, animation, or special move. There MUST NOT be a stab button, a `STAB_ATTACK` phase, or a thrust damage multiplier. A point strike exists only when the physical state produces one: the sword's point enters the opponent first, along a sufficiently axial trajectory, without the opponent's weapon intercepting it. Classification is purely geometric — it describes how the contact arose and MUST NOT be gated on severity. A weak aligned tip contact is a weak POKE, not a GRAZE. GRAZE means the contact geometry is glancing or tangential, not merely low-energy.

POINT_STRIKE is the parent classification. Two sub-kinds describe how the contact arose:

- **POKE**: point-first body contact. Classified when: tip-region contact (`blade_fraction >= tip_region_start`), sufficient thrust alignment, sufficient incidence quality, and the weapon supports thrusts. No severity threshold — a slow aligned tip contact is a weak POKE, not a GRAZE. A POKE MAY be lethal if physical severity reaches the lethal threshold (COMBAT-011).
- **THRUST**: point-first body contact with forward burst and sword-to-motion alignment. Classified when: all POKE criteria AND the attacker is in an active burst with burst direction aligned to the sword axis. A THRUST is an **instant kill** regardless of HP or severity. This is an explicit game rule, not a physics calculation. Defense is handled entirely by the chronological TOI solver: a blade contact that precedes the body contact changes the weapon trajectory, and the body contact is re-evaluated from the post-deflection state. If the thrust classification no longer qualifies, the defense succeeded. If it still qualifies, the physics says the point drove through despite the deflection.

A point-strike candidate MUST satisfy all of: (1) tip-region body contact (`blade_fraction >= tip_region_start`), (2) sufficient thrust alignment (`A = max(0, v_axial) / (|v_rel| + ε)`), (3) sufficient incidence quality (`G = max(0, -â · n̂)`), and (4) weapon supports thrust. Severity MUST NOT gate classification — it affects damage, not what kind of contact occurred. The chronological TOI contact loop (COMBAT-007) MUST evaluate point-strike candidates after blade contacts that precede them, because a parry at `t = 0.17` changes whether a thrust at `t = 0.28` exists at all. One body contact gets exactly one classification (`SLASH`, `POKE`, `THRUST`, or `GRAZE`); there MUST NOT be separate detectors that independently apply both slash damage and a thrust kill for the same contact.

**GRAZE** is a geometric classification: the contact quality (blade efficiency × edge alignment) is below the graze threshold, meaning the blade's edge did not lead the contact — it slid or scraped. A low-energy well-aligned cut is a weak SLASH, not a GRAZE. A low-energy well-aligned tip contact is a weak POKE, not a GRAZE. Classification separates geometry from severity.

Defense is determined entirely by the chronological TOI solver, not by persisted flags or episode tracking. If a blade↔blade contact at `t = 0.17` changes the weapon state and a recomputed thrust candidate at `t = 0.23` no longer qualifies, the defense succeeded — the physics redirected the weapon. If the thrust still qualifies after the deflection, the physics says the point drove through despite the interception attempt. An exact TOI tie between blade defense and body contact MUST resolve as defense-wins (COMBAT-002). There MUST NOT be a `target.is_unprotected` flag, an `attack_episode_id`, or any other persisted defense marker — the chronological loop itself decides.

Fighter translation, fighter rotation, weapon rotation, and target motion all contribute to tip velocity through shared contact-point kinematics (PHYS-007). A stationary sword on an advancing fighter, a motionless fighter whose opponent dashes onto the point, a post-deflection alignment, and a combined rotational-translational entry are all equally valid point-strike sources. A point strike MUST NOT require the fighter to be facing the opponent perfectly — it requires the sword point's trajectory to intersect the opponent. Facing affects structural coupling, control, and exposure; it MUST NOT veto a physically valid point contact. `WeaponDefinition.supports_thrust` controls whether a weapon can produce a lethal point strike; `tip_region_start` and `thrust_efficiency` are per-weapon content.

### COMBAT-011

Point-strike severity and lethality. POKE and THRUST share one physical severity model for the base evaluation. Severity is computed from axial relative velocity, effective mass, incidence quality, and structural coupling through the existing `ImpactModel`. Lethality diverges by classification:

- **POKE**: severity below the lethal threshold produces ordinary point damage from the compressive damage curve. Severity at or above the lethal threshold produces an instant kill. A POKE MAY be lethal if the physical severity is high enough (e.g. opponent dashes onto the point); a POKE at walking speeds is usually survivable.
- **THRUST**: an instant kill. No additional damage roll, no HP check, no severity threshold. The forward burst velocity and sword alignment are the criteria. The chronological TOI solver handles defense: a blade contact that precedes the body contact physically redirects the weapon, and the thrust is re-evaluated from the post-deflection trajectory. A thrust that still qualifies after a deflection is physically valid and lands.

There MUST NOT be a `STAB_MULTIPLIER` or a damage bypass that ignores physics for the base severity evaluation. The THRUST instant-kill rule is an explicit game-design decision layered on top of the physics, not a physics shortcut. Lethal-contact TOI ordering (COMBAT-008) remains the authoritative simultaneous-kill rule.

### COMBAT-012

Body-body impulse. Fighter-body contacts are reciprocal physical collisions. At contact TOI, the solver applies equal-and-opposite normal impulses derived from relative contact velocity, fighter masses, and authored restitution. New contacts (first tick) use authored restitution; persistent contacts (subsequent ticks) use zero-restitution velocity constraint. The constraint prevents interpenetration without injecting energy; equal and opposite motor forces cancel exactly with no drift. Dash, walking, retreat, and counter-charge influence the result only through physical state; no movement mode receives an arbitrary body-collision multiplier. Collision-induced velocity persists into the remainder of the chronological simulation and MAY affect later weapon, body, or arena contacts. Input locomotion accelerates toward desired motion and MUST NOT erase the resulting impulse on the next tick. A stationary fighter MUST NOT be treated as infinite mass unless an explicit bracing mechanic is authored. Body-body collision does not directly reduce HP; the sword remains the lethal mechanism. Stamina still drains from motor exertion during stalemate. Running-into-point parity: for equal masses and geometries, a fighter walking point-first at +4 m/s into a stationary target and a stationary sword with a target walking into the point at −4 m/s MUST produce approximately equal physical quality, damage, pushback, and lethality result — relative collision velocity is what matters, not which participant supplied the motion.

### COMBAT-013

Chronological defense resolution. Defense against a thrust is determined entirely by the chronological TOI contact loop (COMBAT-007), not by persisted state on the weapon. When a blade↔blade contact resolves before a weapon→body contact in the same tick, the blade impulse changes the weapon trajectory and the body contact is re-evaluated from the post-deflection state. If the thrust classification no longer qualifies, the defense succeeded through physics. If the thrust still qualifies after the deflection, the point drove through and the thrust lands. There MUST NOT be `attack_episode_id`, `intercepted_episode_id`, or any other per-episode defense tracking in authoritative combat state. The `DamageModel` MUST NOT accept a `defended` parameter — lethality is determined by classification alone.

## Stamina (STAMINA)

### FALLEN-BODY-001

A killed body is a body (rules 39 onward). The kill begins a `FallenBodyState` (hashed, reset per round): thrown along the killing impulse's direction, collapsing for `fallen_settle_ticks_cut` or `fallen_settle_ticks_point` (a run-through holds the body on the blade first), then lying as a capsule ±`lying_half_length` along its yaw, radius `lying_radius` — the fighter's own body geometry (`FighterDefinition`), never a rule constant — **through the fighter's own position, which is its centre of mass** — lying down moves nothing. While its round is decided (`_step_decided`) a body has its fighter's real mass and no motor or bracing: it slides against Coulomb ground friction (deceleration `μ·g`) and its spin decays by that friction's torque over a uniform rod (`α = 1.5·μ·g / h`, derived); a living fighter's push circle meeting it is one inelastic normal impulse at the capsule's closest point through `k = 1/m_a + 1/m_b + (r × n)² / I` (`I = m·(2h)²/12`, derived), with the torque `Δω = −J·(r × n)/I` — so a push through its middle moves it straight and a push near an end turns it — and overlap is then cleared along the normal by inverse mass. Its centre of mass crossing the platform edge, swept, is the post-round corpse fall: `over_edge`, one `POST_ROUND_CORPSE_FALL` event at the swept fraction, and nothing else: the body MUST NOT be marked `is_falling` (a living fighter's lost footing — reusing it would re-read how the round ended), and the score, `round_winner` and `end_reason` MUST NOT change. Only the dead are bodies (`StateInvariants.FALLEN_ALIVE`); a body's yaw and spin are finite. Presentation reads it through the snapshot (`body_lying`, `body_yaw`, `body_spin`, `body_over_edge`) and never writes it back. Implementation: `game/src/domain/state/fallen_body_state.gd`, `game/src/domain/combat/fallen_body_system.gd`. Tests: `FALLEN` (thrown along the killing impulse; pushed without overlap; an off-centre push turns it and mirrors; slides farther than a braced fighter, to where `μ·g` stops it; carried over the edge with the result and terminal cause untouched; hashed; only the dead are bodies), `FUZZ`, `REPLAY`.

### STAMINA-003

Superseded by STAMINA-004 (rules 53). Rules 47–52: there is no fatigue resource (state/replay schema change; rules version unchanged at 47, tick order 14). Stamina, its model, the per-tick exertion ledger that only fed it (motor work and utilization in `FighterTickScratch`), the contact shock and its event key are removed from authoritative state, the hash, the invariants and the content. STAMINA-001 (motor-based exertion) and STAMINA-002 (a deprecated resource with no consumer) are retired with it. Damage alone drives capability (CONDITION-001). A fatigue mechanic would be a new, explicit design decision with its own invariant. Its tests were replaced by STAMINA-004's.

### STAMINA-004

Stamina is a physical resource (rules 53 onward, layout 7; its settle step landed at tick order 15). The current sequence is tick order 16: impact-authority recovery runs after contact upkeep and before this settle. Stamina does not read authority, and authority does not read stamina. Each fighter carries `FighterState.stamina` ∈ `[0, 1]`, hashed, set to 1 when every round is reset (`DuelSetup.reset_round`) — so a round, a new set and a rematch (a fresh session) all start fresh, and fatigue never carries between rounds. **Tick order.** (1) Stamina `s` is read at the start of the tick. (2) `ConditionModel.compute` freezes this tick's capability from `s` and health. (3) Commands are canonicalized against `s`: a dash starts only if `s ≥ stamina_dash_cost` — a refused dash is dropped, never buffered, and costs nothing — and a held charge earns wind-back credit only while `s > 0` (charge stops accumulating; the attack is never released for the player, and the player's release fires with the charge already earned). (4) The authoritative movement, heading, weapon and contact simulation runs, each motor's own work accumulating in `FighterTickScratch`. (5) Stamina settles once: `s ← clamp(s − e − d + r, 0, 1)`, where `d = stamina_dash_cost` on the tick a dash actually starts (once per dash), `r = stamina_recovery_rate·dt` when this tick's exertion is at most `stamina_recovery_effort_ceiling·dt` (else 0), and the exertion `e = Σ_c k_c·(W⁺_c + β·W⁻_c) / R_c` over the movement, heading and weapon motors: `W⁺` / `W⁻` the motor's driving / braking work over the tick (force or torque times the mid-step velocity, measured before any contact, so a contact impulse is never exertion), `β = stamina_brake_share`, `k_c` the `stamina_{move,turn,swing}_cost` per reference energy `R_c` (½·m·v_max² for footwork, ½·I_body·ω_max² for the heading, ½·I_weapon(guard)·ω_swing(full charge)² for the blade — derived from the fighter and weapon, never authored). (6) The snapshot projects the settled `s`. So a tick's actuator capability comes from its starting stamina, and the settled value decides the next tick's: a dash's cost never weakens its own start tick. Stamina settles only while a round is live; the post-round phase reads it and never changes it, and a dead body's is frozen. **Capability.** Fatigue scales voluntary actuation force: `fatigue = Fs + (1 − Fs)·s` (`Fs = stamina_force_floor`) and `damage_force = F + (1 − F)·h` are stored separately, and `force_scale = damage_force · fatigue` (CONDITION-001). Locomotion, braking, burst, heading torque, and the weapon's swing, brake, wind-back and stagger hold read `force_scale`. The neutral hold and the guard return read `damage_force` only (`base_drive`); fatigue is applied once, at that boundary, and is never divided back out. The product never falls below `condition_force_floor × stamina_force_floor ≥ 0.5` (validated), so a wounded, spent fighter still acts. Because brake force carries fatigue, a tired blade loses less speed on a braking tick. A constant-deceleration reading of that tick is a longer stop; the soft zone, the guard limit, and a phase change can end the coast first, so that reading is not a measured stopping trajectory. Low-stamina and high-stamina weapon trajectories are not the same. Stamina MUST NOT change speed ceilings, the tracking cap, command timing, the guard-return target, control availability, mass, inertia, geometry, friction or perception; MUST NOT rescale existing momentum (the drain tick is bit-identical in velocity, θ̇ and φ̇, PHYS-003); and MUST NOT multiply damage — a tired cut does less only because its actuator drove the blade less hard. Motor authority and its recovery (WEAPON-AUTHORITY-001) are not in this rules version; when they exist they do not take fatigue. **Three separate properties**, each tested on its own: (a) continuous fatigue scales the voluntary forces named above, including brake force, and does not scale the guard return; (b) the dash and charge gates are the only discrete effects, and they read start-of-tick stamina; (c) speed ceilings, tracking, input timing and the guard-return target stay on their own rules. **Fairness.** The same law applies to every fighter from their own actuators; the CPU reads its own stamina and the opponent's from the same state a human's HUD shows (CPU-001), and no difficulty changes any stamina number. Implementation: `game/src/domain/combat/stamina_model.gd`, `condition_model.gd`, `game/src/domain/match/duel_simulation.gd`, `movement_system.gd`, `weapon_system.gd`. Tests: `STAMINA`, `CONDITION`, `CPU`, `PRES-SNAPSHOT`, `REPLAY`.

### CONDITION-001

Damage-driven physical capability (rules 45 onward). Damage does not change the laws of physics; it changes how much voluntary force, speed and tracking the fighter can produce within them. With `h = clamp(health / max_health, 0, 1)`, one immutable `ConditionState` per fighter MUST be computed exactly once at the start of every tick (`ConditionModel.compute`, stored in that fighter's `FighterTickScratch`), before any motor runs, holding `force_scale = F + (1 − F)·h`, `speed_scale = S + (1 − S)·h` and `tracking_scale = T + (1 − T)·h` with authored floors `F = 0.70`, `S = 0.85`, `T = 0.80` (`CombatTuning.condition_*_floor`, each in `[0.5, 1]` so the healthy identity is exact). All three are strictly linear in damage, exactly 1 at full health, and reach their floors only at zero health (0.85 / 0.925 / 0.90 at half health). `force_scale` MUST multiply every voluntary force and torque — locomotion, braking, burst force, heading turn torque, and the weapon's swing, brake, wind-back and hold torque; `speed_scale` every voluntary target-speed limit — top footwork speed, burst speeds, the swing's target speeds and the wind-back speed; `tracking_scale` the heading-rate cap `turn_speed_max`. Condition MUST NOT rescale existing momentum (PHYS-003): on the injury tick velocity, `θ̇` and `φ̇` are bit-identical and only future actuator output changes. It MUST NOT change mass, inertia, geometry, collision, reach, friction, restitution, input buffering, perception, reaction delay or decision cadence, and every command still takes effect on the tick it arrives. Fatigue (STAMINA-004, rules 53) composes with it on force only: `force_scale` is the damage term times the fatigue term; speed and tracking stay damage-only. `CommitmentModel` composes with it unchanged: there is no extra injured-commitment penalty, so injury is never counted twice. The same law applies to every fighter from their own healthy actuators. Readers outside the tick (threat, CPU, snapshot) compute it with the same model and never rederive it; the player HUD shows the condition band (and, from rules 53, stamina), and the debug overlay shows the three scales. A dead body has no voluntary motor and takes the identity. Implementation: `game/src/domain/combat/condition_model.gd`, `condition_state.gd`, `game/src/domain/match/duel_simulation.gd`. Tests: `CONDITION`.

## CPU (CPU)

### CPU-001

Fair CPU. The CPU MUST emit the same `PlayerCommand` a human would and obey the same rules. It feels its own body now — every reading a decision takes — threat times, route readings, the opponent's point aimed at it — uses its current self, never a delayed copy (`CpuObservation.feel_self`, CPU `test_the_cpu_feels_itself_now_and_sees_the_opponent_late`) — and perceives its opponent only through a reaction-delay memory extrapolated by its anticipation skill; it MUST NOT read hidden state or future commands. Difficulty is `CpuProfile` data (reaction, cadence, anticipation, discipline), never stat or rule changes. Variety comes from `SeededRng`, so CPU play is reproducible per seed. When its own stamina is below one dash's cost and the opponent owes nothing — not open, not an intercept, no tempo window — it does not start a probe or a charge. A capitalize, an intercept, and a tempo window are still taken, and a taken opening MUST progress to an attack press, start, and release; the capitalize intent alone is not that attack. The dash cost is the guarded-probe gate on purpose, so attack selection and dash affordability share one bar. There is no second stamina threshold and no per-difficulty stamina cost (`CPU` `test_a_tired_cpu_holds_a_guarded_line_and_still_punishes_an_opening`). The held-out grade shows difficulty ordering. It does not show that the gate reduced probes; that effect is read on `CpuLadder.AUDIT_SEEDS` and is not a grade.

### AI-FAIRNESS-001

CPU profiles differ only in information processing, reaction and decision behaviour, and policy. They MUST NOT receive different physical laws or hidden state unavailable to the player. Footwork is expressed in the CPU's own combat frame like a human's (MOVEMENT-FRAME-001), so it gets no footwork a player cannot. How the CPU computes is not part of its fairness and MUST NOT change a decision: the costly readings of an observation are taken only when a decision reads it, from the bodies as they stood at that observation's tick, bit-identical to taking them every tick. Tuning reads only the tuning corpus (`CpuLadder.AUDIT_SEEDS`, `pnpm test:balance:audit`); the held-out ladder is run once after a tuning pass, and its bar MUST NOT be lowered. The rules-53 grade on `ACCEPTANCE_SEEDS` (101–108) is consumed. The graded set after the tired-attack policy is `ACCEPTANCE_SEEDS_V2` (301–308). That grade is difficulty ordering. It is not a measurement of the tired-attack gate, and those seeds are not rerun to tune one. Implementation: `game/src/application/cpu/cpu_observation.gd` (`record`, `resolve`), `cpu_controller.gd`, `cpu_profile.gd`. CPU-MIRROR-001: the same profile in slot 0 of a duel and in slot 1 of its point reflection issues the same frame-relative commands and the same decisions; only the starting state is built by hand, and each slot's random stream — its own by design — is pinned by the test's profile. Ladder statistics are therefore read paired and side-swapped. Tests: `CPU` (`test_a_recorded_observation_resolves_to_what_was_seen_then`, `test_the_cpu_plays_the_mirrored_duel_from_the_other_slot_identically`, the existing fairness laws), `CPU-BALANCE` (the three corpora are disjoint), `CPU-ACCEPT`.

### CPU-002

Physical parity. For identical `FighterDefinition` and `WeaponDefinition`, CPU difficulty MUST NOT modify any physical quantity: fighter mass, body inertia, movement force, braking force, turn torque, weapon mass, weapon inertia, weapon torque, charge rate, reach, damage, exposure, collision response, burst magnitude, movement cap, or stagger recovery. A harder opponent MUST be the same body and the same sword in better hands.

Difficulty MUST NOT reach `DuelRules`. `MatchConfig` MUST resolve identical rules content for every difficulty, so an identical command stream replayed under each difficulty produces an identical state hash. A difficulty that changed the physics could not satisfy that.

### CPU-003

CPU acceptance testing. Combat changes may require CPU profile retuning, but MUST NEVER weaken a tactical acceptance criterion merely to restore green tests. The acceptance-seed corpus is fixed and MUST NOT be inspected while tuning. If combat physics changes cause Hard to lose its decisive margin over Easy, the correct response is to fix the underlying physics or retune the profiles — not to lower the decisive threshold, shrink the seed corpus, or add variance tolerance. Acceptance tests that can be weakened into passing are not tests.

Information parity. CPU decisions about the opponent MUST read only delayed, perceived state. The CPU MUST NOT read a future or in-flight command, a private input edge before it manifests physically, hidden RNG state, or any authoritative value a watching human could not infer from the opponent's body. Prediction MUST extrapolate observation (`last seen position + last seen velocity × horizon`) and MUST NOT consult truth. Its own body it may feel immediately, which is proprioception rather than privilege.

A CPU MUST NOT receive a pre-contact strike quality (COMBAT-009): before contact nobody knows what a hit would do, so an expected outcome MUST be a coarse reading of perceived geometry rather than a call into the damage resolver.

### CPU-004

Difficulty is decision quality. The axes along which profiles MAY differ are perception delay, decision cadence, prediction horizon, tactical assessment weighting, planning depth, opponent-tendency memory, rhythm variation, and action-selection error rate. Every difficulty MUST share one tactical evaluator and one intent generator; there MUST NOT be a per-difficulty behaviour tree, and there MUST NOT be a scripted technique call (`perform_pull_counter()`) — tactics are plans over the same primitives a thumb drives.

Lower difficulties MUST express error by choosing a worse _plausible_ option, never by acting at random. A profile MUST NOT be made stronger by lowering reaction delay below a human-achievable latency; a strictly faster reader is not a better fencer.

### CPU-005

Behavioural support. A claimed tactical proficiency MUST declare a minimum count of eligible situations. Below it the verdict MUST be `INSUFFICIENT_SUPPORT`, which MUST NOT be reported as a pass — a 100% success rate over three opportunities is not evidence.

Where a test grades an emergent outcome rather than an authored value, calibration seeds and acceptance seeds MUST be disjoint, and the acceptance corpus MUST NOT be inspected while tuning. A claim whose effect size is too small for the affordable sample MUST be measured by a diagnostic tool rather than gated; raising the sample until a gate passes re-creates the overfitting the split prevents.

### CPU-006

Edge safety. `EdgeSafetyEvaluator` is a pure stateless predictor that evaluates candidate commands against `platform_radius` using real motor laws (`locomotion_force/mass`, `burst_force/mass`, scaled by the CPU's own condition, CONDITION-001). The safety filter is identical across all difficulties (Layer A); difficulty changes tactical judgment only (Layer B via `TacticalAssessment` edge features and `CpuProfile.edge_exploit_weight`). Walk safety activates only when the fighter is within `push_radius` of the platform edge; further out, edge steering handles avoidance. Burst safety is the hard filter: a burst that would cross the platform MUST be suppressed. If no safe candidate exists, the CPU MUST choose the candidate with maximum `min_clearance`. The CPU MUST remain fully vulnerable to forced ring-outs (opponent impulse, body collision, unavoidable momentum).

### CPU-007

Body-pressure awareness from solved contact physics. The CPU reads push pressure from `BodyContactState.last_constraint_impulse` — the impulse the contact solver actually applied — not from the opponent's hidden motor intent or input commands. Push pressure is `J_constraint / dt`, signed so positive means the CPU is being pushed toward its own edge. All difficulties use the existing delayed perception model; Hard improves prediction quality (when to escape, which direction is safe), not reaction latency. The push-pressure survival response activates only in the outer rim of the platform where ring-out is a real threat, and does not dominate center-arena spacing decisions. `CpuDecisionTrace` captures `body_contact_active`, `push_pressure`, `being_displaced`, and `time_to_support_loss` for analytics and diagnostic replay.

### CPU-008

Capitalization is a CPU intent from physical initiative, never a combat mechanic (review 15). `CpuController`'s CapitalizeIntent changes commands only — nothing in `FighterState`, `DuelRules`, contact, damage, recovery or replay — and never reads a WHIFF, PARRY or DEFLECTION label, so one test serves a miss, a parry, a deflection, a clash, an overswing or a stumble. Each decision: (1) the CPU reads its own body as it is now and the opponent through its delay (CPU-001); (2) the direct route — closing straight at the perceived opponent, its strike pressed now — is read with the steel-aware predictor (`ThreatContinuation.route`, the opponent's sword under its own known law for its perceived phase — a held charge keeps winding — its heading tracking automatically, its body at its current velocity, never its future input; its blade swept between the prediction ticks as the duel sweeps it, so a fast point cannot skip it); (3) if that reaches the torso circle before any steel, the route is straight in; (4) if steel is in the way, the detour beside the opponent on the side of its line away from its sword (`preferred clear side`, from the sword's perceived angle, never from facing alone) is read the same way; (5) a route that starts with the swords already bound is no answer — the predictor does not carry the bind's constraint (THREAT-AGREEMENT-AUDIT found its clear readings from a bind mostly wrong) — so a bind is left to the ordinary utilities and the physics. The intent MUST start only when the opponent is open (overswinging, recovering, staggered, or threatening later), a route is clear, it is **feasible** — arrival along that route before the opponent's own threat read in the same imagined world (`opponent_threat_reading`: one `ThreatContinuation`, both swords swept, each body at its current velocity; a strike of theirs my steel would stop first is no threat), the same test for every profile — **confident** — sooner by the profile's `capitalize_margin` (policy data: Easy wide, Hard tight; never applied to feasibility) — and **safe** (CPU-006). It is persistence of a spatial solution, not a script: every decision re-reads the route (the lateral detour only while steel blocks the direct line; once clear it closes straight), re-checks feasibility and safety, and drops the intent the moment any fails; a safety cap (`CAPITALIZE_LIMIT_TICKS`) only guards stale intent. It dashes only when the gap needs closing and strikes with an ordinary tap. A dash is always a decision: the CPU feels its own gesture state and eases a footwork step that would complete a double tap it did not choose, within the range a human stick gives. Implementation: `game/src/application/cpu/cpu_controller.gd`, `cpu_observation.gd` (`feel_self`, `route_reading`), `game/src/domain/combat/initiative_model.gd` (`motion`, `steel`). Tests: `CPU` (decision-function laws on held scenes: an open line is taken straight in; steel in the direct line is gone around on the side away from it; a route only into steel is declined; a route that starts in a bind is not taken as clear; a guarded opponent at rest is no opening; the decisions mirror exactly; integration in live play: `test_the_capitalize_intent_lives_in_real_play` — chosen, converts, abandoned when the opening closes, never started mid-strike; `test_the_cpu_never_types_a_dash_it_did_not_decide_on`), `ATTACK` (`test_the_threat_estimate_sees_the_steel_in_the_way`), `LINE-GAME` (HUMAN-CAPITALIZE-001). The predictor's agreement with real rollouts is measured, not gated, by `game/tools/interaction_audit.gd -- agreement`.

### CPU-009

The CPU's range preference is profile data, honoured with its own body (rules 52). Preferred distances (`CpuProfile.tap_range`, `engage_range`, `charge_range`) are authored in metres at the reference reach (`CpuController.calibration_reach`) and scale with the CPU's own strike reach. An approach closes to `CpuController.preferred_range` — just past tap range when the CPU can strike, its engage range otherwise — judged where the bodies will be once the approach can stop. A CPU free to act that is inside its `smothered_line` steps back out of it before it attacks; a forced state (stagger, a fall) is never asked to move. A forward dash spends its whole travel at once (`dash_travel`: the burst and its glide to rest at full condition), so it is taken only when that travel still stops outside the range the approach closes to — never a dash into the CPU's own smothered measure. These are decisions over the same commands a human has (CPU-001); nothing physical changes and no profile value moved. Whether the CPU stays in sword-fighting range through whole exchanges is OPEN. On the final rules 52 the Hard–Medium ladder (seeds 301–320) spends 19% of live time inside 1 m (28% on the first rules-52 candidates; retuning `tap_range` to 1.35–1.65 m there measured 35–52%). Of each CPU's time inside 1 m, about 70% is forced (staggered 30–33%; steel or a sword on a torso holding the bodies 37–42%), 4–5% is its own strike, and about 24% it is free to act — 12–13% not opening the distance (missed step-outs). A live sword-on-torso spell lasts a median 8 ticks, its 90th percentile 33 and its longest 202; the longest traced are a mutual stagger, then contact kept loaded by one fighter driving or pursuing the other — never a stale row or a trap (an earlier report of 246- and 1787-tick pins counted swords left in fallen bodies through round ends). A second after a hit or a clash the distance has not changed (median 0.00 m, +0.05 m). Implementation: `game/src/application/cpu/cpu_controller.gd`. Tests: `CPU` (`test_a_dash_in_never_carries_the_cpu_inside_its_own_range` — with the dash made certain, from far enough it still dashes and stops outside its smothered line, from where one dash would carry it inside it walks in instead; `test_a_smothered_cpu_that_can_act_steps_back_out_before_it_attacks`).

### ARENA-001

Platform geometry. The arena has one authoritative physical dimension: `DuelRules.platform_radius`. `edge_warning_inset` still derives a radius from `platform_radius`. The product Arena does not paint that ring. `edge_policy` selects what crossing that radius means. `EDGE_OPEN` is the default and the meaning of rules version 58: body separation uses pure inverse-mass overlap resolution with no arena-wall clamping, a fighter whose center-of-mass crosses `platform_radius` loses support (`is_falling = true`), and post-impulse support loss marks any living non-falling fighter past `platform_radius` falling and emits `RING_OUT`. Every physical cause — walk, dash, knockback, body push, stagger drift — MAY produce a ring-out through normal trajectory evaluation. `EDGE_CLOSED` holds a standing centre at `platform_radius` minus `push_radius`, and a fallen centre at `platform_radius` minus the larger of `push_radius` and `lying_half_length`. Outward radial velocity is removed only on that support circle, in the same tick the centre is held there. Inside the circle the movement velocity is left alone. Inward and tangential components stay. It MUST NOT emit `RING_OUT` or a corpse-fall for that edge. Separation and later impulses MUST NOT leave a centre outside that support radius. Closed does not add a rebound contact. A recording pinned to version 58 stays open; a closed selection is a later version and MUST NOT reinterpret version 58. The product pit is version 60: closed, with the Arena's walls as structures (STRUCTURE-CONTACT-001). Bodies are still held only by the support circle; the walls stop swords.

### CONTACT-MATERIAL-001

Contact physics is per material pair. Every contact surface carries a `ContactMaterial` (restitution, the closing speed below which it does not bounce, its own Coulomb coefficient): each weapon (`WeaponDefinition.material`), each body (`FighterDefinition.material`), each structure. How two materials meet is the rules' `ContactMaterialTable` (`DuelRules.materials`): an authored pair entry wins; otherwise friction is a surface's own μ on itself and `√(μa·μb)` between two surfaces, and restitution is the less elastic surface at its own threshold. Pairs are resolved once, at setup, into `ContactPair`s the rules cache (`blade_pair`, `sword_body_pair`, `body_pair`, `structure_pair`); no solve looks up an id. The standard table holds today's contacts exactly: steel↔steel μ 0.20 with steel's 0.35 above 1.4 m/s, steel↔flesh μ 0.05 and e 0.02 at any speed, flesh↔flesh μ 0.30 and e 0.05; a change in any of them is a rules change. Unknown or impossible coefficients fail closed (`DuelRules.problem`). A material is digested into its combatant's fingerprint (content schema 5) or the rules' world fingerprint. Implementation: `game/src/domain/rules/contact_material.gd`, `contact_pair.gd`, `contact_material_table.gd`, `game/content/rules/material_catalog.gd`. Tests: `RULES` (`test_the_material_table_keeps_todays_contacts`), every contact suite and the `REPLAY` goldens unchanged across the move.

### CONTACT-SIDE-001

A contact row has two sides, each named by how an impulse reaches the simulation's coordinates (`RigidContactSolver.Side`): `WEAPON`, a held sword — its wielder's body through its real mass and the weapon angle through its lever over the held inertia; `BODY`, a body only; `WORLD`, which does not move — zero inverse mass, zero velocity, no lever. A row's effective mass is `k = J·M⁻¹·Jᵀ` over the coordinates its sides own, so a world side contributes nothing and the row is the moving side's alone. One mass per coordinate across a solve still holds (`_share_masses`); a world side adds no coordinate. Heading is never a contact coordinate. The world is never the opponent: a row against it sets no `opponent_contact`. Adding the descriptor changed no row order, iteration count, law or budget (every contact suite and the `REPLAY` goldens unchanged). Implementation: `game/src/domain/combat/rigid_contact_solver.gd`, `structure_contact_solver.gd`. Tests: `STRUCTURE` (`test_the_wall_is_the_world_side_of_one_impulse_law`).

### STRUCTURE-CONTACT-001

Swords meet collidable stage structures through the same deterministic contact engine as each other; Godot physics never decides one. A structure (`StageObjectDef`) is rules content: a stable id, simplified collision shapes, one material, what it blocks (`blocks_blade`; bodies are not filtered here and keep ARENA-001's support circle), and its motion (static only). Shapes are the ones shipped content needs: `ARC`, the inside face of a circle over a span under half a turn (solid beyond, normal toward the centre), and `SEGMENT`, a thin wall rounded at its ends. An arc owns only its span; its ends are where a segment (a jamb) takes over. The render mesh never collides. The blade is the capsule every blade contact uses, `blade_base_radius` to `tip_radius`, `blade_radius` thick; the guard, handle and hands do not meet structures.

The sweep finds structure contacts in the same chronological loop as every other contact (COMBAT-007): inside one substep a blade-on-blade contact outranks a structure, and a structure outranks a body, so a wall that got in the way stops a cut before what lies past it. Each sword keeps one `StructureContactSet` (present only when the rules have structures, so a structure-free duel hashes exactly as before): the lifecycle SEPARATED → CONTACTING → SEPARATING with the sword pair's `separation_epsilon`, at most two points, and identity by feature (structure, shape) — a blade sliding along one arc keeps one identity. A new contact is one impulse (`StructureContactSolver`): the exact normal block with each row's pair restitution as its target, a simultaneous Coulomb tangent at one relaxation, a final normal top-up, fixed iterations — `SwordContactSolver.solve_points` with the world as the second side. A persisted contact is rows of `RigidContactSolver` (`ROW_STRUCTURE`, b the `WORLD` side): held without restitution, friction warm-started by feature, overlap pushed out to `contact_slop` with the other rows, and inside the contact budget and its no-tunnel fallback. A held blade does not strike again.

Consequence is fixed for every structure: it blocks. It never damages, never parries, never scores and never counts as meeting the opponent (`attack_contacted` untouched). A swing it actually stops ends by the one arrest law (RIGID-CONTACT-002), and the sword's impact authority dips from its own Δθ̇ like any hard impact (IMPACT-AUTHORITY-001). One `BLADE_STRUCTURE_CONTACT` event per new contact carries the point, normal, impulses, energy, structure, feature and arrest. The weapon-speed corruption bound accounts for the stiffer world side (`SimulationGuardrails.structure_weapon_speed_bound`). The rules' world fingerprint (materials and structures) is in every replay header (format 3), so a recording is refused against moved walls under the same version; the state hash covers each structure contact (layout 10). Version 58 and The End carry no structures. The Arena (`StageStructures.arena`, rules 60) is a stone wall on the support circle — two arcs and four straight jambs — and two wooden doors recessed 0.23 m north and south. Not yet modelled: the guard or hands on a wall, a body against a wall, the CPU's prediction of walls, kinematic structures. Implementation: `game/src/domain/rules/stage_object_def.gd`, `structure_shape.gd`, `game/src/domain/combat/structure_contact_geometry.gd`, `structure_contact_solver.gd`, `game/src/domain/state/structure_contact_set.gd`, `collision_system.gd`, `contact_resolver.gd`, `rigid_contact_solver.gd`, `game/content/rules/stage_structures.gd`. Tests: `STRUCTURE` (rules and fingerprint, narrow phase on wall, gate and jamb, world side and restitution, Coulomb slide and stick and separation, a cut into stone at 20 and 45 rad/s stopping once with no hit, parry or opponent contact and no tunnelling, the open disc letting the same cut through, determinism, a held blade not striking again, a body-carried blade meeting the wooden door, a saturated tick not tunnelling).

## Sides (SIDE)

### SIDE-001

Cardinal sides and one locked world. The arena has exactly one permanently fixed orientation — north is `+y`, south is `-y` — and the simulation MUST NOT rotate for anyone. `DuelSide { LIGHT_SOUTH, DARK_NORTH }` is a first-class identity that determines canonical spawn, initial facing, presentation identity, and local camera orientation; it MUST NOT be inferred from slot number, spawn position, colour, or camera yaw, all of which are consequences of it. Light spawns at `(0, -spawn_offset)` facing north and Dark at `(0, +spawn_offset)` facing south, each looking at the other. Exactly one fighter MUST hold each side, and side MUST survive a round reset. Side MUST be covered by `StateHasher`.

Quick Play MUST assign sides 50/50 from the match seed, so both cardinal spawns and both camera orientations are exercised by ordinary play.

Local camera yaw is **presentation only**: the local player is always at the bottom of the screen, so a local Dark player's view is turned half a revolution. It MUST NOT enter `StateHasher`, replay state, or any authoritative state — it is the one quantity two viewers of the same match may legitimately disagree about, which is what lets two networked players see opposite perspectives of one authoritative world. Footwork MUST stay encoded through the duel basis rather than world directions, and the presentation invariant _local right projects right on screen, local forward projects up_ MUST hold for both sides.

Side MUST be communicated by more than colour: colour plus edge pattern plus spawn orientation plus HUD label. Arena cardinality cues MUST NOT compete with blade readability.

## Content (CONTENT)

### CONTENT-001

Authored definitions are immutable data. Fighters, weapons, and arenas are plain id-keyed definitions produced by pure catalog functions, never mutable Godot `Resource`s inside the domain. A definition MUST NOT carry runtime state: an authored definition and a mutable match state are different things, and nothing may write to a definition after creation. Derived quantities (moment of inertia, available acceleration, collision geometry) MUST be computed from the definition rather than stored alongside it; caching is permitted only where recomputation is measurably wasteful, and the cache MUST NOT be authorable. Every definition MUST validate: positive physical magnitudes, `blade_length <= length`, `guard_limit > guard_angle`, `I > 0`.

### CONTENT-002

Physical baseline. The duel has exactly one normalized physical baseline, stated once in `PhysicalBaseline`: a 1.75 m, 80 kg fighter with a 0.27 m footprint, holding a 1.22 m bastard sword with a 0.97 m effective blade at 1.60 kg, with canonical guards at ±45°, a ±135° guard limit, and a 90° tap arc. `scale = 1.0` MUST mean exactly that fighter and that weapon, in SI units. That pair — `ContentIds.FIGHTER_DUELIST` (presented as Wolf) holding `ContentIds.WEAPON_BASTARD_SWORD` — is the canonical physical reference pair: every derived reference (impulse, cut and thrust severity, calibration reach) comes from it, and future fighters and weapons are judged against it. Abstract units (`player_size = 100`) MUST NOT appear anywhere. Baseline magnitudes MUST NOT be duplicated as literals in content or code. Weapon reach MUST be the wielder's `FighterDefinition.grip_radius` plus the weapon's blade: a weapon's `blade_base_radius` MUST equal its holder's grip radius, and no presentation measurement (a mesh, a rig, an arm length) may decide reach. Normalized ratios against the baseline MAY be exposed as diagnostics, but the simulation MUST NOT read them, because the absolute quantities already carry every effect of scale and reading both would count scale twice.

The reference pair is **calibration content, never infrastructure** (COMBATANT-GENERIC-001): it is where the injury calibration, the clash yardstick and the CPU's calibration reach were measured, and no simulation system may fall back to it. A shipped fighter's strength is authored, never inferred from size: content authors `strength_scale` (weapon drive), `traction_scale` (locomotion, braking and burst force) and `turn_support_scale` (heading turn torque) relative to the reference (1.0 each) and resolves them to newtons and newton-metres when the definition is built (`FighterCatalog.resolve_actuators`); the simulation reads only the resolved values, never a scale. Geometry, mass, reach, the lying body and the hilt track are each authored on their own — height never scales mass, mass never scales a radius. The CONTENT-002 scaling laws (geometry linear, mass cubic, force squared, torque cubic) survive only as an explicit prototype generator (`FighterCatalog.prototype_at`) for scaling proofs and quick prototypes.

> Calibration order is normative, because it is the only order in which the numbers mean anything: freeze dimensions, then locomotion force, then turn torque against body inertia, then sword torque, then structural coupling, and only then collision severity and the damage curve. A baseline that feels right MUST NOT be achieved by picking a damage number first.

### COMBATANT-GENERIC-001

The deterministic simulation has no character-identity behaviour. Every fighter is represented by the same `FighterState` and `CombatantPhysicsSpec` contracts. Differences in movement, reach, weapon geometry, mass, inertia, force production, materials and handling MUST arise exclusively from validated immutable content passed into the shared physics systems. `DuelRules` is the match's physics context and holds one spec per fighter slot (`combatants`); every system reads a fighter's physics through `DuelRules.spec_of(fighter)` / `combatant(slot)` or receives a spec directly — there is no shared `rules.fighter` / `rules.weapon`, and no system may look up a catalog, a content id or the reference baseline. Pair quantities use both sides' own values: body contact at the sum of the two push radii and through both real masses, weapon→body touch at the target's hurt torso plus the attacker's blade, a blade clash through each sword's own geometry, feature radii, held inertia and material (restitution: the less elastic of the two), strike reach as the attacker's forward reach plus the target's torso. Swapping character/loadout specifications changes only those physical inputs; no simulation branch may depend on a character name, fighter slot, model, skeleton or presentation asset, and a fighter's slot MUST equal its index (`StateInvariants.SLOT_MISMATCH`). A mirror match with mirrored world and swapped specs MUST produce the exact reflection with the actors exchanged. The engine is generic for any fighter carrying one rigid compound weapon on the one-degree-of-freedom θ model; articulated, flexible or dual-wielded weapons are out of scope until one ships. Lint enforces the seam (`COMBATANT-GENERIC`: no `rules.fighter`/`rules.weapon` anywhere in `src`/`tools`; no catalog, content id, baseline or identity name in the domain systems). Implementation: `game/src/domain/rules/combatant_physics_spec.gd`, `game/src/domain/rules/duel_rules.gd`. Tests: `GENERIC` (heterogeneous Light-vs-Heavy translation, weapon dynamics, contact and reach; mirror + slot swap; alternate weapon on one body), `REPLAY` (the reference mirror match is hash-identical to before the extraction).

### LOADOUT-001

Character body, weapon, and fighter↔weapon handling are independently authored. A `FighterDefinition` knows no weapon; a `WeaponDefinition` is the object (geometry, mass distribution, grip stations, contact material, motor torques, damage); a `WeaponHandlingProfile` is how this body carries this weapon — the hilt track `C(θ)` and its carriage. A match MUST resolve them into one immutable `CombatantPhysicsSpec` per fighter before tick 0 (`LoadoutCatalog.compile`), validated as a whole (`CombatantPhysicsSpec.problem`: each part valid, the handling authored for exactly this fighter and weapon, the weapon's hilt at the fighter's grip, nothing of the held sword inside the wielder's torso). Unsupported fighter/weapon combinations MUST fail closed — no duel — and MUST NOT fall back to another fighter's handling data or to the reference pair. Runtime state MUST NOT copy content values. Replays pin the context: the header carries, per slot, the character, weapon and handling ids and a SHA-256 fingerprint of the resolved physical content, plus the content schema version (`ReplayRecord` format 2), so a recording is refused — never reinterpreted — against different content under the same ids; the per-tick state hash stays dynamic state only. Implementation: `game/src/domain/rules/weapon_handling_profile.gd`, `game/content/rules/loadout_catalog.gd`, `game/content/rules/handling_catalog.gd`, `game/src/domain/replay/replay_record.gd`. Tests: `GENERIC`, `RULES`, `REPLAY`.

## Presentation (PRES)

### PRES-001

Presentation never authorizes outcomes. `SnapshotProjector` is the only place presentation reads `MatchState`, producing one immutable `PresentationSnapshot` per tick. `MatchPresenter`, proxies, directors, the HUD, and touch controls consume snapshots and events and emit intents or requests (hitstop, pause); they MUST NOT step, mutate, or read the simulation. `src/presentation` MUST NOT reference application classes (lint derives the ban from `class_name`s).

### CONTACT-PRESENTATION-001

The drawn swords meet where the simulation says they touch. Physics computes the fight once; the deterministic combat plane owns every contact's XY, each sword's yaw `θ` and each hilt's horizontal place `C(θ)`, and presentation adds only a height. The snapshot carries a read-only projection of every touching manifold point (`PresentationContact`: XY, features and fractions on each sword, feature-local coordinates, normal, `Jn`, `Jt`, slip, age, `contact_id` — CONTACT-IDENTITY-001); no presentation code computes a contact of its own, and a dropped or repeated presentation frame cannot change any hash. Because a pitched blade's ground projection is shorter than the blade (`d·cos p`), a sword can pass through the authoritative contact point only while it is level there; so while a contact exists each contacted sword MUST be drawn with hilt XY and yaw unchanged, pitch 0, and one shared height `z_contact = mean over touching points of ½(z_free,a + z_free,b)` (each `z_free` the sword's height at the contact under its free lift); roll stays presentation (it never moves the centreline). Both swords at one height meet edge to edge exactly as the plane says, so there is no over/under to decide and no slot or attacker flag ever picks one. The swords are anchored at once (exact parity the frame a contact exists); the bodies follow through the arm IK, and leaving a contact eases back to the free lift (inertialized, never a pop). Clash and parry sparks, the clang and the grind sit at the same rendered contact (`ContactPresentation.contact_height`, the one home of that height); a strike on a body is not a sword contact and keeps the blade plane. The presenter is the one interpolation owner; nothing adds a second interpolation to the weapon branch. Implementation: `game/src/presentation/entities/contact_presentation.gd`, `game/src/presentation/snapshot/presentation_contact.gd`, `FighterPresentation3D.apply_pose`. Tests: `PRES-CONTACT` (snapshot projection is read-only; contacted swords level, at one height, through the contact, yaw authoritative; apart swords keep their free lift; release eases without a pop; sparks and clang at the rendered contact).

### COMBAT-READABILITY-001

Every gameplay-critical combat cue is derived from authoritative physical state — `Jn`, `Jt`, slip, `E_diss`, blade velocity, contact age and identity, the attack phase — never from a `BIND` or `PARRY` state of its own, and where practical it is carried on at least two senses: a clash is seen (sparks at the rendered contact) and heard (a clang); a body hit is seen on the victim and heard; a true whiff is heard as its own hollow follow-through (`CUE_WHIFF`, louder for a harder launch) and seen in the body's overswing, and is never punctuated like a hit (no sparks, hitstop, shake or haptic); sustained contact is seen (grind sparks) and heard (a held scrape). Optional third channels read the same sources: sound captions (`SoundCaptions`) are picked from the frame's own audio requests — at most one per tick, by a fixed order that keeps the physical hierarchy, with a scrape captioned once per contact when it becomes audible — and the contact highlight (`ContactHighlight3D`) rings exactly the snapshot's touching points at the shared rendered contact height. Haptics are always optional and supplemental, never the only channel. Color MUST NOT carry combat information alone (UX-001). Accessibility settings — combat FX intensity, flash, screen shake, motion, trails, high-contrast swords, haptics, announcer and sound captions, the contact highlight, separate music/SFX/voice levels, hold-or-toggle charge, and key rebinding (`KeyBindings`, which rewrites only the `InputMap` actions the game reads) — change only how strongly a cue is presented or how input is entered: they MUST NOT change the simulation, timing, contact result or replay hash. Toggle charge emits exactly the press and release command edges a hold emits. Turning every visual intensity down never removes a cue's other sense. Implementation: `game/src/presentation/feedback/combat_feedback_director.gd`, `game/src/application/input/human_input_state.gd`, `PlayerSettings`. Tests: `PRES-READABILITY` (clash, hit, whiff on two senses; reduced visuals keep cues audible; presentation settings never change the simulation hash; sound captions keep the hierarchy and are asked for only when on), `PRES-CONTACT` (the highlight rings exactly the touching points; a scrape is captioned once per contact), `PRES-HUD` (sound captions beside the announcer), `INPUT` (toggle charge emits the same commands as holding), `SETTINGS` (bindings default to the authored actions, swap without stranding, drive the `InputMap`, and distrust a stored set), `APP-E2E` (a key rebound through the real panel reaches the game).

### PRES-002

Presentation architecture. The data flow is:

```text
Simulation → PresentationSnapshot + DuelEvents
→ CombatFeedbackDirector → FeedbackFrame (value-like requests)
→ CameraFeedback, FighterPresenter, WeaponPresenter, VfxPresenter,
  AudioPresenter, clock requests → FixedTickDriver
```

`CombatFeedbackDirector` MUST be pure computation — no SceneTree dependency, no node manipulation. It outputs a `FeedbackFrame` of typed value-like requests (`CameraShakeRequest`, `HitstopRequest`, `AudioCueRequest`, `VfxRequest`, `FighterCueRequest`, `WeaponCueRequest`). Downstream presenters consume requests. Nothing below the director may modify authoritative state. The simulation exclusively owns weapon angle, angular velocity, contact geometry, reach, and every outcome; the displayed weapon is a deterministic mapping of authoritative fighter and weapon state (PRES-CARRIAGE-001), never driven by animation clips. Character animation visually supports the displayed sword, never the reverse. Root motion, if used, MUST be warped to match the authoritative trajectory.

### PRES-CARRIAGE-001

The displayed sword is the authoritative sword, lifted. Its carriage (grip centre) sits horizontally exactly on the authoritative `C(θ)` and its horizontal yaw is exactly θ in the combat frame (WEAPON-ORBIT-005), evaluated at the interpolated θ. `CombatPresentationField` (guard field, charge gather, recovery) and `CutPresentationCurve` (a cut in flight: descent from the load, near level through centre, low follow-through, the pitch inflection into the opposite guard) add only the lift (WEAPON-ORBIT-006): the carriage's height and the blade's pitch and roll about it. They MUST be functions of authoritative angle, signed angular velocity, launch direction, charge, launch charge, phase and swing progress plus presentation-only hysteresis (guard side, cut inflection), and MUST NOT write anything back; a phase boundary's discontinuity in the lift is absorbed by a decaying (inertialized) offset in height, pitch and roll, never by changing the field and never horizontally. Pitch foreshortens the drawn blade's ground projection; nothing re-aims it. Swing presentation MUST be keyed to physical travel, never animation time, so a blade stopped, deflected, or reversed by contact stops, deflects, or reverses the picture. Long Guard, Ready, Gather and Load are readings of the one continuous θ, not presentation modes. Trails follow the dangerous space (TRAIL-PARITY-001); sparks and gameplay effects originate at authoritative contact coordinates.

### TRAIL-PARITY-001

The trail equals the dangerous space. A sword trail's sample MUST be the authoritative planar blade's hilt and tip at the interpolated θ (`FighterPresentation3D.trail_points`), raised to the drawn sword's height, so the ribbon's ground footprint is exactly the swept blade collision uses — never the drawn sword's foreshortened, pitched or lifted projection, which would draw the danger shorter than it is. The F3 debug overlay draws the 270° control domain faintly (coverage, SLASH-SHAPE-001) and the swing in flight up to its committed end strongly (the immediate threat), both from the authoritative pose. Implementation: `game/src/presentation/entities/fighter_presentation_3d.gd`, `game/src/presentation/hud/debug_vectors_3d.gd`. Tests: `PRESENTER` (the trail's ground footprint lies on the authoritative planar sweep while the drawn sword pitches).

### PRES-KIT-001

One manifest per combatant identity. Each combatant is a `CombatantPresentationKit` composing a `FighterPresentationKit` (body scene, animation map, condition profile, audio) and a `WeaponPresentationKit` (blade scene, grip metadata, trail/spark/impact profiles, audio). This split exists because the same fighter MAY hold different weapons and different fighters MAY hold the same weapon; both MUST compose cleanly.

Changing an identity's art, animation, or sound MUST be a kit edit (an authored `.tres` at `RiposteKits.AUTHORED_KIT_PATHS`), never a presenter or gameplay change. Generic presentation code MUST NOT name content identities. Debug builds fail closed on a missing kit; release builds degrade to a placeholder.

Animation clips use semantic slots (`IDLE`, `MOVE_FORWARD`, `MOVE_BACKWARD`, `ORBIT_LEFT`, `ORBIT_RIGHT`, `DASH_FORWARD`, `DASH_BACK`, `DASH_LEFT`, `DASH_RIGHT`, `CHARGE`, `SWING`, `OVERSWING`, `RECOVERY`, `HURT`, `STAGGER`, `CRITICAL`, `DEATH`). `animation_clips` keys MUST be a subset of declared semantics; a kit mapping anything else has authored a clip the proxy will never ask for. Primitive presenters drive procedural transforms from these semantics; authored scenes play the mapped clip (an `AnimationTree` inside the scene MAY blend them) and fall back to the procedural transform for any semantic without one. An authored scene MUST NOT own the blade, a physics body, or a collision shape: the simulation decides position, facing, and contact, and the rig only shows them. An authored rig's hands MUST follow the displayed `SwordCarriage` (two-hand IK to its grip markers), which is the authoritative planar sword lifted (PRES-CARRIAGE-001); `WeaponOrigin` is the undrawn authoritative sword itself. A rig MUST NOT write either. Rig and animation contract: [docs/reference/godot.md](../docs/reference/godot.md).

Cosmetic overlays — `FighterSkinKit`, `WeaponSkinKit`, `FighterVoiceKit`, `FighterIntroProfile`, and the per-match `MatchPresentationLoadout` — are optional, resolved after the rules are fixed, and MUST NOT change any definition, rule, or authoritative state; a skin authored for another base kit MUST be refused, and an unknown skin MUST resolve to the base look.

Contact feedback uses shared semantic `ImpactPresentationProfile`s (clash, slash, poke, thrust, graze, kill) defining shake curve, hitstop band, baseline particle intensity, and audio category. `WeaponPresentationKit` MAY override cosmetic aspects (audio family, spark look, trail look) but MUST NOT redefine the semantic meaning of a contact class. Damage state belongs to fighter presentation (`FighterPresentationKit.condition_profile`), not weapon. The size of a strike's feedback MUST be one continuous, monotonic response of the resolver's quality across every channel — contact kind picks the shape of an effect, never a size bucket — and an audio take MUST be chosen deterministically from the event so replays sound identical.

### PRES-INTRO-001

Once-per-set introduction. A set is one match (first to `rounds_to_win` rounds), identified by a `set_id` the application opens for every Quick Play and every Rematch. A set MAY open with the fighter introduction exactly once (`claim_set_intro`); its later rounds MUST NOT. A Rematch is a new set and is introduced again. The tick driver MUST be stopped for the whole intro, so no tick runs and the first authoritative tick is identical with or without it; a press that skips the intro MUST NOT become an attack. The intro's showcase figures and their display swords are presentation-only and MUST NOT be the match proxies. Every announcer line MUST have a caption.

### PRES-TERMINAL-001

One terminal presentation per fighter, derived from authority. Each fighter's terminal presentation cause (`KILL`, `RING_OUT`, or none) MUST come from the snapshot's projected `terminal_cause` (COMBAT-014), never from which request or event arrived first. `KILL` plays the death presentation and the death weapon release; `RING_OUT` plays the fall trajectory and the airborne release; a tick where both fighters have a cause presents both. A death or fall request for a fighter whose authoritative cause disagrees MUST be dropped. Terminal latches (death, finisher, fall, weapon drop, grip, one-shot clip) MUST clear at the next round.

### PRES-TIME-001

Four clocks, one owner each. **Simulation time** (60 Hz ticks) decides every outcome. **Presentation-scaled time** — the frame's real time with hitstop counted as zero and slow motion at its scale (`FixedTickDriver.presentation_delta`) — drives fighter clips, the death collapse and finisher, the fall trajectory, weapon-release timers, and grip release, so terminal choreography slows and freezes with the duel it shows. **Real time** drives UI, camera smoothing, audio, and the set intro and victory cinematics, which run while no duel is being shown. **Godot physics time** drives presentation rigid bodies (dropped swords, a future ragdoll). A system MUST NOT pick its own delta; `MatchPresenter.render` hands each consumer its clock. Fighter clips play on Godot's normal process step (so the skeleton's modifiers — body support, IK — run after animation, as the engine orders them) at `speed_scale` = presentation-scaled ÷ real time; only the cinematic showcase actor and capture tools advance animation manually, and then the whole pose pipeline is theirs.

### PRES-VICTORY-001

Winner control continuity. A decided round is not a cutscene: one domain gate, `DuelSimulation.accepts_gameplay_input(state, slot)`, decides whose commands a tick reads — both fighters while a round is fought; once it is decided only the round's winner, alive and on the platform, through the whole post-round freedom **and** the result (one shared step, `_step_decided`), until exactly the next `ROUND_INTRO` or `_end_match`. The loser's commands are ignored, the loser coasts and their blade settles. Presentation MUST NOT drain, skip or fast-forward the decided round's ticks: the set's final beat is that round played live, and every terminal presentation's mandatory beat MUST fit within `post_round_free_ticks + result_ticks`. Walking off the edge then is a celebration fall that keeps the result. Tests: `ROUND` (the gate's truth table, the winner answering on the result's last tick, dash/charge/swing late, walk-off keeps the score, the deciding round keeps control until the match ends), `PRES-PRESENTER` (`test_every_terminal_beat_fits_before_the_next_transition`), `FULL-E2E`. Once-per-set victory. When a set resolves with a winner, the winner MAY be shown once (`claim_set_victory`) in a victory showcase; an ordinary round end MUST NOT start it, and a draw or no-contest MUST NOT show one. The set-winning fanfare is that showcase's sting and plays from the claim alone, exactly once. `BODY_HIT`, `FIGHTER_KILLED`, and `ROUND_ENDED` MUST NOT play it; a round end plays the round sting only. The winner MUST be read from the authoritative `match_winner`. The showcase actor MUST be built fresh from the winner's resolved combatant kit (fighter, skin, weapon, weapon skin, colorway for their side) and MUST NOT be, reuse, or mutate a match proxy. The showcase MUST NOT step, read, or write the simulation, so the replay hash is identical with or without it. Results controls MUST NOT be interactive until the cinematic finishes or is skipped, and a press that skips it MUST NOT activate a control. Every voiced line MUST have a caption. Leaving the results frees every showcase node and stops its audio. The victory is a quick cut, the quick return cut, and the gather into the same high shoulder load the duel's carriage uses, held while the camera pushes in; there is no third, released attack.

### PRES-HEADING-001

The fighter faces where their weapon window is. Presentation MUST show the combat heading `φ` — the centre of the 270° weapon domain, `worldYaw = φ + θ` — as the stance's and the head's forward, and the target bearing `τ` only as what `φ` is trying to catch: the head MAY glance toward `τ` by at most `CombatPoseModifier3D.LOOK_LIMIT` (between 10° and 15°; 12° shipped) and MUST NOT lock onto it. A committed fighter whose heading has not turned back onto the opponent therefore reads as not having done so — the head never claims a lock-on the attack window does not have. Presentation only: `τ`, `φ` and the sword frame are unchanged, and nothing is hashed. Implementation: `game/src/presentation/entities/combat_pose_modifier_3d.gd`, `fighter_presentation_3d.gd`. Tests: `PRES-RIG` (`test_the_head_faces_the_heading_and_only_glances_at_the_target`).

### PRES-STANCE-001

Bladed stance, combat frame unchanged. Simulation facing stays opponent-forward and owns movement, the ±135° sword angle, and every contact. A fighter's `FighterStanceProfile` turns only the presented body: the pelvis and shoulder line bladed against combat-forward, the head counter-rotated onto the opponent, a fixed lead foot (Wolf: right), and a per-side cap on held-load coil (the rear-side load MAY coil a little more). The sword angle MUST NOT be re-measured against the bladed chest, and no presentation component may chase the raw angle by turning the whole body. The body's support of the sword is one deterministic mapping from the same interpolated θ (`BodySupportPose`): torso coil effort and cap, elbow-guide inputs, gather and lift. Its support magnitudes MUST be continuous in θ — the guard bands (the Long Guard corridor's 12°/18° hysteresis, the load band) are readings and MUST NOT step the body — and the legs keep the stance's frame at every θ (the lead foot leads at ±135° as at 0°). Weapon physics stays an exact mirror; only this human support is side-dependent.

### STANCE-FOOT-001

Semi-bladed head to foot. Wolf's stance is a fixed right lead between square and fencing profile, a gameplay abstraction rather than one historical school's prescription. The blade MUST grow up the body: the lead toe stays close to the combat heading, the pelvis is modestly bladed (Wolf 12°), the chest more (Wolf 22.5°), and the head returns to the combat heading (PRES-HEADING-001). The rear foot MUST be more open than the lead foot (Wolf: lead toe 8°, rear 25°), and the feet MUST never stand parallel-square or cross in ordinary movement. The base is a stable two-handed width, authored in the clips (every grounded clip opens the thighs by `STANCE_ABDUCTION` and rolls the soles level — `tools/blender/bootstrap/build_wolf.py`), never offset at runtime: Wolf's settled ankles stand ~24 cm apart across the line (a 20–28 cm presentation band, short of the ~40 cm shoulders), and no step gathers them onto one line. It is a look, not a physics value. In a settled guard the sword MAY coil the chest only within `guard_coil_degrees`, so the torso keeps its blade (Wolf 20–25°) wherever the sword rests; a charge and a cut coil further on top of that base, never replacing it. Foot yaw is applied after the clip, about the vertical at each ankle, so the clip's foot placement and stance width are untouched, a planted foot never skates, and no gait clip squares the feet; it is constant, so no new motion is introduced. During commitment the head, lead foot, hips and sword all stay on the combat heading; the head only glances toward the target bearing within `CombatPoseModifier3D.LOOK_LIMIT` — nothing swivels to hide a whiff. Stance yaw is presentation only and MUST NOT redefine the combat heading or the sword frame. Tests assert relationships, not exact angles. Implementation: `game/src/presentation/kit/fighter_stance_profile.gd`, `game/src/presentation/entities/combat_pose_modifier_3d.gd`. Tests: `PRES-RIG` (`test_the_stance_is_semi_bladed_head_to_foot`).

### GRIP-001

A right-handed hand-and-a-half grip. The dominant (right) hand is the guard-side hand and the off (left) hand the pommel-side hand: pommel < off hand < dominant hand < guard along the weapon axis, both on the usable handle (the pommel's shoulder to the underside of the guard, measured on the authored sword and stated in `PhysicalBaseline`). Each hand's position MUST be derived from that handle and the hand's size — the dominant hand a half hand plus a small clearance under the guard, the off hand a half hand plus a small clearance above the pommel — never authored as free numbers; the fists MUST NOT overlap each other, the guard or the pommel. The grip markers are fixed weapon-local points: they MUST NOT swap, slide or bunch with θ, side, charge, cut, parry or recovery; the arms reorganize around them. Where the hands hold the sword MUST NOT move the authoritative sword: the orbit's reference point on the sword (`WeaponHandlingProfile.carriage_radius`, `PhysicalBaseline.CARRIAGE_REFERENCE_M`) is separate from the hands, so θ, `C(θ)` and every blade point keep their meaning; the hands enter physics only where they physically are — the domain hand clearance and the centre of percussion about the hands. The asset validator holds the authored markers, pommel shoulder and guard underside to the baseline. Implementation: `game/src/domain/rules/physical_baseline.gd`, `game/src/domain/rules/weapon_definition.gd`, `tools/blender/validate_assets.py`. Tests: `PRES-RIG` (`test_the_grip_is_a_right_handed_hand_and_a_half_grip`, `test_hands_stay_on_the_grip_through_the_whole_legal_arc`), `SHAPE`.

### PRES-ARMS-001

Elbows are structure. Each arm bends toward a pole from `ElbowGuideField`, derived from that arm's displayed hand in the stance's torso frame and the guard/cut landmark (`ArmStructureProfile`: mid guard, Longpoint, high load attacking and support arm, follow-through), with Longpoint as the bridge between sides and the roles exchanging on the blade's own inflection. The runtime pose stack MUST stay one clip layer (`AnimationPlayer`, in place, no root motion), one `CombatPoseModifier3D` (torso support and elbow poles, solved from that update's shoulders), and one native `TwoBoneIK3D` with both arms; carriage, cut, guide, and clearance logic are pure helpers and data, never further modifiers. A pole MUST NOT be a fixed target rotated by the raw angle. It is the shoulder-side horizontal projected off the shoulder→hand line — that projection's sign needs no flip — plus a downward hang, and it MUST NOT go colinear with the arm. A vanishing projection MUST fade out rather than be renormalized. PRES-RIG MUST prove through the guard field, both charge gathers, and both full-charge releases (the old failure zone at 1°) that no elbow bends toward the torso, no elbow jumps beyond a per-degree budget, and IK never stretches an arm.

### PRES-POSE-001

Rigid presentation geometry. Bones keep their authored lengths, the weapon its authored geometry, and both hands stay on their grips; no hand, wrist, forearm, elbow, pommel, guard, or blade may penetrate the fighter's own clearance proxies (`SelfClearanceProfile`: primitive torso shells and head carried by their bones — presentation-only, never physics bodies or combat geometry). Presentation MUST NOT move the sword horizontally to clear the body (WEAPON-ORBIT-005): hand clearance on the plane is the orbit's (WEAPON-PATH-003), and a presented pose that still penetrates is fixed in the body (stance, coil, elbows), in the lift, or — as a rules change — in `C(θ)`, never by stretching, inverting, or pushing a joint through the body. Non-penetration is hard; the profile's visible-air margins are tuning targets PRES-RIG reports. Because the pose domain is bounded (±135° × charge × phase × side, one skeleton per profile), prevention is offline: PRES-RIG MUST sweep it densely, and there is no runtime self-clearance correction — never per-frame physics queries, shape casts, or physics bodies for self-clearance.

### PRES-POSE-002

Contact-coherent presentation (target; not yet implemented). When authority reports weapon/body or weapon/weapon contact, presentation prioritizes the authoritative contact point and normal while satisfying PRES-POSE-001, and never continues a weapon path through a contacted body after authoritative motion stopped or changed. A lethal thrust's run-through is the one allowed penetration, along the thrust axis, inside PRES-STAB-001's timeline.

### PRES-STAB-001

One stab timeline. A killing thrust plays one data-driven `StabFinisherProfile` shared by striker, victim, and the victim's sword: IMPALE → HOLD → WITHDRAW (along the thrust axis) → BLADE CLEAR → VICTIM COLLAPSE → WEAPON RELEASE. The victim MUST NOT begin to fall before the blade is clear (`victim_collapse_start ≥ withdraw_clear`) nor release the sword before falling; the authored clips MUST hold where the profile says. The kill itself is already authoritative and is not delayed.

### PRES-CHROME-001

One chrome policy. `MatchScreen` alone decides whether the gameplay HUD (name plates, health, round pips, clock, Pause) is shown: only while a duel is being fought — never over the set intro, the round-start card, or the set's final beat and victory. No director toggles it; banners and captions sit outside it so cards and every voiced line still read.

### PRES-ROUND-START-001

Every round starts with "MATCH N … FIGHT!". The round's own intro ticks are the window: "MATCH N" over the set score as the round is introduced, then "FIGHT!" on the tick the round goes live, both called by the set intro's announcer voice from pre-generated, captioned takes. Input held through the card is discarded at the transition (INPUT-002) and the first live tick accepts input with no grace period. Presentation says "Match"; the domain keeps "round".

## Character art (ART)

### ART-HEAD-001

The pentagonal head's forward point is the face's centreline. A character's head is a five-sided prism whose one forward vertex (`nose_vertex`) points along the character art's forward axis (`coordinate_frame.forward`); that vertex is the implicit nose and the line the eyes and brow are placed across. Eye and brow placement is authored per character relative to its own head, never copied as world coordinates from another character. A modeled nose or mouth is optional and MUST NOT be added to compensate for misplaced eyes or brow. Docs: [docs/concepts/character-art.md](../docs/concepts/character-art.md).

### ART-HEAD-002

Hair and clothes frame the face; they never cover the eyes and brow. Each character authors a `face_clearance` region in head-relative terms — an eye/brow `band` as fractions of its head's height, a `width` as a fraction of its head's radius, and a forward `reach` in front of the nose — so a taller or shorter head gets its own region, not a shared box. The region MUST hold the alive eyes and the brow, and no `hair` or `clothes` part of any variant may enter it; temples, side locks, sideburns, a short lock above the brow and rear hair stay legal. The eyes and brow stay modeled voxel features. A validator cannot judge a face, so a hairstyle change still needs a front, three-quarter and gameplay-camera capture. Implementation: `tools/blender/character_art.py` (`face_problems`, `clearance_self_check`, run by `pnpm lint`). Data: `game/content/characters/*.character.json`.

### ART-LAYER-001

Painted base, modeled outer layer. A character is a LEGO-like block body and pentagonal head (the base) with modeled voxel pieces on top — hair volume and locks, collars, hems, cuffs, belts, bracers, armour — where depth or silhouette reads at the match camera. Detail too thin to model (a hairline, light scruff, weave, stitching) belongs painted on the base once the UV pipeline is proven end to end; until then the base stays flat materials and vertex colors. Paint MUST NOT stand in for a missing surface or a broken mesh, and a modeled piece MUST sit on the surface it belongs to, never fight the layer beneath it.

### ART-CROWD-001

Spectators are people in the same art language, with less detail. A crowd figure has a block body, a pentagonal head on its neck, and its eyes and brow placed by the same head fractions as a fighter's (ART-HEAD-001) — never another character's coordinates, which read as a mark at mouth height. The crowd draws each layer's bare mesh in a `MultiMesh`, so every exported layer (`skin`, `fabric`, `leather`, `face`, each hairstyle) MUST share the figure's origin; an offset layer draws away from the rest. Spectators keep shared meshes, a small palette, instance tinting, section-level `MultiMesh` batches, and no shadow casting; no spectator gets its own skeleton or material. Implementation: `tools/blender/bootstrap/build_crowd.py`, `game/src/presentation/world/crowd_stage.gd`. Tests: `PRES-ARENA` (`test_the_same_seed_seats_the_same_people`).

### ART-CROWD-002

A stage seats the crowd its profile names, or nobody. `StagePresentationProfile.crowd` is an optional `CrowdProfile` — the figure scenes, one scene per hairstyle, and the palettes — and `ArenaScaffold` builds a crowd only from it; it never decides from the ground type or a stage name. The Arena names its Roman crowd (`assets/presentation/arenas/standard/roman_crowd.tres`); The End names none, and a deck MUST NOT name one. Every scene a profile names MUST exist and every hairstyle MUST be its own file (`CrowdProfile.problem`), so a missing look fails instead of drawing another. A new scaffold never carries the last stage's crowd, and the application's `StageDefinition.has_crowd` MUST agree with the kit. Tests: `PRES-ARENA` (`test_each_stage_seats_the_crowd_its_profile_names`).

## Coverage (COVERAGE)

### COVERAGE-001

Every non-UX/UI production source file MUST achieve 100% line, function, and branch coverage individually. Web/TypeScript code MUST additionally achieve 100% statement coverage. Coverage is necessary but not sufficient: every behavioral invariant MUST also have an independent, non-vacuous behavioral test.

Coverage MUST be measured per file. Do not use project-average 100%. One file at 99.9% means the gate is RED. No `autoUpdate`. No coverage-ignore comments. No exclusions inside covered roots merely because something is difficult to test.

**Covered scope** includes: authoritative simulation/domain, deterministic math, combat, AI/targeting, economy, production, placement/build validation, game state machines, commands, config resolution, content validation, replay/hash/serialization, application orchestration, interaction/authorization logic, matchmaking, ELO calculation, nonvisual web application/domain logic, and executable presentation logic (directors, feedback mapping, settings scaling, snapshot projection, camera math, impact classification).

**Excluded from numeric 100%** (by architectural scope only): purely visual node hierarchy (scene tree wiring, mesh construction, material assignment), VFX/SFX asset playback, shaders, animation/art polish (what looks/sounds good), purely decorative camera feel (what feels right), third-party addons, generated code, test code itself.

If code affects authoritative state, permissions, simulation outcome, economy, progression, win/loss, deterministic hashes, matchmaking results, ELO ratings, or shipping product behavior, it MUST NOT reside in a coverage-excluded directory.

**Web/Vitest**: `coverage.include` MUST cover every in-scope web source file (`src/**/*.{ts,tsx}` minus tests, `*.d.ts`, and `src/test/`; routes and layouts included). Required: `thresholds: { 100: true, perFile: true }`. No v8/istanbul ignore comments in in-scope code. A mechanical manifest completeness check (`check-coverage-manifest.mjs`, run by `test:coverage`) MUST verify that the set of in-scope filesystem source files equals the set of files present in `coverage-final.json`. A new production file that no test imports MUST cause the manifest check to fail, not silently disappear from the coverage denominator.

**GDScript**: 100% measured line/function/branch coverage is required for in-scope non-UX/UI production scripts before Mechanical Freeze closes. Do not rewrite the existing deterministic harness merely for instrumentation. Mechanical Freeze stays OPEN until measurement exists.

**Content coverage**: catalog-driven content validators MUST cover 100% of canonical entries. A newly registered content item MUST automatically enter the test denominator.

## Testing (TEST)

### SCENARIO-REACHABILITY-001

Interaction and scenario tests MUST reach a constrained configuration through the simulation — fixed ticks and the contact chronology — rather than placing fighters past an earlier contact that would have blocked them, unless the test explicitly targets recovery from an invalid or penetrating initial state (and says so). Pure geometry tests may evaluate any transform; a placed configuration that live play cannot reach is not a scene to tune the solver around. When real ticks reach a broken invariant, the test stays red and the simulation is fixed.

### TEST-TRUTH-001

Every behavioral test MUST explicitly assert its fixture (ARRANGE), the perturbation (PERTURB), run production code (ACT), and verify the contract (ASSERT).

A test's function name and comments are not evidence. Preconditions MUST be asserted before the oracle is invoked.

**Anti-vacuity rules** (test lint MUST reject):

- `assert_true(true)` / equivalent tautologies
- disabled/skipped tests in covered suites
- zero-assertion test functions
- commented-out assertions
- warning-only correctness checks
- coverage-ignore directives
- ignored fallible fixture setup

**Expected results MUST be independent** of production logic under test.

Do NOT use `assert()` for required release behavior. Godot strips `assert()` in non-debug builds. Production handling MUST use explicit `if/else` branches that are testable and present in shipping builds.

### TEST-TIER-001

Every behavioral suite MUST be registered in `game/tests/suite_manifest.json` with a size (`fast`, `focused`, `gate` — all three run in `pnpm test` — or `balance`, `accept`, `ship`, each its own process run only when asked for) and a measured runtime budget, and every production script MUST have an owning area there. The harness, `pnpm test:changed` and `pnpm test:focused` select from that manifest only. A suite over its budget is reported (`SLOW`, `over_budget`), never failed; a budget makes growth visible and is never a target. Statistical corpora (CPU tuning and held-out ladders, the contact ship corpus) MUST NOT run in `pnpm test`, and every long-running case MUST print progress at least once per duel or seed, so the no-output guard stays a hang detector. While implementing, the checks run are the cheapest suites owning the changed code (`test:changed`, `test:focused`); `pnpm test` runs once when an implementation batch is feature-complete; when it is red, every red is classified, reproduced at the lowest useful layer, fixed, and the red suites alone rerun, then one final `pnpm test`; the audits run at release checkpoints. A rules-version change re-pins goldens once per batch, after the replay diff is explained. Tests: `HARNESS` (`test_tiers_partition_the_suites`, `test_the_suite_manifest_is_complete_and_truthful`), `test:tooling` (`game/scripts/test-suite-select.mjs`).

### TEST-OWNERSHIP-001

Every gameplay law has one lowest-level authoritative test owner (Coulomb friction: FRICTION; commitment mapping: MOTION-COMMIT; weapon trajectory: KINEMATICS / SHAPE; parry semantics: CONTACT; frame movement: MOVE). Higher-level suites — scenarios, APP-E2E, FULL-E2E — prove wiring and player journeys and MUST NOT duplicate a law's detailed numerical assertions. When a broad test finds a defect, the defect MUST first be reproduced by a focused regression at the owning layer, and the fix proven there; the broad test then keeps proving only its journey.

### ZERO-TOLERANCE-001

Zero `@warning_ignore`; Godot default warnings are errors. The repository MUST contain zero `@warning_ignore`, `warning_ignore_start`, or `warning_ignore_restore` directives.
